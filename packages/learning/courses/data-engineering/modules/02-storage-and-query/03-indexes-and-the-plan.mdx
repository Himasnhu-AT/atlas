Query latency issues often stem from full table scans rather than sheer data volume. The database query planner provides insight into access paths through query explanation commands.

## Evaluating query execution plans

Inspecting the execution plan reveals how the storage engine resolves a filter:

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer = ?;
```

```
SCAN orders
```

`SCAN` indicates a sequential scan across every row in the table. On small tables this overhead is negligible, but on large tables it causes noticeable query latency.

Adding an index on the filtered column alters the access strategy:

```sql
CREATE INDEX orders_customer ON orders (customer);
```

```
SEARCH orders USING INDEX orders_customer (customer=?)
```

`SEARCH` indicates the database uses the index structure to navigate directly to matching records.

## Trade-offs of index maintenance

Indexes are sorted data structures that require updates on every `INSERT`, `UPDATE`, or `DELETE`. They accelerate read operations while increasing write latency and storage consumption.

In bulk data ingestion pipelines, maintaining multiple indexes during large writes creates substantial overhead. Dropping indexes before bulk loads and rebuilding them afterward is a standard optimization pattern.

Additionally, standard B-tree indexes only support predicates matching the indexed expression. An index on `(customer)` does not accelerate `WHERE lower(customer) = ?`, because the index stores un-transformed values. Wrapping indexed columns in SQL functions bypasses index usage and reverts execution to a full table scan.

## Composite indexes and leftmost prefix matching

An index on multiple columns, such as `(customer, placed_at)`, accelerates queries filtering by `customer` alone, or by both `customer` and `placed_at`. It cannot accelerate queries filtering solely on `placed_at`.

Multi-column indexes operate on the leftmost prefix rule, analogous to a telephone directory sorted by surname then first name. You can look up entries by surname or by full name, but not by first name alone. Column ordering in composite indexes must reflect primary query filter patterns.

## Benchmarking query performance

Execution plans indicate access methods, but actual execution time depends on table cardinality, page cache utilization, and data layout. For tiny tables, sequential scans can outperform index traversals due to reduced I/O overhead.

Always benchmark query execution times on representative data volumes before and after schema modifications.

## What the exercise asks

Inspect query plans to differentiate table scans from index searches, create required single and composite indexes, and verify that query results remain identical before and after index application.
