Joining transactional tables to dimension tables is a standard operation in analytical transformations:

```sql
SELECT o.order_id, o.total, c.country
FROM orders o
JOIN customers c ON c.email = o.customer;
```

Executing this join on uncleaned data often returns fewer rows than the source `orders` table. The query finishes without error, but aggregate sums calculated from the output omit unmatched transactions.

## Root causes of dropped records in joins

Unmatched records in relational joins occur for three distinct reasons:

1. **Missing dimension keys:** The foreign key does not exist in the referenced table. For example, order 1008 has an empty customer string and cannot match any customer record. This is a validation failure that belongs in quarantine storage.
2. **Casing and whitespace mismatches:** Unsanitized keys like `" Grace@Example.com "` fail to match normalized entries like `"grace@example.com"`. Normalizing values at the ingestion boundary avoids ad-hoc `lower(trim(...))` calls in downstream queries that invalidate indexes.
3. **Pipeline synchronization lag:** The order arrived after recent customer signups, but before the customer dimension table refreshed. This indicates an upstream dependency orchestration issue.

All three failure modes present identically in the final result: missing rows.

## Auditing join cardinality and drops

Inner joins discard non-matching rows by definition. The pipeline should quantify and monitor these drops:

```sql
SELECT count(*) FROM orders;
SELECT count(*) FROM orders o JOIN customers c ON c.email = o.customer;
```

Tracking the difference between source row count and joined row count across pipeline runs establishes a baseline. A steady drop rate of two rows per batch may reflect known test accounts, whereas a sudden drop of several hundred rows signals a pipeline incident. The alerting pattern mirrors the rate check introduced in [quarantine, not deletion](lesson:de-cleaning.quarantine-not-deletion).

## Left joins and missing attributes

Replacing an inner join with a `LEFT JOIN` preserves all order records by setting missing customer columns to `NULL`.

This approach is appropriate when the relationship is optional. When dimensional attributes are mandatory, converting missing relations to nulls transfers the burden of null-handling to every downstream consumer. Explicitly capturing unjoined records in an audit table or quarantine store preserves traceability without polluting reporting models.

## Detecting Cartesian multiplication in joins

If a dimension table contains duplicate join keys, an inner join emits multiple output rows for each matching input row. Joining orders to a customer table containing two duplicate records for `ada@example.com` outputs every order placed by Ada twice.

This produces the same double-counting distortion seen with unnesting operations in [shapes that nest](lesson:de-records.shapes-that-nest). Pipelines should verify that the joined row count does not exceed the source table count when joining to a dimensional entity on its primary key.
