Data pipelines establish structural commitments about published datasets. Making these commitments explicit turns an internal transformation workflow into an interface that downstream teams can depend on.

## Components of a data contract

A data contract defines the structural guarantees of a dataset across four core pillars:

1. **Shape:** Column definitions, data types, and nullability constraints. This corresponds to the table schema defined in [loading a table](lesson:de-storage.loading-a-table) combined with the validation logic in [a schema that reports](lesson:de-cleaning.a-schema-that-reports).
2. **Grain:** The primary entity represented by an individual row (for example, "one row per completed order"). Clearly defining table grain prevents double-counting issues like array explosion in [shapes that nest](lesson:de-records.shapes-that-nest) and duplicate join matches in [the rows a join loses](lesson:de-storage.the-rows-a-join-loses).
3. **Freshness:** Expected update cadence, maximum allowable ingestion lag, and automated alerts for stagnant feeds.
4. **Semantics:** Explicit definitions of business column contents (such as whether `total` is gross or net of sales tax, or whether `status` reflects the order state at extraction time).

## Executable contracts versus static documentation

Static wiki documentation quickly falls out of sync with production code. A data contract becomes reliable when expressed as automated, executable assertions.

Each contract component maps directly to an automated verification stage:

- **Shape and types:** Enforced by database schema constraints and ingestion validators.
- **Grain and uniqueness:** Verified via key uniqueness assertions introduced in [counting is a test](lesson:de-contracts.counting-is-a-test).
- **Freshness:** Monitored via independent schedule checkers.
- **Semantic rules:** Verified through relational invariant tests (such as asserting that `total >= subtotal`).

Structuring contracts as executable test suites ensures that violations surface automatically before breaking downstream systems.

## Managing schema and semantic evolution

Schemas evolve as business requirements change. Managing changes through explicit contracts makes updates transparent:

- **Non-breaking additions:** Appending new nullable columns or optional fields does not interrupt existing downstream consumers.
- **Breaking modifications:** Dropping columns, renaming fields, altering entity grain, or changing value definitions invalidates downstream queries.

Breaking modifications require advance notification and versioned transitions to prevent silent report corruption.

## Summary of core pipeline principles

Across these modules, dependable data engineering relies on consistent practices:

- Parse raw files with explicit handling for escaping, delimiters, and malformed lines.
- Implement field coercion functions that return explicit error states rather than silent defaults.
- Collect batch validation errors and route rejected records to quarantine stores instead of dropping them.
- Enforce schema constraints and transaction boundaries during database writes.
- Maintain idempotence across runs using keyed upserts and atomic partition replacement.
- Track incremental watermarks and job completion states to make batch pipelines resumable.
- Deploy automated assertions and independent freshness monitors to verify data integrity.

## Scaling beyond embedded engines

While SQLite serves as an effective learning environment and embedded engine, large-scale production platforms transition to client/server relational engines (such as PostgreSQL), analytical engines and warehouses (such as DuckDB or Snowflake), columnar storage formats (such as Parquet), and workflow orchestrators (such as Airflow or Dagster).

The underlying architectural principles remain identical: orchestrators manage the execution state log described in [the partial run](lesson:de-pipelines.the-partial-run), data warehouses optimize partitioned storage, and automated contracts protect data consumers from silent failures.
