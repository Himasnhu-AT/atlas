      kind: assign
      prompt: Sort each way a batch goes wrong onto the check that would catch it first.
      buckets:
        - id: volume
          label: Row count against recent history
          note: How many rows arrived, compared with what usually arrives.
        - id: uniqueness
          label: Key uniqueness
          note: Whether one order id means one row.
        - id: nullability
          label: Null count on a key column
          note: Whether the column that identifies a row has a value in it.
        - id: domain
          label: Allowed value set
          note: Whether a categorical column still holds values you know about.
      items:
        - id: truncated-export
          label: The extract stopped after 12 rows. A normal day is 9,800.
          bucket: volume
          because: Nothing is wrong with any of the twelve rows. The only thing that is wrong is how few of them there are.
        - id: zero-rows
          label: The source sent nothing at all and the job wrote nothing at all.
          bucket: volume
          because: Every per-row check passes on an empty batch, because there is no row to fail one.
        - id: retried-batch
          label: A retried export re-sent 40 rows out of 9,800.
          bucket: uniqueness
          because: Forty extra rows out of nine thousand does not move the count enough to trip a volume check. The forty duplicate keys are unmissable.
        - id: join-fanout
          label: A join to the items table made each order appear once per item it contains.
          bucket: uniqueness
          because: Most orders have one item, so the count stays inside its band. The grain has changed and only the key shows it.
        - id: renamed-key
          label: A rename upstream left order_id empty on every row written after Tuesday.
          bucket: nullability
          because: The right number of rows arrived and each one is well formed. They cannot be joined to anything, which nothing else here notices.
        - id: new-status
          label: Someone upstream added a status called on_hold and told nobody.
          bucket: domain
          because: The rows are complete and unique and the count is normal. The only evidence is a value you have never seen before.
      hints:
        - Two of these leave every individual row perfectly valid, and two of them leave the row count perfectly normal.
        - A retried export and a fanned out join both change how many rows carry the same key. That is one check, not two.
        - The one about the empty column is not about missing rows. The rows arrived; the column that identifies them did not.
      reveal: >-
        Four counts and a comparison. None of this is statistics, and the work is in
        choosing what to count: a check that counts rows will never see a duplicated key,
        and a check that counts duplicates will never see an empty batch.

      prompt: >-
        Click every assertion that would still pass on the exact batch it was written to

      lang: python
      source: |
        assert rows > 0
        assert rows >= median_7d * 0.5
        assert nulls("order_id") == 0
        assert distinct("order_id") <= rows
        assert set(statuses) <= ALLOWED
        assert sum(total) >= 0
      targets: [3, 5]
      decoys:
        '0': An empty batch has zero rows, so this one fails and says so. It is the cheapest check in the file.
        '1': A batch of twelve against a median of nine thousand eight hundred is well under half, so this fires.
        '2': A rename that empties order_id puts the null count above zero immediately.
        '4': A status nobody warned you about is not in the allowed set, so this raises on the first row that carries it.
      hints:
        - Two of these are true of almost every batch that has ever existed, including the broken ones.
        - Duplicated keys make the distinct count go down. Ask which direction the comparison allows.
        - A decimal point moving two places to the right leaves a sum that is larger, and still not negative.
      reveal: >-
        A check that cannot fail is worse than no check, because it appears in the report
        as a green tick. The uniqueness one needs distinct to equal rows rather than sit

        - The two readouts move in opposite directions, and each has a ceiling. You are looking for the overlap rather than the best value of either.

          "row_count": { "min_fraction_of_median_7d": 0.4 },

          "status_in": ["shipped", "pending", "cancelled", "refunded"]

Pipelines that fail with clear error messages allow immediate triage. Pipelines that complete successfully while writing corrupt numbers often remain unnoticed for extended periods, silently invalidating downstream reports.

Routine verification checks on row counts and key distributions catch the majority of ingestion errors.

## Core data quality assertions

The most effective data quality checks rely on standard assertions:

- **Row count volume:** If a typical batch contains 9,800 records and a new batch contains 12, an upstream extraction step was truncated. Row count assertions catch empty and partial extracts before data lands in reporting tables.
- **Null value assertions:** Critical identifier columns like `order_id` must never contain nulls. Nulls indicate schema mismatches or unconstrained write paths.
- **Uniqueness checks:** Verifying primary key uniqueness ensures that duplicate extraction batches or multiplying joins have not inflated record counts.
- **Allowed value sets:** Validating categorical columns like `status` against an allowable set detects unannounced upstream enum changes immediately.
- **Aggregate range assertions:** Verifying that the sum of numeric columns like `total` falls within historical tolerances prevents corrupted decimal points or Cartesian join explosion.

## Setting effective alert thresholds

Selecting alert thresholds requires balancing sensitivity against false positives:

- **Overly strict thresholds:** Triggering alerts on routine variance (such as weekend dips or promotional spikes) leads to alert fatigue, causing teams to ignore notifications.
- **Overly loose thresholds:** Failing to trigger alerts allows significant data degradation to proceed unnoticed.

A reliable approach uses **relative thresholds** based on recent historical moving medians rather than hard-coded constants. For example, validating that a batch row count falls within 50% of the median across the previous seven days accommodates organic business growth while catching catastrophic extraction failures.

## Data quality evaluation stages

Quality checks can execute at different stages of the data lifecycle:

- **Pre-write staging checks:** Validating records in temporary staging tables before writing to production tables prevents corrupt records from becoming visible to consumers.
- **Post-write checks:** Validating tables immediately following commits ensures errors are logged and consumers are notified before daily analytical jobs run.

Automated threshold alerts running directly in the pipeline provide faster issue detection than manual dashboard reviews.

## What the exercise asks

Implement five data quality assertions and a test runner that executes all checks and collects complete diagnostic results (rather than halting on the first failure).

Returning comprehensive test diagnostics allows data teams to evaluate overall dataset usability across multiple dimensions.
