Validation assertions inspect incoming payloads, but fail to detect scenarios where no data arrives at all.

When an upstream source stops transmitting, downstream ingestion tasks find zero new records, write zero rows, and exit with status code zero. Dashboards continue to render static metrics without alerting teams to data stagnation.

## Measuring record timestamp freshness versus job execution

Checking whether a scheduled job executed successfully does not verify data recency. The job may execute cleanly while processing an empty queue.

Verifying data freshness requires inspecting the newest business timestamp in the dataset:

```sql
SELECT max(placed_at) FROM orders;
```

Combining job execution status with data recency isolates the specific failure mode:

| Job executed | Data fresh | Diagnosis |
|---|---|---|
| Yes | Yes | Pipeline healthy |
| Yes | No | Pipeline running, upstream source delivery halted |
| No | Yes | Scheduler failure, data within tolerance |
| No | No | Scheduler offline, data stale |

Differentiating between scheduler failures and upstream ingestion halts directs remediation alerts to the responsible team.

## Cadence awareness and business hour exclusions

Freshness thresholds depend on expected ingestion schedules and business calendars:

- An hourly stream is stale if no records arrive for two hours.
- A nightly batch arriving at 02:00 UTC is expected to show 22 hours of lag at 00:00 UTC, but indicates a failure if lag persists past 03:00 UTC.
- Feeds that operate exclusively on weekdays will trigger false alarms on Monday mornings if measured in calendar hours rather than business hours.

Freshness logic must incorporate expected delivery intervals and business day exclusions to prevent alert fatigue.

## Volume-weighted freshness

A subtle failure mode occurs when data continues to arrive, but at a fraction of expected volume.

If an integration failure drops 95% of incoming traffic, new records still arrive continuously and pass basic timestamp freshness checks. Pairing timestamp checks with rolling volume assertions (introduced in the previous lesson) ensures both recency and completeness are verified together.

## Decoupling freshness checks from pipeline schedules

Freshness monitors must execute independently of the pipelines they monitor.

Embedding freshness checks as the final step in a batch pipeline creates a failure blind spot: if the pipeline crashes or the scheduler fails to trigger the job, the freshness check never executes. Running freshness monitors on an independent external schedule ensures monitoring continues during pipeline outages.

## What the exercise asks

Calculate the age of the latest record, evaluate staleness against configured schedule intervals, combine job run history and data age into a diagnostic status, and apply weekend calendar exclusions.
