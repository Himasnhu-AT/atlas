Full table reloads on a nightly cadence provide simple operational semantics. As datasets expand, pipelines transition to incremental synchronization using a **watermark**: a cursor recording the latest state or timestamp processed by previous runs.

## Boundary conditions and record loss in watermarks

A naive approach records the maximum `placed_at` timestamp from the previous batch and filters for subsequent records using strict inequality:

```sql
SELECT * FROM source WHERE placed_at > :watermark
```

Strict inequality silently skips records whenever multiple transactions share the exact boundary timestamp. If the final record processed by a batch had timestamp `2026-03-06T09:14:00`, any additional records created at that exact second are excluded by `>` and will never be processed.

Using inclusive bounds (`>=`) retrieves all boundary records:

```sql
SELECT * FROM source WHERE placed_at >= :watermark
```

Inclusive filtering causes boundary records to be fetched again. Combined with idempotent upserts, re-evaluating boundary records ensures that no records with identical timestamps are omitted.

## Handling late-arriving records

Records often arrive out of chronological order due to long-running source transactions, delayed ingestion queues, or retroactively edited entries.

A watermark filtering strictly on a business event timestamp cannot detect records inserted with historical event dates. Data architectures address late-arriving data using three primary strategies:

1. **Ingestion timestamps:** Tracking a monotonic system insertion timestamp (`created_at` or `_ingested_at`) assigned by the source database on write, rather than relying on mutable business dates.
2. **Lookback windows:** Querying an overlapping window (such as the watermark minus three hours) to capture delayed records, relying on upserts to deduplicate previously processed rows.
3. **Periodic full reconciliations:** Supplementing incremental runs with scheduled batch re-syncs to reconcile historical discrepancies.

Combining an overlapping lookback window with regular reconciliation provides high consistency without requiring full reloads on every cycle.

## Atomic watermark commits

Updating the watermark outside the transaction that writes the batch data introduces failure vulnerabilities:

- Committing the watermark before writing data causes crash recovery to skip the batch entirely.
- Committing the watermark in a separate follow-up transaction risks leaving the data committed while the watermark remains behind.

Updating the watermark table inside the **same database transaction** as the data write guarantees that data and tracking state advance together atomically.
