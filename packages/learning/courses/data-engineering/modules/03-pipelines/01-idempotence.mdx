Data pipelines regularly execute multiple times across the same input dataset. Schedulers retry failed tasks after network timeouts, backfill jobs reprocess historical partitions, and deployment rollouts replay queue messages.

Pipeline designs must account for repeated executions without producing side effects or corrupting state.

## Defining pipeline idempotence

An operation is idempotent when executing it multiple times produces the identical final system state as executing it once.

In data engineering, this definition requires a specific property: the state of the target datastore after $N$ runs over the same input must match the state after a single successful run, even if previous attempts were interrupted halfway through.

Handling unexpected interruptions during execution is essential for building resilient batch architectures.

## Operations that break idempotence

Several common write patterns violate idempotence:

- **Unconditional inserts:** Appending records on every run produces duplicate rows. While primary key constraints prevent silent duplication, naive inserts cause subsequent runs to fail with integrity errors rather than succeeding idempotently.
- **Incremental updates:** Statements like `UPDATE totals SET amount = amount + ?` are valid only during the initial run. Each subsequent retry inflates aggregate metrics without leaving an audit trail of the overcount.
- **Unbounded file appends:** Appending batch output to existing files duplicates data on every retry.
- **Premature side effects:** Triggering external notifications (such as webhook posts or emails) mid-pipeline causes duplicate alerts during retries. External side effects should occur only after storage transactions commit.

## Patterns for idempotent data processing

Three structural patterns ensure idempotent pipeline behavior:

1. **Keyed upserts:** Using primary keys with conflict resolution (`ON CONFLICT DO UPDATE`) allows re-runs to update existing rows with corrections instead of inserting duplicates.
2. **Partition replacement:** Defining units of work by explicit partitions (such as a calendar date) allows pipelines to atomically replace the partition:

```sql
DELETE FROM orders WHERE placed_at = ?;
-- then insert that day's rows
```

Executing a partition delete followed by inserts within a single database transaction guarantees idempotence by construction. It repairs malformed partitions on replay and avoids complex row-level merging logic. The partition boundary must rely on an immutable business timestamp from the record rather than the ingestion execution time.

3. **Derivation over accumulation:** Deriving metrics directly from underlying transactional records ensures consistent results across repeated runs.

## Distinction between idempotence and data safety

Idempotence ensures that pipeline execution is deterministic given a specific input. However, idempotence does not guarantee that the input itself is valid.

For example, re-running a partition replacement with an empty or truncated input file empties the target partition. Idempotent execution must be paired with pre-write validation to verify extract integrity before committing changes to production storage.
