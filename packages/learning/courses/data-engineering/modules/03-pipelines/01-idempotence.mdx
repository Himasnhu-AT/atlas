      prompt: >-
        Each of these is the whole of what one pipeline step does. Sort them by what the

      buckets:
        - id: unchanged
          label: The same state as one run
          note: Running it again lands where the first run landed.
        - id: more-rows
          label: More rows than one run
          note: The second pass adds records the first pass already wrote.
        - id: bigger-number
          label: A number that moved
          note: No new rows, and a stored figure that no longer matches reality.
        - id: outside
          label: The table is fine, the world is not
          note: Storage ends up correct and something outside the database happened twice.
      items:
        - id: plain-insert
          label: INSERT INTO orders VALUES (?, ?, ?) for every row in the extract.
          bucket: more-rows
          because: Nothing here asks what is already there. With a primary key the second run fails instead, which is louder but still not a run you can repeat.
        - id: append-file
          label: Open the day's output file in append mode and write the batch to it.
          bucket: more-rows
          because: The same shape as the unconditional insert, with no key available to make it fail loudly. A file has no constraints, so the duplication is silent.
        - id: accumulate
          label: UPDATE totals SET amount = amount + ? WHERE day = ?
          bucket: bigger-number
          because: Correct exactly once. Nothing in the statement remembers what it has already added, so there is no conflict clause that could repair it.
        - id: bump-counter
          label: UPDATE runs SET n = n + 1 WHERE job = ?
          bucket: bigger-number
          because: The same accumulation, and a good example of why it is not always a bug. A count of executions is meant to move on every run.
        - id: upsert
          label: INSERT with ON CONFLICT(order_id) DO UPDATE SET total = excluded.total
          bucket: unchanged
          because: The row is addressed by its key rather than appended, so a second run overwrites what the first run wrote with the same values.
        - id: replace-partition
          label: DELETE the day's rows, then insert the day's rows, in one transaction.
          bucket: unchanged
          because: The write states what the partition should contain rather than what to add to it, so replaying it repairs a half-written partition instead of doubling it.
        - id: derive-total
          label: Recompute the day's total from the orders table and write it keyed by day.
          bucket: unchanged
          because: Derived from the rows rather than accumulated across runs. Two runs read the same rows and compute the same figure.
        - id: notify-customer
          label: Email each customer whose order was loaded, as the row is written.
          bucket: outside
          because: An upsert can correct a row. Nothing can unsend a mail, which is why external effects wait until the transaction that justified them has committed.
      hints:
        - Read each one as a sentence about the state it is writing into. Some of them mention that state and some do not.
        - Two of these add to something rather than setting it, and only one of the two is a bug.

      reveal: >-
        The safe three all name what the result should be. The unsafe ones all describe a
        change to apply, and a change applied twice is applied twice. That is the whole

        - id: upsert-only
          label: Use upserts and never delete anything.
          note: Nothing gets emptied, and nothing gets removed either, so a partition that legitimately shrank keeps rows the source no longer has. It swaps a visible failure for an invisible one.

          label: Compare the extract against what the partition held before, and refuse to write when it falls outside the expected range.

          note: The write is gated on a fact about the input rather than about the run. Zero rows fails, a tenth of the usual volume fails, and a real holiday is a threshold somebody chose on purpose.

Data pipelines regularly execute multiple times across the same input dataset. Schedulers retry failed tasks after network timeouts, backfill jobs reprocess historical partitions, and deployment rollouts replay queue messages.

Pipeline designs must account for repeated executions without producing side effects or corrupting state.

## Defining pipeline idempotence

An operation is idempotent when executing it multiple times produces the identical final system state as executing it once.

In data engineering, this definition requires a specific property: the state of the target datastore after $N$ runs over the same input must match the state after a single successful run, even if previous attempts were interrupted halfway through.

Handling unexpected interruptions during execution is essential for building resilient batch architectures.

## Operations that break idempotence

Several common write patterns violate idempotence:

- **Unconditional inserts:** Appending records on every run produces duplicate rows. While primary key constraints prevent silent duplication, naive inserts cause subsequent runs to fail with integrity errors rather than succeeding idempotently.
- **Incremental updates:** Statements like `UPDATE totals SET amount = amount + ?` are valid only during the initial run. Each subsequent retry inflates aggregate metrics without leaving an audit trail of the overcount.
- **Unbounded file appends:** Appending batch output to existing files duplicates data on every retry.
- **Premature side effects:** Triggering external notifications (such as webhook posts or emails) mid-pipeline causes duplicate alerts during retries. External side effects should occur only after storage transactions commit.

## Patterns for idempotent data processing

Three structural patterns ensure idempotent pipeline behavior:

1. **Keyed upserts:** Using primary keys with conflict resolution (`ON CONFLICT DO UPDATE`) allows re-runs to update existing rows with corrections instead of inserting duplicates.
2. **Partition replacement:** Defining units of work by explicit partitions (such as a calendar date) allows pipelines to atomically replace the partition:

```sql
DELETE FROM orders WHERE placed_at = ?;
-- then insert that day's rows
```

Executing a partition delete followed by inserts within a single database transaction guarantees idempotence by construction. It repairs malformed partitions on replay and avoids complex row-level merging logic. The partition boundary must rely on an immutable business timestamp from the record rather than the ingestion execution time.

3. **Derivation over accumulation:** Deriving metrics directly from underlying transactional records ensures consistent results across repeated runs.

## Distinction between idempotence and data safety

Idempotence ensures that pipeline execution is deterministic given a specific input. However, idempotence does not guarantee that the input itself is valid.

For example, re-running a partition replacement with an empty or truncated input file empties the target partition. Idempotent execution must be paired with pre-write validation to verify extract integrity before committing changes to production storage.
