A backfill over thirty days dies on day twenty. What now?

If the answer is "start again", the backfill is not really a tool, it is a gamble that gets
worse as the range gets longer. And re-running the first nineteen days is not free even when
it is safe: it is time, it is load on the source, and it is nineteen more chances to hit
whatever killed day twenty.

## A run has to leave a trace

Resuming needs one thing: a durable record of which partitions completed. Not in memory, not
in the log, in a table.

```sql
CREATE TABLE run_log (
    partition   TEXT PRIMARY KEY,
    status      TEXT NOT NULL,      -- 'running' | 'done' | 'failed'
    rows_written INTEGER,
    started_at  TEXT NOT NULL,
    finished_at TEXT
);
```

That is enough to answer "what is left", which is the only question a resume asks.

`running` matters as much as `done`. A partition marked `running` with no `finished_at` is one
that was interrupted, and it is different from one that was never attempted: it may have
written some rows. If the write is idempotent it can simply be redone, which is the whole
reason the earlier lessons insisted on it.

## Mark done after, not before

Same argument as the watermark, and it is the same mistake wearing a different hat. Write the
partition, then mark it done, in the same transaction if you can. Marking it done first means
a crash produces a partition that is recorded as complete and is not.

If the target and the run log are in the same database, one transaction covers both. If they
are not, you cannot have atomicity across them and the honest choice is to mark done **after**
and accept that a crash in the gap means a partition gets redone. Redoing an idempotent
partition costs time. Skipping one costs data.

## Failure is a status, not an exception

A partition that failed should be recorded as failed, with the error, and the run should carry
on to the next one.

Stopping at the first failure is right for a daily run of one partition and wrong for a
backfill of thirty, because one bad day should not hide the fact that the other twenty-nine
were fine. What you want at the end is a report: twenty-nine done, one failed, here is which
and why.

The exception to that is a failure that means everything after it will also fail — the source
is unreachable, the disk is full. Distinguishing "this partition is bad" from "everything is
bad" is genuinely hard, and the usual compromise is a consecutive-failure limit: stop after
three in a row, on the reasonable guess that it is no longer about the data.

## Concurrency, briefly

Two copies of the same backfill running at once is a real hazard, usually because somebody
started it again thinking the first had died.

The primary key on `partition` gives you a cheap defence: claim a partition by inserting a
`running` row, and if the insert conflicts, somebody else has it. That is not a distributed
lock and it will not save you from every interleaving, but it turns the common case from
silent double-processing into a row that says who got there first.

## What the exercise asks

A run log, a resumable runner that skips what is done and retries what was interrupted, a
consecutive-failure limit, and a report of what happened.

The test kills the runner partway through and resumes it, then checks the final state matches
running it straight through.
