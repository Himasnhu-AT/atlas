When a long-running batch job processing thirty historical partitions fails on partition twenty, restarting the entire job from the beginning introduces unnecessary latency, source database strain, and additional opportunities for transient failures.

Resuming execution requires structured tracking of completed work.

## Durable state tracking for pipeline runs

To enable deterministic resume behavior, the pipeline maintains a persistent run log in database storage:

```sql
CREATE TABLE run_log (
    partition   TEXT PRIMARY KEY,
    status      TEXT NOT NULL,      -- 'running' | 'done' | 'failed'
    rows_written INTEGER,
    started_at  TEXT NOT NULL,
    finished_at TEXT
);
```

This table allows resuming processes to identify unfinished partitions immediately.

The `running` status is critical: a partition marked `running` without a `finished_at` timestamp indicates an interrupted job. Because individual partition operations are designed to be idempotent, interrupted partitions can be safely re-executed upon resumption.

## Ordering status transitions and data writes

Status updates must synchronize with data commits:

1. Write partition data.
2. Mark the partition status as `done` within the same database transaction whenever possible.

Marking a partition as `done` before committing its data risks recording a partition as complete when it was interrupted. When data writes and metadata updates live in separate datastores without cross-database transactions, update the metadata store **after** the data write commits. A crash between the two causes an idempotent partition re-run rather than silent data omission.

## Treating failure as operational state

Individual partition failures should be recorded as structured state in the run log rather than unhandled process crashes.

In multi-partition backfills, a single malformed partition should not halt processing for the remaining valid partitions. The runner logs the specific partition error, transitions its status to `failed`, and advances to the next partition.

However, environmental failures (such as storage capacity limits or network disconnection) affect all subsequent runs. To handle widespread infrastructure issues, runners enforce a consecutive-failure threshold: aborting the job after three successive failed partitions.

## Guarding against concurrent executions

Concurrent runs across the same partition range risk conflicting writes.

Using a `PRIMARY KEY` constraint on `partition` in the run log provides concurrency protection: a job attempts to insert a record with status `running`. If an active run record already exists, the conflicting insert alerts the runner that another process is handling the partition.

## What the exercise asks

Implement a run log table, a resumable batch runner that skips completed partitions and retries interrupted ones, a consecutive-failure threshold, and execution summary reporting.

The test suite halts the runner partway through execution, restarts the process, and verifies that final storage state matches an uninterrupted run.
