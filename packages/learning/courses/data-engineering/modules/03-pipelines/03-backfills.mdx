      prompt: >-
        A day that held four hundred orders is corrected upstream and now legitimately
        holds none. The backfill reruns that partition. Which write leaves the table
        agreeing with the source?
      options:
        - id: upsert-only
          label: Upsert every row in the payload.
          note: The payload has no row for the four hundred that were removed, so nothing addresses them and all four hundred stay. The table now disagrees with the source and nothing raised.
        - id: delete-then-insert
          label: Delete the partition, then insert the payload, in one transaction.
          correct: true
          note: The delete is what deals with rows that are no longer sent. An empty payload leaves an empty partition, which here is the correct answer rather than the accident.
        - id: soft-delete
          label: Flag the missing rows as deleted rather than removing them.
          note: It keeps the history and hands every consumer a WHERE clause they have to remember. That is a decision about the table's contract, not a fix for the backfill.
        - id: skip-empty
          label: Treat an empty payload as nothing to do and move on.
          note: That is the guard against an empty extract wiping a good partition, and here the emptiness is real. A rule that cannot tell a broken extract from a closed shop belongs in validation as a threshold, not here as a hard skip.
      hints:
        - Nothing in the payload mentions the rows that were removed. Ask which write can act on a row it was not sent.
        - Two of these leave the four hundred rows readable. One of the two is a deliberate contract and one is an accident.
        - The right answer here is the same write that makes a re-run safe, and for the same reason.
      reveal: >-
        Replacement handles removals because it states what the partition should contain
        rather than what to add to it. Upserts cannot, because a row that is gone sends
        nothing to conflict with. This is the case that decides between the two patterns,
        and it only shows up on the day something upstream is genuinely deleted.

      because:
        order-check: This decides whether the range can be split across workers or has to go through one at a time, and it is far cheaper to answer than to discover halfway.
        stage: The same code with one parameter changed. If this needs a separate script, the backfill has already stopped being the same job as the nightly run.
        diff: Staging without comparing is a rehearsal nobody watched. This is the step that catches the logic change nobody meant to make.
        verify: A run that recorded counts nobody read produced a log file. The counts exist so that they can be held against something.
      hints:
        - Two of these happen before production is touched at all.
        - One decides whether the middle of this can be split across workers, and it is not a question you want to answer after the run.
        - The run is not the last step, because a number nobody compares against anything has not checked anything.

        A backfill is the nightly job with a wider date range, and every step here exists to
        prove that before it touches five weeks of production. The staging pass and the
        comparison are the whole safeguard. The per-partition record is what makes a failure
        on day twenty cost twenty minutes instead of the entire range.

When business logic bugs affect historical records, repairing the dataset requires reprocessing historical partitions without introducing side effects or schema divergence.

## Unifying scheduled runs and historical backfills

A common failure mode in data platforms is maintaining a separate, ad-hoc script for historical reprocessing that diverges from the production pipeline codebase.

When pipeline jobs are parameterized by target partition boundaries (such as a date parameter), the scheduled daily run and the historical backfill execute the exact same core logic:

```python
for day in days_between("2026-02-01", "2026-03-06"):
    run(day)
```

Partition-level replacement allows jobs to execute predictably over any historical date range. Pipelines relying on unkeyed appends cannot safely reprocess history without dedicated cleanup scripts.

## Partition execution ordering constraints

Partition dependencies determine whether historical ranges can execute concurrently:

- **Stateless partitions:** When each date partition calculates output independently of adjacent dates, partitions can execute in parallel or arbitrary order.
- **Stateful dependencies:** When output depends on previous state (such as rolling balances, cumulative sums, or Type 2 slowly changing dimensions), partitions must execute sequentially in strict chronological order.

Documenting execution ordering constraints explicitly in code prevents regressions when batch runners are refactored for concurrent execution.

## Operational safeguards for historical re-runs

Backfills process large volumes of data against production tables. Three architectural practices mitigate operational risk:

1. **Resumable execution:** Tracking partition-level status ensures that failures on day 20 of a 30-day backfill do not require restarting from day one.
2. **Partitioned reporting:** Emitting structured metadata per partition (including records read, records written, and execution time) provides clear visibility into reprocessing progress.
3. **Target parameterization:** Allowing destination tables to be configured via parameters permits dry runs against staging tables before updating production datasets.

## Purging stale partition data

Reprocessing logic must handle partitions where source records were deleted or corrected to zero rows. An insert-only approach leaves outdated rows in the target table indefinitely.

A delete-then-insert pattern within a single transaction handles empty partitions cleanly by removing obsolete records before inserting the updated record set. Pure upserts require explicit deletion logic for rows omitted from the updated payload.

## What the exercise asks

Implement a date range generator, an idempotent single-partition runner, a backfill driver that iterates through date partitions with progress reporting, and cleanup logic for emptied partitions.

The verification test executes the complete backfill process twice to confirm that target tables reach an identical state across repeated runs.
