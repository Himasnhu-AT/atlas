With field coercions capable of reporting failure, the next step is applying them across full records and entire datasets to produce structured validation summaries.

## Reporting errors instead of raising exceptions

In transactional web services, halting execution on validation failure is standard practice:

```python
def validate(row):
    if not row["order_id"]:
        raise ValueError("missing order_id")
```

Batch ingestion requires a different pattern. The operational unit of work is the entire batch or extract. Halting immediately on row four prevents evaluating the remaining 9,996 rows. Operational monitoring requires complete visibility: knowing that 9,997 rows passed, two lacked identifiers, and one contained an unparseable quantity.

A batch validator accumulates diagnostics and returns a structured report rather than raising an immediate exception.

## Structure of field validation rules

Field specifications require three parameters: the field name, the coercion callable, and a boolean flag indicating whether the field is required:

```python
{"name": "quantity", "coerce": to_int, "required": False}
```

The `required` flag differentiates distinct failure categories:

- A required field that is missing indicates an incomplete payload from the source.
- An optional field that contains an invalid, unparseable value indicates malformed source data.

Keeping these error categories separate allows upstream teams to distinguish between missing columns and unparseable contents.

## Producing actionable error diagnostics

Generic errors like `"invalid quantity"` make troubleshooting large datasets difficult. An actionable diagnostic includes the source row index, field name, rejected value, and failure description:

```python
{"row": 6, "field": "quantity", "value": "unknown", "problem": "not an integer"}
```

The row index must reflect the original line number in the source file, not an internal index in an already filtered array. Retaining original line numbers and invalid values ensures error logs can be audited against source files.

## Partitioning valid and invalid records

The validation engine splits the input dataset into two collections: valid records and invalid records, accompanied by error metadata.

Separating records without discarding invalid entries allows downstream loaders to make context-dependent decisions:

- A regular batch pipeline can load valid records and write invalid records to quarantine storage.
- A strict database migration can abort if any record fails validation.
- A backfill operation can ingest records while tagging problematic entries for manual review.

## What the exercise asks

Implement three components:

1. A field validation rule definition.
2. A row validator that evaluates fields against rules and collects errors.
3. An extract validator that processes batches, returning valid records, invalid records, and an error frequency summary by field.

An aggregated error summary provides immediate visibility into systematic upstream schema changes.
