Every field in a raw delimited file arrives as text. Values such as `29.99`, `2026-03-02`, and `unknown` are all strings. Transforming them into typed values requires explicit assumptions about source formatting.

## Three approaches to invalid values

Consider the `quantity` field across multiple rows. Most rows contain values like `2` or `3`. One row contains an empty string, and another contains `unknown`.

```python
int(row["quantity"])
```

Calling `int()` directly raises a `ValueError` on non-numeric strings. This approach halts immediately on the first malformed row. While explicit, failing immediately on row four in a million-row batch prevents auditing errors in the remainder of the dataset.

```python
int(row["quantity"] or 0)
```

Falling back to default values masks data quality problems. An empty string silently coerces to zero, while `unknown` still raises an exception. Replacing missing quantities with zero corrupts aggregated metrics, making unverified transactions indistinguishable from valid zero-item transactions.

A reliable pattern returns both the parsed value and a status flag:

```python
value, ok = to_int(row["quantity"])
```

Explicit return tuples require callers to handle parsing failures directly, allowing pipelines to collect row-level validation errors without crashing.

## Ambiguity in date parsing

Timestamps in extracts often arrive in varying formats:

```
2026-03-01
01/03/2026
2026-03-02T09:14:00
```

ISO 8601 strings (`2026-03-01` and `2026-03-02T09:14:00`) are unambiguous. Slash-delimited dates (`01/03/2026`) are ambiguous: they can represent March 1 or January 3 depending on regional conventions. If every day value in a dataset is 12 or below, the format cannot be determined from values alone.

The reliable approach defines an explicit expected format, documents the parsing convention, and flags rows that violate it. Applying cascading `try/except` heuristics across multiple formats within a single column risks parsing some rows as day-first and others as month-first, destroying timestamp consistency.

## Empty values versus missing fields

Distinguishing between empty and missing fields is essential for root-cause analysis:

- An **empty value** (`""`) indicates that a column was present in the record but contained no data. This is typically a source-system data entry issue.
- A **missing field** indicates that the record lacked the column entirely due to line truncation or schema drift. This points to an export or transport issue.

Mapping both conditions unconditionally to `None` removes the diagnostic distinction needed to identify upstream pipeline failures.
