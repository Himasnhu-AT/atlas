      kind: order
      prompt: Put one pass of the dollar bar aggregator in order.
      items:
        - { id: open-bar, label: Take the open from the first tick after the last reset }
        - { id: accumulate, label: 'Add price times size to the running dollar total, and update the high, low, close and share volume' }
        - { id: test, label: Compare the running dollar total against the threshold }
        - { id: emit, label: Emit the completed bar }
        - { id: reset, label: Clear the accumulators so the next tick opens a new bar }
        - { id: tail, label: Decide what happens to the partial bar left when the stream ends }
      solution: [open-bar, accumulate, test, emit, reset, tail]
      because:
        accumulate: The tick has to be inside the bar before the threshold is tested, or the bar that crosses the threshold is emitted without the trade that crossed it.
        test: Testing after accumulating is what makes the bar close on the crossing tick rather than one tick later.
        reset: The reset has to happen after the emit and before the next tick, and forgetting it is how one bar's high leaks into the next.
        tail: The stream always ends mid bar. That leftover is not a bar and it never reached the threshold, so treating it as one puts a short, unrepresentative observation at the end of every series.
      hints:
        - The threshold test reads a running total, so something has to have run before it.
        - Two of these six only happen on the ticks that complete a bar.
        - One of them happens once, after every tick has been seen.
      reveal: >-
        The partial tail is the step people leave out, and it is the one that shows up in
        live trading rather than in the backtest. In a backtest the stream ends once. In
        production it ends every time the process restarts, and a system that emits the
        partial bar on shutdown produces a short bar at every restart, all of which have
        larger returns per unit of dollar volume than any real bar does.

    - id: setting-the-threshold
      kind: choice
      prompt: >-
        You are running dollar bars across a universe of 500 names over twelve years. How do

      options:
        - id: fixed-forever
          label: One constant dollar threshold, fitted once on the first year of data
          note: Traded value grows with the market and with the company. Twelve years on, the same threshold produces several times as many bars a day, so the number of observations per year is a fact about the calendar rather than about information.
        - id: adv-fraction
          label: A rolling fraction of trailing dollar volume, retargeted so an average day gives a fixed number of bars
          correct: true
          note: This holds the bar count roughly constant per name per day, so a one bar return means about the same amount of trading in 2014 as in 2026 and in a mega cap as in a small cap. The labels and features built on top can then be pooled.
        - id: tick-count
          label: Sample every N trades, since trade arrivals already track activity
          note: Closer to information time than the clock is, and still fooled by order slicing. One parent order chopped into 200 child fills prints 200 events, and the algorithm doing the chopping changes from year to year.
        - id: share-volume
          label: Sample every N shares
          note: Invariant to how the size is sliced, but not to price. A name that triples transacts three times the value per share bar, and a split resets the entire series to a different meaning of the same threshold.
      hints:
        - Ask what each threshold means to a name whose price has tripled since the sample started.
        - Two of these are broken by the same thing, which is that value per unit changes over time.
        - The property you want is a stable number of bars per day, so make that the thing you set.
      reveal: >-
        The threshold is chosen to hit a bar count, not a dollar figure, and the dollar figure
        is whatever delivers that count on trailing volume. It gets recomputed on a schedule
        and never from the period being sampled, because a threshold fitted on the same window
        it samples has already seen how that window ends.

Standard financial analysis aggregates transactions into fixed time bars (e.g. 1-minute, 5-minute, or 1-day OHLCV candles).

Time bars present structural flaws:
1. **Uneven information arrival**: Markets process vast transaction volumes during market open and macroeconomic announcements, but trade thinly during midday lulls. Fixed time bars sample noise during quiet periods and over-compress information during turbulent bursts.
2. **Fat tails and heteroskedasticity**: Return distributions computed from time bars exhibit severe kurtosis (fat tails) and time-varying variance, violating standard regression assumptions.

## Information-driven dollar bars

**Dollar bars** sample market observations whenever a fixed aggregate dollar volume has transacted:

$$
\sum_{k=1}^M P_k \cdot V_k \ge \Theta_{\text{dollar}}
$$

Sampling by dollar value provides three properties:
* The number of bars generated scales dynamically with market activity.
* Return series generated from dollar bars exhibit properties closer to normal (Gaussian) distributions with stable variance.
* The sampling rate automatically adjusts for long-term price drift and stock splits.
