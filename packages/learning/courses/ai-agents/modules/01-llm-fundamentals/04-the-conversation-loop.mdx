A chat completions API is stateless. The provider retains no session objects across requests. Multi-turn dialogue is maintained by passing a growing array of message objects on every call:

```python
response = client.chat.completions.create(
    model="mock",
    messages=[
        {"role": "system", "content": "You are a terse assistant."},
        {"role": "user", "content": "Capital of France?"},
        {"role": "assistant", "content": "Paris."},
        {"role": "user", "content": "And of Japan?"},
    ],
)
```

The model generates "Tokyo" because preceding dialogue turns are explicitly included in the request payload. Removing earlier turns clears that context from subsequent inference.

Understanding conversation state management is essential, as every multi-turn agent architecture builds upon this list structure.

## Message roles and authorization

Chat APIs define four primary message roles:

| Role | Author | Purpose |
| --- | --- | --- |
| `system` | Application developer | Persistent instructions and behavioral constraints |
| `user` | End user or client | Current query or prompt input |
| `assistant` | Model output | Previous generated responses recorded in dialogue history |
| `tool` | Application runtime | Structured output returned by executed tools |

The `system` message provides baseline instructions. Post-training conditions the model to prioritize system instructions over user input, establishing a boundary between administrative rules and untrusted user data.

`assistant` messages record what the model returned. Application code can edit or prune these entries, such as dropping truncated responses before they contaminate conversation history.

`tool` messages provide function execution outputs, each referencing a specific `tool_call_id` requested by the preceding assistant turn.

## Conversation growth and execution cost

Turn 1 submits the system prompt and the initial user query. Turn 2 submits both original messages, the assistant reply, and the new user message.

```python
class Conversation:
    def send(self, message):
        self._messages.append({"role": "user", "content": message})
        response = self._client.chat.completions.create(
            model="mock", messages=self._messages,   # full history sent on every turn
        )
        reply = response.choices[0].message.content
        self._messages.append({"role": "assistant", "content": reply})
        return reply
```

The application owns `self._messages`. The token cost of turn `n` scales with cumulative dialogue length rather than the length of the newest turn.

## History pruning and message boundaries

When conversation history approaches context window capacity, apply pruning rules:
1. Pin the `system` message at index 0. Removing or shifting system instructions alters agent behavior unpredictably and invalidates prompt caches.
2. Retain the most recent `user` message to preserve the active task context.
3. Apply a sliding window across intermediate exchanges.

When trimming conversations containing tool calls, preserve tool exchange integrity:

```python
history = [
    {"role": "system",    "content": "You are a support agent."},        # 0
    {"role": "user",      "content": "Where is order 5512?"},            # 1
    {"role": "assistant", "content": None,                               # 2
     "tool_calls": [{"id": "call_1", "type": "function",
                     "function": {"name": "lookup_order", "arguments": '{"id": 5512}'}}]},
    {"role": "tool",      "tool_call_id": "call_1", "content": "in transit"},  # 3
    {"role": "assistant", "content": "It is in transit."},               # 4
    {"role": "user",      "content": "And 5513?"},                       # 5
]
```

If a sliding window keeps the last three messages (indexes 3, 4, and 5), message 3 becomes an orphaned `tool` result lacking its matching assistant tool call. Provider APIs will reject this payload.

Adjust the window boundary backward to include the initiating assistant message:

```python
start = len(rest) - keep_last
while start > 0 and rest[start]["role"] == "tool":
    start -= 1
```

This backward adjustment ensures every retained `tool` message has its corresponding `assistant` turn intact.

## The agent control loop

In multi-step agents, `finish_reason` dictates loop continuation, as introduced in [reading a completion](lesson:ai-foundations.reading-a-completion).

When `finish_reason == "tool_calls"`, the model has not completed its task. The application executes the requested functions, appends the assistant call and tool result messages, and invokes the model again. The loop exits when `finish_reason` becomes `"stop"`.

If `finish_reason == "length"`, token generation halted mid-turn. Applications should raise an exception (such as `TruncatedReply`) and prevent partial content from entering conversation state.
