A language model does not ingest raw string characters. A tokenizer segments the text into integer IDs from a fixed vocabulary before execution. This preprocessing step explains several common edge cases in model behavior.

## Subword tokenization mechanics

Token vocabularies are constructed using algorithms such as Byte Pair Encoding (BPE), which iteratively merges frequent adjacent byte sequences into single token entries. Common sequences map to single tokens, while rare words are split across multiple subwords.

Key tokenization patterns include:
- Common English words typically form single tokens, often including their leading whitespace (for example, `" the"` and `"the"` map to distinct token IDs).
- Rare terms, non-standard spellings, and long numeric sequences split into multiple tokens.
- Capitalization and punctuation alter token boundaries. `"Hello"`, `"hello"`, and `"HELLO"` may produce different token sequences.

A standard heuristic for English text is approximately four characters per token, or three tokens for every four words. This estimate varies across programming languages, non-Latin scripts, and dense numeric data. For exact token budgeting, calculate counts directly using the provider tokenizer.

Non-Latin alphabets and character sets underrepresented in training corpora require more tokens per word, often approaching one token per character. Code formats also show higher token density due to indentation and punctuation.

## Tokenization edge cases

Character-level tasks (such as counting specific letters in a word or reversing a string) often fail because the model observes token IDs rather than individual characters. The model must infer character composition indirectly from patterns observed during training.

Similarly, multi-digit arithmetic requires coordinating across token chunks. When precision is required, delegate string operations and arithmetic to deterministic tools (`len(s)`, Python evaluators) rather than relying on language model generation.

## The shared context window budget

The context window defines the maximum sequence length a model can process in a single request. This limit encompasses all prompt content: system instructions, conversation history, tool definitions, tool results, and the tokens generated in the response:

```python
window = 128_000           # maximum token capacity
prompt_tokens = count(messages) + count(tool_schemas)
room_for_reply = window - prompt_tokens
```

Applications must reserve sufficient headroom for the model response. If input tokens consume the context window up to the ceiling, the generation truncates immediately. Most providers also enforce an independent maximum output token limit (`max_tokens`).

Context window limits vary widely across model tiers. Design agent pipelines with configurable window parameters rather than hard-coded limits. Even within large context windows, placing relevant instructions near the beginning or end improves extraction accuracy.

## Quadratic token accumulation in loops

In multi-step agent loops, token usage grows quadratically. Because the model is stateless, every step resends the base prompt plus the accumulating history of tool calls and results.

Given a base prompt of `B` tokens and `S` tokens added per step, step 1 sends `B`, step 2 sends `B + S`, and step 3 sends `B + 2S`. Across `n` steps, the total prompt tokens processed is:

```python
def loop_cost(base_tokens, tokens_per_step, steps):
    return steps * base_tokens + tokens_per_step * steps * (steps - 1) // 2
```

Consider an agent with a 2,000-token base prompt (including tool schemas) that adds 400 tokens per step:

| Step | Prompt tokens per call | Cumulative tokens paid |
| --- | --- | --- |
| 1 | 2000 | 2000 |
| 2 | 2400 | 4400 |
| 4 | 3200 | 10400 |
| 8 | 4800 | 27200 |
| 16 | 8000 | 80000 |

Steps 9 through 16 generate 52,800 prompt tokens, nearly double the token volume of steps 1 through 8. Unbounded agent loops risk substantial compute consumption, making hard step limits and context pruning mandatory.

Prompt caching reduces the financial cost of repeated prompt prefixes by reusing KV cache state on provider hardware. However, caching does not reduce context window consumption: the prompt still consumes the same capacity against the model window limit.

## Context management strategies

When conversation history approaches capacity, three primary reduction strategies apply:

| Strategy | Computational cost | Information tradeoff |
| --- | --- | --- |
| Truncation / Trimming | Minimal (deterministic slicing) | Drops older messages entirely |
| Summarization | Requires intermediate model calls | Retains high-level context but loses fine details |
| Retrieval | Indexing and query overhead | Retrieves only fragments matching the query |

Production systems typically combine these approaches: pin the system message at index 0, retain recent dialogue turns verbatim, and summarize or retrieve older history as needed.

## Exercise specification

Implement six context budgeting and trimming functions:
1. `estimate_tokens`: approximate token counts using character heuristics.
2. `message_tokens`: calculate tokens for a message payload including role overhead.
3. `conversation_tokens`: calculate total tokens across a message list.
4. `headroom`: determine remaining token capacity given window limits and output budgets.
5. `loop_cost`: compute cumulative prompt token consumption across multi-step execution.
6. `trim_to_budget`: trim history to fit a token budget while preserving the system message and the newest user turn.

When trimming history, preserve contiguous message spans. If an older message cannot fit within the remaining budget, halt trimming at that boundary rather than skipping it to include smaller, disconnected messages.
