      because:
        examples: Examples are part of the stable prefix, so they sit above the thing that changes. Putting them after the document separates them from the instructions they illustrate.

        question: Recall is strongest at the start and the end of a long context, and generation continues from the end. The question is what you most need it to be looking at.
      hints:

        The structural techniques share a property. You can name the mechanism, and you can

        mechanism behind it is a measurement of one checkpoint, and it will stop being true

A prompt provides the prefix that conditions language model generation. Instructions, constraints, and context shift logit distributions across vocabulary tokens. Prompt engineering focuses on structuring this prefix to yield consistent, verifiable outputs.

## The five core prompt components

Production prompts typically decompose into five modular sections:

1. **Role and Domain Context**: Sets the vocabulary, persona, and stylistic expectations (for example, "You are triaging support tickets for a payments processor").
2. **Task Definition**: States the required operation explicitly (summarization, categorization, information extraction).
3. **Constraints and Rules**: Defines behavioral boundaries and negative constraints. Positive directives ("Answer using only the provided excerpts") generally constrain outputs more reliably than negative prohibitions ("Do not mention pricing").
4. **Output Schema Contract**: Defines formatting rules, schema field names, and allowed values.
5. **Input Data**: Encapsulates external user input inside explicit XML-style or markdown delimiters:

```python
user = f"<ticket>\n{ticket_text}\n</ticket>\n\nClassify the ticket above."
```

Delimiters separate application instructions from user data, reducing the risk of prompt injection and parsing ambiguities.

## System prompts versus user prompts

The distinction between system and user messages concerns message lifetime and instruction precedence:

```python
messages = [
    {"role": "system", "content": SYSTEM},        # persistent across turns
    {"role": "user", "content": "Ticket: ..."},   # single turn input
]
```

Placing standing rules in the system prompt provides two operational benefits:
1. **Context Position Stability**: The system message remains pinned at index 0 throughout the dialogue, avoiding the recall degradation that affects older user turns in long context windows.
2. **Prompt Caching Efficiency**: Keeping the system message byte-identical across requests enables provider-level KV caching. Avoid interpolating dynamic timestamps or request IDs into the system prompt prefix, as this invalidates the cached prefix. See [tokens and context](lesson:ai-llm-fundamentals.tokens-and-context).

## Ambiguity and default model completions

Consider a minimal instruction:

```python
system = "Summarise this email."
```

Without additional constraints, the model may return a conversational reply:

```
Thanks for getting in touch about your recent order! It sounds like the checkout page
has not been working for you since Tuesday, and I can see you have already tried a
different browser and clearing your cache. I completely understand how frustrating
that must be, and I want to help get this sorted for you as quickly as possible.
```

The output mimics a customer service response rather than an internal triage summary because unconstrained prompts default to common training text patterns.

Adding explicit constraints shapes the output:

```python
system = (
    "You are triaging inbound support email for a payments company.\n"
    "Write a summary for the agent who picks the ticket up next.\n"
    "Two sentences. First what the customer wants, then what they have already tried.\n"
    "Write about the customer in the third person. Do not address them.\n"
    "If the email does not contain a request, write exactly: NO REQUEST"
)
```

Specifying the target audience, sentence count, required fields, and an explicit fallback string (`NO REQUEST`) resolves ambiguity and enables automated assertion testing.

## Rule complexity and prompt bloat

Adding dozens of ad-hoc rules degrades instruction compliance. Logit shifts interact across the token sequence, and conflicting rules yield inconsistent continuations.

To maintain prompt reliability:
- Remove obsolete or untested guidelines.
- Consolidate overlapping instructions.
- Move deterministic criteria into code validators (for example, verifying field enums via JSON schema validation rather than natural language instructions).
- Split multi-step workflows with distinct output contracts into separate API calls.

## Instruction placement in long contexts

Attention mechanisms recall information at the beginning and end of long contexts more reliably than information located in the middle.

When processing large input documents, position operational instructions after the document payload:

```python
messages = [
    {"role": "system", "content": SYSTEM},
    {"role": "user", "content": f"<policy>\n{policy_text}\n</policy>"},
    {"role": "user", "content": "Which clause covers refunds after 30 days? Quote it."},
]
```

Placing the query at the end ensures the instruction remains immediately adjacent to the generation point.

## Structural techniques versus prompt tricks

Reliable prompt techniques rely on verifiable mechanisms: clear task definitions, explicit schema contracts, structured delimiters, and few-shot examples.

In contrast, non-structural phrases ("take a deep breath", "my career depends on this") are model-specific artifacts that do not generalize across model updates. Verify prompt modifications using systematic evaluation suites, as covered in [measuring a prompt](lesson:ai-prompt-engineering.measuring-a-prompt).
