Agent workflows require machine-readable data structures to execute conditional logic, call external tools, and update database state. Generating predictable structured output requires combining prompt instructions, decoding constraints, schema validation, and targeted error recovery.

## Three levels of schema enforcement

### 1. Prompt instructions

Specify the desired JSON schema in the prompt text:

```python
SYSTEM = (
    "Extract the order details. Reply with JSON only, no prose and no code fence.\n"
    'Shape: {"customer_name": string, "order_id": string or null, '
    '"quantity": integer, "status": "open" | "shipped" | "closed"}'
)
```

This approach works across all model providers and incurs zero schema pre-processing overhead. However, it provides no structural guarantees: the model may emit conversational preambles, markdown code fences, or invalid syntax.

### 2. Constrained decoding

Constrained decoding forces the decoding sampler to mask illegal tokens at each generation step. If the grammar expects a JSON key or closing bracket, tokens violating the syntax rule are assigned zero probability.

Provider implementations vary:
- **JSON mode**: Guarantees syntactically valid JSON, but does not enforce specific schema fields.
- **Structured outputs**: Enforces strict JSON Schema compliance at the token mask level.
- **Tool schemas**: Constrains output to valid function argument payloads.

Constrained decoding ensures syntactic validity, but cannot verify semantic truth. If a required field is missing from the source text, the token mask forces the model to generate a syntactically valid placeholder value rather than permitting an explanatory refusal. Design schemas with nullable fields or explicit fallback enums to capture missing information.

### 3. Application validation and retry loops

Regardless of provider guarantees, downstream applications must validate parsed objects against domain schemas:

```python
data = extract_json(reply)     # deserialize JSON payload from string
validate(data, ORDER_SCHEMA)   # verify field presence, types, and allowed values
```

| Enforcement layer | Guarantees | Operational overhead |
| --- | --- | --- |
| Prompt instructions | None (probabilistic guidance) | Resilient parsing code required |
| Constrained decoding | Syntax and schema structure | Schema compilation, provider-specific API |
| Application validation | Explicit domain invariants | Additional round trips when retrying |

## Common parsing failures

Common formatting anomalies encountered when parsing unstructured model output include:
- **Conversational wrapping**: Introductory text ("Here is the requested JSON:") or trailing remarks.
- **Markdown code fences**: Output enclosed in triple backtick blocks.
- **Syntax errors**: Trailing commas, single-quoted strings, or unquoted keys.
- **Type mismatches**: Numeric values returned as strings (`"quantity": "2"` instead of `"quantity": 2`).
- **Length truncation**: Responses exceeding output limits truncate abruptly. Inspect `finish_reason == "length"` before parsing, as introduced in [reading a completion](lesson:ai-foundations.reading-a-completion).

## Validating domain invariants

Schema validation converts runtime anomalies into explicit exceptions at the boundary of your system.

Key validation checks include:
- Verifying required keys are present.
- Checking types strictly (in Python, `isinstance(True, int)` evaluates to `True`, requiring explicit checks to distinguish booleans from integers).
- Verifying enumerated field values match allowed domain sets.

## The feedback retry pattern

When validation fails, append the failed output and the validation error message to the conversation history, then request a correction:

```python
messages.append({"role": "assistant", "content": raw})
messages.append({
    "role": "user",
    "content": f"That reply was not usable: {error}. Return only corrected JSON.",
})
```

Providing both the invalid response and the specific error allows the model to target the failing field directly.

Set an upper bound on total attempts (typically 2 to 3). If a model fails validation across multiple attempts with the error in context, the failure usually stems from schema ambiguity or ungrounded source data rather than sampling noise.
