Modifying a system prompt to fix a single edge case often introduces unintended regressions elsewhere in the input space. An automated evaluation suite measures prompt changes against a consistent benchmark, providing immediate feedback on performance shifts before deployment.

## The regression problem in prompt editing

Prompts serve as a shared prefix for every input. Adding an ad-hoc instruction to fix a specific bug shifts output probabilities across all inputs:

```python
SYSTEM_V2 = SYSTEM_V1 + "\nA chargeback is always an escalation."
```

While this modification correctly routes chargeback inquiries to `escalation`, the increased salience of the token `escalation` may cause urgent billing inquiries (such as duplicate charges) to flip incorrectly from `billing` to `escalation`.

Verifying a prompt fix only on the input that motivated it creates a false sense of progress. Evaluating candidate prompts against a persistent test set exposes regressions immediately.

## Constructing a minimal evaluation suite

An evaluation suite defines a collection of test cases pairing inputs with expected assertion graders:

```python
CASES = [
    Case("double charge", "I was charged twice this month.", [exact_match("billing")]),
    Case("crash", "The app crashes on startup.", [exact_match("bug")]),
    Case("chargeback", "I filed a chargeback with my bank.", [exact_match("escalation")]),
    Case("thanks", "Thanks, that worked!", [exact_match("other")]),
]
```

A small suite of ten high-quality test cases based on real historical issues provides significant regression protection. Ground truth annotations should come from verified domain data rather than model-generated labels.

## Deterministic output graders

Deterministic programmatic checks execute quickly and yield consistent results:

| Grader | Assertion logic | Application domain |
| --- | --- | --- |
| `exact_match(expected)` | Verifies output equals expected string | Classification, routing, extracted codes |
| `matches_schema(spec)` | Verifies JSON parsing and field types | Structured payloads |
| `contains_all(terms)` | Verifies every required substring is present | Key information inclusion |
| `rejects(term)` | Verifies forbidden substring is absent | Content filtering, competitor mentions |

Graders return `None` when an assertion passes, and a diagnostic string explaining the mismatch when it fails:

```python
Grader = Callable[[str], str | None]


def exact_match(expected: str) -> Grader:
    def grade(output: str) -> str | None:
        actual = output.strip()
        return None if actual == expected else f"expected {expected!r}, got {actual!r}"

    return grade
```

Programmatic graders provide instant, deterministic feedback. Semantic quality evaluations (such as assessing summary tone or faithfulness) require model-based evaluators, which are covered in subsequent modules.

## Comparing baseline and candidate prompts

### Pass rate as a comparative metric

Evaluate baseline and candidate prompts on the identical test suite:

```python
baseline = run_eval(client, prompt_v1, CASES)     # 0.75, chargeback fails
candidate = run_eval(client, prompt_v2, CASES)    # 0.75, chargeback passes now
```

Both runs report a 0.75 pass rate, yet the underlying behavior shifted. Summary statistics alone obscure which individual test cases improved or regressed.

### Tracking explicit regressions

The evaluation comparison reports itemized diffs:

```python
result = compare(baseline, candidate)
result.regressed          # ["double charge"]
result.improved           # ["chargeback"]
result.pass_rate_delta    # 0.0
result.better             # False
```

A candidate prompt is marked `better` only if it improves overall accuracy without introducing regressions on previously passing cases (`regressed` is empty). This rule prevents silent degradation on critical test paths.

## Scope and limitations of static suites

Evaluation suites reflect observed failure modes. To maintain suite coverage:
1. Capture production failures as new test cases before applying prompt fixes.
2. Include negative test cases (such as out-of-scope inquiries or polite refusals) to ensure the prompt does not over-generalize to produce eager, ungrounded answers.

## Exercise specification

Implement an evaluation harness:
1. `exact_match`, `contains_all`, `rejects`: create deterministic grading functions.
2. `Case`: dataclass holding case name, input text, and a list of graders.
3. `run_eval`: execute a prompt against all cases using `MockClient`, recording pass status and aggregate pass rates.
4. `compare`: evaluate two test run summaries, calculating `pass_rate_delta`, identifying `regressed` and `improved` cases, and determining whether the candidate is strictly `better` (higher pass rate with zero regressions).
