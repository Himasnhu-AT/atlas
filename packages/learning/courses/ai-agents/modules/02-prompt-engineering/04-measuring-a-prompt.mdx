Everything in the first three lessons was a claim about what makes a prompt better. This lesson
is the part that decides whether any of those claims is true of your prompt, on your task, with
your model. Without it you are not engineering a prompt, you are decorating one.

The workflow that produces the problem is the one everybody has: someone reports a bad output,
you add a line to the system message, you paste the bad input back in, the output is now good,
you ship. Every step is reasonable and the result is unreliable, because you verified the change
on exactly the case that motivated it.

## The specific way it goes wrong

A prompt is one artefact serving every input. A line added to fix one input applies to all of
them.

Say tickets that mention a chargeback are being labelled `billing` when your team wants
`escalation`. You add a line:

```python
SYSTEM_V2 = SYSTEM_V1 + "\nA chargeback is always an escalation."
```

The reported case is now correct. The mechanism that fixed it is the one from
[anatomy of a prompt](lesson:stage-2.anatomy-of-a-prompt):
the token `escalation` is now in the prefix of every call, and a label that appears in the
instructions is more probable than one that does not. That mechanism does not know which ticket
you were thinking of. The ticket about being charged twice reads as urgent and mentions money,
so `escalation` is now the more available label there too, and it flips. So does the one about a
delayed bank transfer, for the same reason and with no more warning.

You fixed one case and broke two, and every part of that is ordinary.

The arithmetic is what makes this persistent. One case fixed is visible, immediate, and yours.
Two cases broken are invisible, delayed, and get reported as a new bug by someone else in a
fortnight. The change looks like a pure win at the moment you make it, and the only way it looks
otherwise is if you check the other cases at that moment.

That is the entire argument for an eval. Not rigour, not process. You need to see the other
cases at the moment you make the change.

## The smallest useful eval

A case is an input and something you expect to be true of the output.

```python
CASES = [
    Case("double charge", "I was charged twice this month.", [exact_match("billing")]),
    Case("crash", "The app crashes on startup.", [exact_match("bug")]),
    Case("chargeback", "I filed a chargeback with my bank.", [exact_match("escalation")]),
    Case("thanks", "Thanks, that worked!", [exact_match("other")]),
]
```

Four is already useful. Ten is enough to catch the failure above. Saying so plainly matters
because people postpone evals until they can build the proper version, and the proper version
never gets built while the guessing continues.

Ten honest cases beat a hundred generated ones for a precise reason. A case is worth having only
if the expectation attached to it is one you believe, which means somebody who knows the task
decided what the right answer was. Ask a model to invent a hundred cases and you get inputs that
resemble your task carrying expectations from the same kind of system you are testing, agreeing
with itself. Generated inputs are useful raw material. The labels have to come from you.

The best source of cases is your bug tracker. Every case in a mature suite should be traceable
to something that actually went wrong once.

## What you can grade without a model

The graders worth writing first are the ones with no judgement in them.

| Grader | Checks | Good for |
| --- | --- | --- |
| `exact_match(expected)` | Output equals the expected string | Classification, routing, extracted values |
| `matches_schema(spec)` | Parses as JSON with the right field types | Anything structured |
| `contains_all(terms)` | Every term appears | An answer that must mention the order id |
| `rejects(term)` | A term does not appear | A refusal that must not name a competitor |

Each of those is a few lines. Written out, the first one is all of this:

```python
Grader = Callable[[str], str | None]


def exact_match(expected: str) -> Grader:
    def grade(output: str) -> str | None:
        actual = output.strip()
        return None if actual == expected else f"expected {expected!r}, got {actual!r}"

    return grade
```

Two things about that shape, because the rest of the graders are built the same way. Calling
`exact_match("billing")` checks nothing; it builds a grader that has `"billing"` baked into it
and hands it back, which is what lets a case carry a list of graders that each already know
what they are looking for. And a grader answers with `None` when the check holds and a short
reason when it does not, rather than with `True` and `False`. That is the difference between a
failing run that says `chargeback: expected 'escalation', got 'billing'` and one that says
`chargeback: False`.

They run in microseconds and give the same answer every time. Reach for them before anything
cleverer, and shape the task so they apply: asking for a label rather than a paragraph makes
the output gradeable as well as parseable, which is an argument for structured output beyond
the parsing.

What they cannot do is judge quality. Whether a summary is faithful, whether a reply is polite
enough, whether an explanation is correct, none of that reduces to a substring. The usual move
is a second model call with a rubric, which is a real technique with real problems: the judge
needs its own evaluation against human labels before you can trust it, and judges have known
biases towards longer and more confident answers. Later modules build one. Exhaust the
deterministic checks first, because much of what people reach for a judge to grade is checkable.

## Comparing two versions

### Pass rate is a comparison, not a score

Run the suite, count the cases where every grader held, divide. Run it again with the other
prompt, holding everything else fixed.

```python
baseline = run_eval(client, prompt_v1, CASES)     # 0.75, chargeback fails
candidate = run_eval(client, prompt_v2, CASES)    # 0.75, chargeback passes now
```

Both runs score 0.75, and the change you made was neither a success nor a no-op. It moved which
cases pass. The pass rate is the one number that cannot tell you that, which is the first thing
worth learning about it.

The number on its own means little. A pass rate of 0.8 on ten cases you chose is not 80% correct
on your traffic, and treating it as a score to maximise leads to adding easy cases, which raises
the number and tells you less.

What the number is for is the difference between two runs of the same suite. That comparison is
meaningful in a way the absolute value is not, because everything except the prompt was held
constant. Chasing the score is what people do with an eval they built to look responsible.
Comparing two versions is what people do with an eval they built because they had to decide
something.

### Regression is the alert worth having

Which is why `compare` reports names and not just an average. On the two runs above:

```python
result = compare(baseline, candidate)
result.regressed          # ["double charge"]
result.improved           # ["chargeback"]
result.pass_rate_delta    # 0.0
result.better             # False
```

There is the fix and there is its cost, on one screen, before the change ships. `double charge`
is the ticket about being billed twice, which used to label `billing` and now labels
`escalation`, because that is what adding the word did. Nobody would have found that by pasting
the chargeback ticket back in, and nobody was going to go looking for it.

A case that used to pass and now does not is the most actionable signal in the whole exercise.
It is specific, it names an input you can paste into a client, and it is exactly the class of
damage the workflow at the top of this lesson does invisibly. Note also what you now know that a
pass rate alone would have hidden: the delta is zero, so the summary statistic says nothing
happened, and two named cases say otherwise.

The bank transfer ticket, meanwhile, also broke and is not in this suite, so nothing here
reports it. That is not a flaw in the tooling. It is the limit of the method, and it is the next
section.

It also justifies a rule that feels harsh and is not. A candidate that regressed anything is not
better, even when its pass rate went up. Trading a case away is sometimes right, but it should
be a decision somebody makes with the case in front of them rather than an outcome absorbed into
an average. Building that refusal into the comparison is what forces the conversation.

## What an eval does not tell you

An eval measures what you thought to check, and that is a real limit rather than a caveat.

Your cases are the failures you have already seen, so the suite is blind to the failure modes
nobody has hit yet. The bank transfer ticket above is the shape of it. A green run means you
have not reintroduced anything on the list. It does not mean the prompt is good, and the
distance between those two statements is exactly the part of your traffic you have never
written a case for.

Two habits keep it honest, and they attack different halves of the problem.

Add a case when something goes wrong in production, before fixing it. Writing the case first
means you watch it fail, which is the only proof that the case actually tests the thing, and it
means the suite grows along the axis your users are finding rather than the axis you imagined.
A suite built this way converges on your real failure distribution. One built in an afternoon
converges on what you could think of in an afternoon.

Keep a few cases whose correct outcome is a refusal or an out of scope label. Without them,
every grader in the suite rewards producing an answer, and a prompt that answers everything
confidently scores higher than one that knows when to stop. This is the same trap as a rubric
that rewards escalating, and it is worth checking for deliberately, because the suite will not
tell you it has it.

None of this is expensive. The harness in this exercise is the same shape as the persona harness
in module 9, which grades a whole conversation instead of one reply.

## Your exercise

Build the harness: a `Case`, four grader factories, `run_eval`, and `compare`.

A grader takes the model's output and returns nothing when the check holds, or a short reason
when it does not, so a failing case reports why rather than reporting false. `run_eval` walks the
cases in order against a scripted client and collects per case results and a pass rate.
`compare` takes two results over the same cases and reports which regressed, which improved, and
whether the candidate is better.

The tests check that a case fails when any one of its graders fails, that an empty suite scores
zero rather than one, that comparing results over different case sets raises rather than
guessing, and that a candidate with a higher pass rate and one regression is still not better.
The part people get wrong is that last one.
