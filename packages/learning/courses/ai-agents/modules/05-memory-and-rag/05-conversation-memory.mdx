"Memory" covers two different problems and the word does them both a disservice.

Retrieval is memory of documents. The corpus exists before the conversation starts, you control
when it changes, and you chunk and embed it ahead of time. Conversation memory is memory of the
transcript, which does not exist ahead of time and grows by at least two messages every turn.

The mechanism is worth saying plainly, because everything else follows from it. A model call is
stateless, and what looks like memory is you resending the conversation every turn. So a long
conversation is not a model that remembers more, it is a request that gets bigger every turn
until it stops fitting and something has to go.

## Four strategies, and what each loses

| Strategy | Keeps | Loses | Costs |
| --- | --- | --- | --- |
| Sliding window | The most recent turns, verbatim | Everything older, completely and silently | Nothing |
| Running summary | The gist of the whole conversation | Detail, unpredictably | A model call, and latency, when it fires |
| Extracted facts | Specific durable facts, across sessions | Everything not judged a fact | A model call, and a judgement you may disagree with |
| Retrieval over past turns | Whatever matches this question | Anything the question does not resemble | An index that grows with the conversation |

A sliding window is the honest baseline and what most systems should start with. Its failure mode
is that it is total: the turn where the user said "I'm in Berlin" falls off the back and nothing
marks its absence, so the agent asks for a city it was already told.

A running summary trades detail for room, and the trade is not one you can predict. The model
decides what a pleasantry is, and the detail the next question needed is exactly the one it
decided to drop. That is not a flaw to fix with a better prompt, it is what compression is.

Extracted facts are the only one of the four that survives the session ending, which is what
makes them worth a separate mechanism rather than a bigger summary. Retrieval over past turns is
this module's machinery pointed at the transcript, and its weakness is specific: it retrieves
what resembles the current question, so the turn that matters for a reason the question does not
mention stays lost.

Real systems combine them. The exercise builds a window plus a summary plus facts, which is the
common shape.

## What must never be dropped

Two things, and the second one is where naive implementations break.

The system message. It is the agent's instructions, not conversation history, and trimming it to
save tokens does not shorten the conversation, it changes what the agent is. So it is kept
whatever the budget, and its cost comes off the budget rather than competing with recent turns
for it.

Not just the first message, though: the whole leading run of them. That looks like a detail until
you see what inserts a second one. A summary replacing older turns goes in as a system message
immediately after the original, which puts it inside the protected run. Insert it anywhere else
and the next trim throws away the summary while keeping the turns it was paid for to replace.

```python
[
    {"role": "system", "content": "You are a booking assistant."},
    {"role": "system", "content": "Summary of earlier conversation:\n..."},
    # everything below here is trimmable
]
```

Providers that mirror the OpenAI chat shape accept more than one system message. Where a provider
does not, the same content goes into the first user message instead and nothing else about the
design changes.

## The corruption a trim causes

A message list is not a flat sequence of independent items:

```python
{"role": "assistant", "content": None,
 "tool_calls": [{"id": "call_1", "type": "function",
                 "function": {"name": "search_restaurants",
                              "arguments": '{"city": "Lisbon", "party": 4}'}}]},
{"role": "tool", "tool_call_id": "call_1",
 "content": "Three with space tonight: Ramiro, Belcanto, Prado."},
```

Those two messages are one exchange. The assistant asks for a tool by id and the tool message
answers that id. Cut between them and you have sent a request in which the model asked for
something and nothing answered, or in which a result arrives for a call that was never made.
Providers reject that outright, so the symptom is not a worse answer, it is a hard API error on a
conversation that had been working for twenty turns.

The fix is to trim in units. Group each assistant message that has `tool_calls` with the tool
messages that follow it, treat that group as indivisible, and make the budget decision about
groups. One tool exchange is one turn of the conversation however many messages it took.

The second rule is less obvious and matters as much. When a group does not fit, stop, do not skip
it and carry on to older ones:

```
system    kept, always
user      "old and short"          <- fits in what is left
assistant 4000 characters          <- does not fit
user      "recent"                 <- kept
```

Skipping the oversized message to squeeze in the older short one leaves a hole in the middle of
the conversation, and nothing downstream can see that the hole is there. The model reads a user
message, then a reply to something that is not in front of it, and answers with complete
confidence. A conversation that stops cleanly at a boundary is understandable; one with a piece
missing from the middle is actively misleading.

## Summarising is a model call

It is easy to treat the summary as free because it is not the user's turn. It costs a call and
its latency on the turn that triggers it, it costs the tokens of everything being summarised,
and it is lossy in the way described above.

So the common path has to be free. Most turns fit, and a conversation that fits returns unchanged
without touching the model:

```python
if sum(estimate_tokens(message) for message in messages) <= max_tokens:
    return ManagedContext(messages=messages, dropped=[], facts=[])
```

The same applies to a conversation barely long enough to have anything old in it: summarising
four messages costs a call, adds latency, and loses detail to save nothing.

When a trim does happen, something has to say what went, which is why the result carries
`dropped`. An agent that has silently forgotten something is almost impossible to debug, because
the evidence of what it forgot is exactly what was thrown away.

## Memory that outlives the session

Facts are the piece that survives the conversation ending, and the hard part is not the
extraction. Extraction is a model call with a clear instruction: read the transcript, return the
durable facts as a JSON array of short strings.

The hard part is deciding what deserves to be in that array. "Party of four" is worth keeping for
tonight's booking and is actively wrong next month. "Prefers Prado" is a preference or a one off,
and no amount of prompting makes that distinction reliably from a single conversation.

So a remembered fact that is wrong is worse than one never remembered, because it gets applied
confidently to every future session, and durable memory needs a way to be corrected and a reason
to expire. Extraction must also never break the turn: a model replying to a request for JSON with
an apology should produce an empty fact list and a log line, not an exception.
