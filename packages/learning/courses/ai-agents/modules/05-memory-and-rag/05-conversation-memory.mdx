Memory mechanisms in agent architectures handle two distinct data sources: static document retrieval and dynamic
conversation history.

Document retrieval operates over an external, pre-indexed corpus. Conversation memory manages the evolving transcript
of the active session. Because model API endpoints are stateless, conversational continuity is maintained by resending
accumulated messages on each turn. As dialogues extend, message histories eventually exceed token limits, requiring
active context management.

## Four conversation memory strategies

| Strategy | Retained context | Discarded context | Operational overhead |
| --- | --- | --- | --- |
| Sliding window | Recent turns verbatim | Older conversation history | None |
| Running summary | Compressed summary of dialogue | Specific nuances and details | Periodic model summarization calls |
| Extracted facts | Persistent key facts | Conversational filler | Extraction model calls |
| Semantic search over history | Matches for active query | Non-matching dialogue context | Incremental session indexing |

A sliding window provides a simple baseline. However, facts mentioned early in a long session eventually fall
outside the window, causing the agent to repeat questions.

A running summary compresses historical turns into a narrative block, preserving general context while sacrificing
granular details.

Extracted facts identify durable attributes (such as user preferences or account settings) that persist across
sessions.

Production systems frequently combine these strategies by pairing a sliding window for recent turns with a
background summary or extracted fact store for older context.

## Protected prompt regions

Certain message blocks must remain protected during context trimming:

The initial system prompt contains core agent behavioral instructions and must never be trimmed. Deduct its token
cost from the total budget before calculating available space for conversation turns.

System messages inserted immediately following the primary instructions (such as running conversation summaries)
must also remain protected:

```python
[
    {"role": "system", "content": "You are a booking assistant."},
    {"role": "system", "content": "Summary of earlier conversation:\n..."},
    # trimmable history begins below
]
```

Placing summaries in the leading system block ensures subsequent trim operations do not discard the summary while
retaining unsummarized turns.

## Preserving turn integrity during context trimming

Message transcripts contain structural dependencies that cannot be arbitrarily severed:

```python
{"role": "assistant", "content": None,
 "tool_calls": [{"id": "call_1", "type": "function",
                 "function": {"name": "search_restaurants",
                              "arguments": '{"city": "Lisbon", "party": 4}'}}]},
{"role": "tool", "tool_call_id": "call_1",
 "content": "Three with space tonight: Ramiro, Belcanto, Prado."},
```

An assistant message with `tool_calls` and its corresponding `tool` result messages form an indivisible unit.
Trimming between these messages leaves dangling tool requests or orphaned tool responses, which API providers
reject with HTTP 400 validation errors.

Group assistant tool requests with their corresponding tool results into single atomic units before evaluating
token limits.

When trimming context, walk backward from the most recent turn. If an older turn exceeds remaining token space,
stop trimming immediately rather than skipping it to include even older messages. Skipping messages creates gaps
in conversation context that produce contradictory responses.

## Cost and latency of dynamic summarization

Generating summaries consumes model tokens and introduces latency during the turn that triggers summarization.

Optimize the common execution path by bypassing summarization when the raw message list fits within budget:

```python
if sum(estimate_tokens(message) for message in messages) <= max_tokens:
    return ManagedContext(messages=messages, dropped=[], facts=[])
```

When messages are trimmed, the returned `ManagedContext` should populate the `dropped` list to maintain observability
over removed context.

## Extracting durable facts across sessions

Extracting durable facts involves prompting a model to identify persistent details from dialogue and return them
as a structured JSON array.

The extraction prompt should target stable user preferences rather than transient state. Extraction failures
should be handled gracefully by returning an empty fact list and logging the issue without failing the user request.
