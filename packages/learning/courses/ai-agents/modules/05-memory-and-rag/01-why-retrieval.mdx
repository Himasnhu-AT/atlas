A model knows only what was included in its training corpus. It has no access to private API documentation,
internal support tickets, recent architecture decisions, or runtime system configurations. When queried about
proprietary information, models generate plausible completions without signaling whether the topic was present
in their training data.

Bridging this knowledge gap requires supplying external information into the model's context.

## Three ways to supply private data to a model

Three primary strategies exist for incorporating private data:

| Approach | Mechanism | Cost structure | Failure mode |
| --- | --- | --- | --- |
| Context stuffing | Paste entire documents into every prompt | High token cost on every turn | Fails when corpus exceeds context limits |
| Retrieval (RAG) | Search relevant excerpts and inject only those | Vector index build and maintenance | Irrelevant retrievals yield plausible wrong answers |
| Fine-tuning | Retrain model weights on domain dataset | Upfront training compute and data curation | Memorizes style well, updates facts poorly |

Context stuffing is viable when documentation is concise and static, such as a short company policy document.
When documentation grows or questions target specific subtopics, retrieval becomes necessary to manage prompt size.

Fine-tuning adapts model tone, schema adherence, and classification behavior. However, fine-tuning is ineffective
for factual knowledge injection. Updating individual facts requires repeating training runs, and model outputs
lack verifiable source citations.

## The trade-offs of large context windows

Expanding context windows allow passing large document collections directly into prompts. However, this approach
introduces three operational constraints:

1. Token costs accumulate per request. A hundred pages of context incurs billing overhead on every turn,
even when an answer requires only a single sentence. Prompt caching mitigates recurring costs for static prefixes
but does not eliminate per-token charges.

2. Latency increases with prompt size. Time-to-first-token scales with input context volume, slowing interactive chat
experiences.

3. Retrieval degradation across long spans ("needle in a haystack"). Models attend unevenly across large contexts,
recalling information placed near prompt beginnings and endings more consistently than content located in the middle.

## What retrieval provides

Retrieval-augmented generation provides two core architectural advantages:

1. Bounded prompt budgets: The application controls the number and size of context passages injected into the prompt,
keeping latency and token costs predictable as the underlying corpus scales.

2. Verifiable citations: Because the retrieval system selects specific text passages, the application tracks exactly
which documents were provided to the model. Responses can link to source excerpts, enabling automated ground-truth
verification and human auditing.

Retrieval restricts the model's reference material, though it does not eliminate hallucinations. Verification
pipelines remain necessary to confirm that generated claims match retrieved context.

## The silent retrieval failure mode

A critical failure in retrieval systems occurs when search returns plausible but irrelevant passages.

If a retriever returns three high-scoring chunks that do not answer the user's specific question, the model
often synthesizes an articulate, confident answer citing the provided text. The output appears valid and contains
citations, yet the underlying claim is incorrect.

Mitigating this failure requires:
- Effective document chunking to preserve complete semantic units.
- Similarity score thresholds to reject low-confidence retrievals.
- Explicit prompt instructions directing models to decline answering when retrieved context lacks sufficient evidence.
- Verifying cited identifiers against retrieved documents.

The subsequent lessons address each stage of this retrieval pipeline.
