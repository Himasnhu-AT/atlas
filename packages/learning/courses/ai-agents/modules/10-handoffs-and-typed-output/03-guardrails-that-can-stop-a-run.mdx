A guardrail is an evaluation function that assesses inputs or outputs and decides whether execution
may continue. In modern agent runtimes, a tripped guardrail halts execution by raising an exception
rather than relying on passive status flags.

```python
# Reference example using the openai-agents package
from agents import Agent, GuardrailFunctionOutput, Runner, input_guardrail

@input_guardrail
async def not_a_homework_request(ctx, agent, user_input: str) -> GuardrailFunctionOutput:
    verdict = await Runner.run(homework_classifier, user_input)
    return GuardrailFunctionOutput(
        output_info=verdict.final_output,
        tripwire_triggered=verdict.final_output.is_homework,
    )

support = Agent(name="Support", instructions="...", input_guardrails=[not_a_homework_request])
```

Using exceptions for tripwires ensures that callers cannot accidentally ignore policy violations.
Attaching structured diagnostic metadata to the exception allows upstream callers to generate appropriate
user-facing rejection messages or operational logs.

## Input versus output guardrails

Guardrails serve distinct operational purposes depending on where they execute in the lifecycle:

- **Input guardrails**: Evaluate the initial user prompt before any model invocation. An input guardrail
  can stop a run before consuming tokens, protecting budgets from out-of-scope requests or injection attempts.
- **Output guardrails**: Evaluate text produced by the agent. By definition, tokens have already been consumed
  and downstream tools may have executed. Output guardrails protect end users from unsafe content or malformed
  responses, but they cannot reduce compute spend.

Production frameworks balance latency and cost when executing input guardrails. Some run input guardrails
concurrently with the initial model request and cancel the stream if a tripwire fires. Evaluating guardrails
strictly prior to model invocation introduces minor latency but guarantees zero token spend on rejected requests.

## Exception handling and short-circuit evaluation

Guardrails should distinguish between intentional policy trips and internal software defects:

- **Do not catch unexpected exceptions**: If a guardrail raises a runtime error (such as a malformed regular expression or network failure), let the error propagate. Catching all exceptions and treating them as trips masks bugs under the guise of security.
- **Short-circuit evaluation**: Evaluate guardrails sequentially in order of definition, halting immediately upon the first triggered tripwire. This avoids unnecessary computation and ensures exception messages report the exact rule that caused the rejection.

## Boundaries of guardrail responsibilities

Guardrails are not a replacement for domain-level access control or system design:

- **Authorization belongs in tools**: Critical business constraints (such as maximum transaction limits) must be enforced directly inside tool functions, not in text-based guardrail checks.
- **Tool scoping is primary**: The most reliable safeguard is omitting sensitive tools from agents that do not require them. Filtering prompts to prevent misuse of unnecessary tools is fragile compared to structural permission boundaries.
- **Model-based guardrail costs**: When using an LLM classifier as a guardrail, ensure the classifier uses a lightweight, low-cost model relative to the primary agent to keep latency and expense bounded.
