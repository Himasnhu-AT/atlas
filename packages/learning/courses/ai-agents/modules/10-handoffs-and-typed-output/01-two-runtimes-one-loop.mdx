While graph-based frameworks represent agent workflows as explicit state machines, another
family of runtimes retains the core execution loop and wraps it with targeted abstractions.
Two prominent libraries in this space are the OpenAI Agents SDK and Pydantic AI.

The OpenAI Agents SDK (the successor to Swarm) organizes execution around four primary concepts:
agents, handoffs, guardrails, and sessions. An agent and a handoff follow this structure:

```python
# Reference example using the openai-agents package
from agents import Agent, Runner, function_tool

@function_tool
def order_status(order_id: str) -> str:
    """Look up the status of an order."""
    return lookup(order_id)

billing = Agent(
    name="Billing",
    instructions="Answer billing questions. Refunds are not yours to give.",
    tools=[order_status],
)

triage = Agent(
    name="Triage",
    instructions="Work out who should handle this and hand off.",
    handoffs=[billing],
)

result = await Runner.run(triage, "I was charged twice for order A-1174")
result.final_output
```

Pydantic AI centers its design on the boundary where untyped model responses convert into validated,
strongly-typed Python data structures:

```python
# Reference example using the pydantic-ai package
from dataclasses import dataclass
from pydantic import BaseModel
from pydantic_ai import Agent, RunContext

class Ticket(BaseModel):
    title: str
    severity: int
    tags: list[str] = []

@dataclass
class Deps:
    db: Database

# MODEL specifies the provider string, e.g., "openai:..." or "anthropic:..."
agent = Agent(MODEL, deps_type=Deps, output_type=Ticket)

@agent.tool
def customer_plan(ctx: RunContext[Deps], customer_id: str) -> str:
    """Which plan a customer is on."""
    return ctx.deps.db.plan_for(customer_id)

result = agent.run_sync("Printer on fire, customer 7", deps=Deps(db=db))
result.output.severity  # integer guaranteed by schema validation
```

Both libraries execute on top of the standard tool loop: submit message history, inspect model response,
dispatch requested tool calls, append tool results, and repeat until final completion. The handoff in the
first pattern is dispatched as a tool call. The schema in the second is provided as a tool definition with
validation handling.

## Optimization goals of each runtime

The OpenAI Agents SDK emphasizes clear orchestration. Agents are discrete entities that transfer control
explicitly, making the execution trace read like a sequence of handoffs between specialists.

Pydantic AI focuses on type boundaries and dependency injection. External dependencies pass into tools
via run context objects rather than global imports. Structured outputs validate against Pydantic models,
and validation failures feed error feedback back into the model for automated correction.

Choose orchestration-focused libraries when managing complex delegation hierarchies. Choose type-focused
libraries when reliable, structured data extraction is the primary requirement.

## Managing dependencies and pre-1.0 stability

Rapidly evolving agent frameworks often operate under pre-1.0 versioning. Under semantic versioning,
minor releases below 1.0 may introduce breaking API changes. Signatures, decorator requirements, and return types
frequently shift across versions.

To protect production systems:
- Pin exact dependency versions in lock files.
- Review changelogs prior to upgrading packages.
- Isolate framework calls behind internal adapter modules, confining breaking changes to single integration points.
- Schedule recurring maintenance cycles to prevent technical debt accumulation.

## Vendor coupling and migration costs

Platform changes present greater operational risk than package updates. When hosted APIs deprecate features
or alter server-side session management, state stored externally must be migrated.

Consider data portability across runtime layers:
- **Prompts**: High portability; plain text prompts transfer across providers with minimal changes.
- **Tool implementations**: High portability; standard Python functions remain independent of frameworks.
- **Message histories**: Portable if stored in application databases; vulnerable to lock-in if managed exclusively within hosted sessions.
- **Orchestration logic**: Moderately portable; keeping routing logic decoupled from proprietary SDK constructs minimizes migration effort.

## Module architecture overview

This module constructs three core mechanisms from first principles:

1. **A runner with handoffs**: Multi-agent delegation implemented as state reassignment within a tool execution loop.
2. **Pre-execution guardrails**: Input validation gates that can abort execution before incurring model inference costs.
3. **Typed output with retry loops**: Structured output validation where parse errors return as feedback for automated model correction.

Building these components directly provides a clear view into the internal mechanics of modern agent SDKs.
