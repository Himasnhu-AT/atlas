In modern agent runtimes, multi-agent systems do not require complex inter-process messaging.
Execution runs through a single loop managing message history and a `current_agent` reference.
A handoff occurs when the model invokes a synthetic tool designed to update that reference.

## What the model sees

An agent configured with two tools and one handoff target receives three tool definitions.
Two correspond to standard tools, and the third is generated dynamically for the target agent:

```json
{
  "type": "function",
  "function": {
    "name": "transfer_to_billing",
    "description": "Hand off to billing. Answer billing questions.",
    "parameters": {"type": "object", "properties": {}, "required": []}
  }
}
```

The transfer tool requires no input arguments because the ongoing conversation history already
supplies context. The tool description includes the target agent's instructions, providing the
model with the context necessary to determine when routing is appropriate.

Tool names must conform to provider formatting constraints. Agent names such as `Refund Desk`
normalize to lowercase identifiers without spaces or special characters (e.g., `transfer_to_refund_desk`).

## How handoff dispatch works

When the model invokes a transfer tool such as `transfer_to_billing`:

1. The assistant message containing the tool call appends to conversation history.
2. A corresponding `tool` role message appends to history (e.g., `"Transferred to billing."`), matching the `tool_call_id`. Model providers enforce that every requested tool call must have a matching response in history.
3. The runtime reassigns `current_agent = billing`.
4. The execution loop continues to the next step.

```python
targets = {handoff_tool_name(t): t for t in current_agent.handoffs}

for call in choice.message.tool_calls:
    if call.function.name in targets:
        target = targets[call.function.name]
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": f"Transferred to {target.name}.",
        })
        current_agent = target
    else:
        # dispatch standard tool
        pass
```

On the subsequent iteration, the runner constructs the request using the new agent's system prompt
and tool schemas alongside the shared conversation history.

## Context and tool boundaries across transfers

Handoffs enforce specific boundaries between agents:

- **Conversation history persists**: The new agent receives prior messages, including the user query and intermediate tool outputs. In production runtimes, context filters can trim earlier history to manage token limits.
- **System instructions are isolated**: System instructions are dynamically prepended on each request based on `current_agent`. Storing instructions directly in the persistent history would cause instruction bleed across handoffs.
- **Tool schemas are scoped**: The model only sees the tools declared by the active agent. An agent cannot invoke unauthorized tools or delegate to undeclared targets.

## Common failure modes

- **Infinite delegation loops**: Two agents configured to transfer to each other can loop indefinitely without reaching a resolution. Enforce strict turn limits and raise an error when the limit is reached.
- **Unanswered tool calls**: Reassigning the active agent without logging the corresponding `tool` message creates invalid message sequences rejected by LLM APIs.
- **Unregistered targets**: If a prompt induces the model to call a transfer tool that does not exist in the active agent's declarations, handle it explicitly as a routing failure rather than a generic unknown tool error.
- **Excessive handoff latency**: Each handoff consumes an API turn. If agents share similar capabilities and security boundaries, combining them into a single agent with multiple tools is often faster and more cost-effective than multi-agent routing.
