Parsing unstructured text outputs with regular expressions is brittle and susceptible to minor phrasing shifts.
While provider-specific constrained JSON modes ensure syntax compliance, they vary across vendors and do
not validate semantic domain rules.

A framework-agnostic approach models structured output as a synthetic tool call (e.g., `final_output`)
parameterized by a JSON Schema. The model invokes the tool, the application validates the submitted arguments,
and successful validation yields a strongly typed Python data structure.

## Generating the schema

Dataclasses provide a clean source for generating structured JSON schemas:

```python
@dataclass
class Ticket:
    title: str = field(metadata={"description": "One line summary of the problem"})
    severity: int = field(metadata={"description": "1 is lowest, 5 is highest"})
    tags: list[str] = field(default_factory=list)
```

Generates:

```json
{
  "type": "object",
  "properties": {
    "title": {"type": "string", "description": "One line summary of the problem"},
    "severity": {"type": "integer", "description": "1 is lowest, 5 is highest"},
    "tags": {"type": "array", "items": {"type": "string"}}
  },
  "required": ["title", "severity"],
  "additionalProperties": false
}
```

Field metadata descriptions are included directly in the generated schema, guiding the model toward
valid domain values. Fields with default values or factories are omitted from the `required` list,
clarifying optional fields to the model.

## Schema validation and error aggregation

Syntax validation alone does not ensure business rule compliance. A payload might parse as valid JSON
while violating type expectations or value bounds.

When validating inputs, aggregate all errors into a single diagnostic response rather than failing on the first error:

```
title: missing
severity: expected integer, got str
```

Key considerations for validation messages:
- Use JSON type terminology in error descriptions so the model understands the schema violation relative to its input definitions.
- Distinguish booleans from integers: in Python, `bool` is a subclass of `int`, so integer validators must explicitly reject boolean values to prevent `"true"` from passing as `1`.

## Self-correction through tool error feedback

When validation fails, the runtime feeds the aggregated validation error back to the model as the result of the tool invocation:

```python
try:
    output = validate_into(output_type, arguments)
except ValidationError as error:
    retries += 1
    messages.append({
        "role": "tool",
        "tool_call_id": call.id,
        "content": str(error),
    })
    continue
return TypedResult(output, retries, messages)
```

The model receives its previous output alongside the specific validation errors in the conversation history,
enabling it to rectify missing or malformed fields on the subsequent turn.

Enforce a maximum retry threshold. Consecutive validation failures typically indicate an ambiguous prompt,
unrealistic schema constraints, or a model capability mismatch. Capping retries prevents costly runaway loops.

## Tool dependency injection via run context

To avoid global state in tools, frameworks like Pydantic AI supply a `RunContext` as the tool's initial argument:

```python
def lookup_customer(ctx: RunContext, customer_id: str) -> str:
    """Look up a customer by id."""
    return ctx.deps.db.plan_for(customer_id)
```

Dependency injection improves testability by allowing mock clients during testing without module patching.
The execution runtime strips context parameters from the exported tool schema to prevent the model from
attempting to populate internal system arguments.
