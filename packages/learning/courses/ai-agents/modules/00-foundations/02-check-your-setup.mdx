Everything in this course runs the same way, so it is worth ten minutes finding out that the
way works on your machine. The exercise at the end is deliberately easy. What it proves is not
that you can count words, it is that Python, the editor, the test runner and the mock client
are all where they should be.

## The toolchain, and why it is this small

Three things, and you already have two of them.

Python 3.10 or newer is the only thing you install. `unittest` is the test framework and it
ships with Python. `mockllm` is a single file with no imports outside the standard library,
which the app copies into each exercise workspace next to your code.

That is the whole list, and the shortness is a design decision with a cost attached. You will
not learn pytest here, and pytest is what most Python projects you join will actually use. Its
fixtures and its parametrisation are genuinely better than what `unittest` gives you. The
trade was made in the other direction because every dependency is one more thing that can be
the reason someone never gets to lesson three, and because the promise that an exercise needs
no API key and no network is only worth making if it also needs no install.

`unittest` is not a toy. It is what the standard library tests itself with, and everything you
learn about reading its output transfers to pytest, which prints a friendlier version of the
same information.

## How grading works

The first time you open an exercise, the app copies `scaffold.py` to `solution.py`. From then
on `solution.py` is yours and the app leaves it alone, so your work survives closing the app,
reopening the lesson, and looking at the scaffold again.

The name is fixed on purpose. `test.py` starts like this:

```python
from solution import (
    count_words,
    first_reply,
    last_user_message,
    role_counts,
    summarise_messages,
)
```

It imports from `solution`, never from `scaffold` and never from `reference`. Everything else
follows from that one word.

It means the same test file grades your attempt and grades the reference solution, with no
mode switch and no special case for either. Which in turn means the course cannot ship a
broken exercise: the content build copies `reference.py` to `solution.py` in a temporary
directory and runs the real test against it, and if the reference fails, the build fails and
the lesson does not ship. An exercise whose tests are impossible, or whose docstring describes
a different function from the one the tests check, cannot reach you. That is worth carrying
into every red test you see. When the grader disagrees with you, the disagreement is not a typo
in the grader.

It also means the names in your file are part of the contract. Rename `count_words` to
`word_count` and no assertion runs at all, because the import at the top of `test.py` fails
before the first test starts:

```
ImportError: cannot import name 'count_words' from 'solution' (/.../solution.py)
```

That is the one failure that is not about your logic. Change the body of a function as much as
you like; leave its name and its parameters alone.

## Reading a failure

Here is a real failure. The exercise asks for a word count, and this attempt used
`content.split(" ")` instead of `content.split()`:

```
test_an_empty_string_is_zero (__main__.TestCountingWords.test_an_empty_string_is_zero) ... FAIL
test_collapses_runs_of_whitespace (__main__.TestCountingWords.test_collapses_runs_of_whitespace) ... FAIL
test_counts_words (__main__.TestCountingWords.test_counts_words) ... ok

======================================================================
FAIL: test_an_empty_string_is_zero (__main__.TestCountingWords.test_an_empty_string_is_zero)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "/Users/you/exercises/check-your-setup/test.py", line 34, in test_an_empty_string_is_zero
    self.assertEqual(count_words(""), 0)
    ~~~~~~~~~~~~~~~~^^^^^^^^^^^^^^^^^^^^
AssertionError: 1 != 0

----------------------------------------------------------------------
Ran 16 tests in 0.001s

FAILED (failures=3)
```

Read it from the bottom. `FAILED (failures=3)` is the count. `AssertionError: 1 != 0` is the
whole story: your code produced 1 where 0 was expected. The left value is yours and the right
is what it should have been, because the tests here are written as
`assertEqual(what_you_returned, what_it_should_be)`. Above that is the line of test code that broke, which tells you the exact input. The squiggles
under it are Python 3.11 and newer pointing at the sub-expression that produced the value.

The `FAIL:` header names the test method, and the method names in this course are written to be
read: `test_an_empty_string_is_zero` says what it wanted before you look at anything else.

Many failures carry a message after the assertion, which is the part worth hunting for:

```
AssertionError: 1 != 0 : content is None on a turn that only calls a tool, so this has to return a number rather than raise
```

Everything after the second colon was written for the moment you are in. It is usually the
fastest route to the fix.

One distinction that matters later. `FAIL` means an assertion was false, so your code ran and
returned the wrong thing. `ERROR` means it raised on the way, and the traceback then points at
a line in `solution.py` rather than in `test.py`. Fix errors before failures: an exception
usually means one broken assumption is making several tests noisy.

## Running the tests yourself

In the terminal pane, or in any terminal sitting in the exercise directory:

```bash
python3 test.py                                        # everything, one line per test
python3 test.py TestCountingWords                      # one class
python3 test.py TestCountingWords.test_none_is_zero    # one test
```

Narrowing to a single test is the habit worth forming, because six red tests are rarely six
problems. The tests in one class exercise one function, so a single wrong line in it fails
every case that touches that line, and what you are reading is one bug described six ways.

Choose which one to narrow to rather than taking the first. `unittest` runs the methods of a
class in alphabetical order, so the failure at the top of the output is the alphabetically
first, not the simplest. Pick by name instead: fix the case with the smallest input, because a
function that is wrong on the empty case is usually wrong on the empty case inside all five
others too.

## When python3 is missing, or is 3.9

Ask before you guess:

```bash
python3 --version
```

If that prints `Python 3.10.x` or higher you are done. The app runs the same check on startup
and tells you what to install when the interpreter it finds is missing or too old, so you
should not be able to get far with a broken one without being told.

If the command is not found, install Python from python.org or from your platform's package
manager. On Windows the launcher is `py` rather than `python3`, so try `py -3 --version` and
run the tests with `py -3 test.py`.

If it prints 3.9 or older, upgrade. Python 3.9 is past the end of its security support, and the
floor here is not arbitrary: the course's own exercise checker asks Python which modules are in
the standard library through `sys.stdlib_module_names`, which arrived in 3.10, and the
exercises are written against the union syntax that became ordinary in the same release.

On macOS, a Python installed by Homebrew or from python.org sits alongside the system one
rather than replacing it, which is what you want. The system Python belongs to macOS, other
things on your machine use it, and upgrading it in place is how you find out which ones.

## Your exercise

Five small functions over a list of chat messages: count the words in one message, count the
messages per role, find the most recent user message, produce a one line summary, and make a
single call to the mock client.

The tests check the edges rather than the happy path, because the edges are where the
toolchain proves itself. Content that is `None`, an empty conversation, a role that never
appears, and a summary string that has to match exactly, plural or not.

Two of them catch people. `str.split()` with no argument collapses runs of whitespace and
returns an empty list for an empty string; `split(" ")` does neither, and that single character
is three red tests. And the last user message is the last one, so search backwards: by the time
you are running an agent the message list holds several user turns and the one you want is
never the first.
