        The draft is written and you have one more call to spend on it. The call has to

        - id: is-it-correct
          label: Here is my answer. Is it correct?

        - id: whats-wrong

        Wording moves the verdict more than the draft does. That is worth knowing, and it

        - id: reread
          label: Re-read the transcript and ask whether the conclusion follows
          bucket: same-context

        - id: rate-confidence
          label: Ask the model how confident it is in what it wrote
          bucket: same-context
          because: A confidence score is generated from the same context as the answer. It moves with fluency, not with truth.
        - id: critique-the-critique
          label: Ask the model whether its own critique was fair
          bucket: same-context

        - id: resample

          bucket: fresh-context

        - id: claim-question

          bucket: fresh-context

        "8": Routing on the verdict is fine. The problem is upstream, in what the verdict was formed from.

        - Reply yes or no is a coin with a heavy side.
      reveal: >-
        Drop the working line and the yes-or-no line and you have a check that has to

        Here is the draft I wrote: "Sonar Systems shipped its first product in March 2019."

        - message: The draft claim is still quoted in the prompt. A checker that is shown the answer is being asked to agree with it.
          check: { op: notContains, text: shipped its first product in March 2019 }
        - message: The reasoning that produced the claim is still here. That inference is exactly what you want checked, so it cannot be an assumption in the checking prompt.
          check: { op: notContains, text: press release }
        - message: A yes or no question about somebody else's answer is answered by agreeing. Ask for the fact instead.
          check: { op: notMatches, pattern: "is that right|reply yes or no|is this correct", flags: i }

          check: { op: contains, text: Sonar Systems }
        - message: What is left has to be a question. End it with a question mark and nothing after it.
          check: { op: matches, pattern: "\\?\\s*$" }
        - message: Still too long to be a standalone question. Anything past the question is context the checker did not need.
          check: { op: length, max: 120 }
      hints:
        - Everything the draft asserted and everything it assumed has to come out. What survives is the thing you do not know yet.
        - You are not asking whether March 2019 is right. You are asking when it shipped.
        - One line, naming the company, ending in a question mark.

        The checking prompt is defined by its omissions. Nothing about the draft is in it,
        so a disagreement between the two answers is real information rather than the same
        run repeated with a different tone of voice.
      solution: |
        When did Sonar Systems ship its first product?

A common intuition in agent design is to ask the model to review its own output before returning a response. Generating a draft and subsequently prompting the model to verify accuracy adds an extra API call.

In practice, direct self-evaluation often confirms incorrect answers with high confidence, creating a false record of verification.

## Sources of confirmation bias

When prompted with *"Here is my answer. Is it correct?"*, the model receives the answer, the initial question, and the intermediate reasoning steps. The elements that contributed to the initial mistake remain present in context.

If an error originated from a misread number or an ambiguous specification, those same inputs persist in the evaluation turn. The second pass repeats the initial evaluation with the proposed conclusion already acting as an anchor in the context window.

Model behavior also exhibits sycophancy. Prompts framed as *"Is this right?"* bias the model toward agreement. Conversely, prompts asking *"What is wrong with this?"* frequently cause the model to introduce unwarranted edits into correct solutions. The framing of the review prompt directly shifts the verdict.

## Spectrum of verification independence

Verification techniques can be categorized by how much contextual dependency they eliminate between generation and evaluation:

**Same-context review.** Re-evaluating the complete transcript with the conclusion visible. This provides minimal independence and rarely catches subtle reasoning errors.

**Sampled self-consistency.** Generating multiple answers independently from the same prompt without cross-referencing previous drafts. Comparing multiple runs reveals whether the model reliably converges on the same conclusion.

**Claim decomposition.** Extracting discrete factual claims from the draft and validating each assertion independently without the surrounding narrative context. This constitutes chain-of-verification.

**Deterministic and external validation.** Executing code in an interpreter, checking schemas, running unit tests, or querying a relational database. External validation removes the LLM from the judging loop entirely.

Prioritize checks that minimize shared context with the original generation step.

This structural requirement mirrors the principle in [a guardrail that cannot be talked out of](lesson:ai-agent-security.a-guardrail-that-cannot-be-talked-out-of). In security contexts, a validator reading a compromised transcript inherits the compromise. In self-correction, an evaluator reading flawed reasoning inherits the flaw.

## Boundaries of self-correction

Self-correction mechanisms have clear operational limits:

**Missing parametric knowledge.** If a required fact is absent from model weights and context, additional reasoning turns cannot deduce it. Missing information requires explicit retrieval mechanisms.

**Flawed core strategy.** If the fundamental planning approach is invalid, recursive reflection typically refines the phrasing of the flawed plan rather than discovering an alternate strategy.

**Drift across iterations.** Open-ended loops that rewrite output until satisfied can drift away from the original user requirements over multiple turns. Verification loops must enforce strict iteration bounds.

## Cost and latency trade-offs

Every verification layer introduces multiplicative API calls. Decomposing an answer into five claims requires six calls instead of one. Sampling five paths for self-consistency multiplies token consumption by five.

In production environments, these calls increase latency and infrastructure costs. Tracking consumption via structured metrics, as outlined in [observability and cost](lesson:ai-multi-agent-and-production.observability-and-cost), reveals whether accuracy gains justify the additional inference expense.

Target verification strictly at high-impact outputs where errors carry operational or reputational cost. The [research briefing](lesson:ai-research-briefing.the-verification-pass) project applies this distinction by isolating factual claims for verification while avoiding redundant passes over stylistic prose.
