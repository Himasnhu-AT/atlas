Reflection structures self-correction into three sequential calls: produce an initial draft, generate a critique, and revise the output according to the feedback.

```
draft    = model(task)
critique = model(critique_prompt, draft)
final    = model(revise_prompt, draft, critique)
```

This pattern functions effectively for tasks governed by verifiable syntactic rules, such as code generation matching an interface, structured JSON output matching a schema, or text requiring specific formatting constraints. It performs poorly when used to verify factual truth.

## Stopping conditions and termination

Implementing a reflection loop requires three explicit stopping criteria:

**Iteration bounds.** Never allow the model to decide when it is finished. Open-ended instructions like *"revise until satisfied"* produce non-deterministic loops. Enforce a fixed iteration ceiling, typically one or two passes, with an early exit if the critique yields no defects.

**Structured negative findings.** The critique prompt must allow the model to report that no errors were found. Prompts asking *"what is wrong with this?"* force the model to identify flaws even in valid solutions. Ask for evaluations against explicit rubric items and accept empty defect lists.

**Improvement verification.** Revisions must be evaluated against objective criteria to verify whether quality improved rather than merely changed.

## Revision drift

Iterating reflection repeatedly across multiple cycles introduces semantic drift.

The first pass often resolves clear formatting issues or omissions. By the second or third pass, the critique begins targeting stylistic variations and rewriting sentences that were already adequate. Over multiple turns, the generated output drifts away from the core requirements of the original user prompt because each pass optimizes for satisfying intermediate critique comments.

Bounding the iteration count is essential for correctness. Unconstrained loops lack a restoring force to anchor generation back to the original prompt, causing the text to wander over successive turns.

## The laundering failure mode

A major risk in factual tasks is error laundering:

When a draft contains a factual error, the critique may highlight minor cosmetic flaws (such as an awkward phrase or missing transition). The revision step fixes the cosmetic flaws while preserving the underlying factual hallucination. The resulting output presents the erroneous fact in polished prose, accompanied by an audit trail that gives the illusion of rigorous review.

Reflection refines formatting, style, and syntax, but it does not establish factual veracity. Validating factual assertions requires isolated claim extraction where checks evaluate propositions without surrounding narrative bias.

## Reflexion and persistent feedback memory

A useful variation of reflection preserves critiques across execution attempts rather than discarding them.

In standard reflection loops, each attempt runs independently and can repeat previously resolved errors. By appending past critique findings into a concise list of recorded failures, subsequent attempts can avoid known pitfalls:

```
attempt 1 -> critique: "the date is not in the source"
attempt 2 -> provided with previous critique notes -> avoids repeating the error
attempt 3 -> provided with accumulated notes
```

This pattern proves valuable for coding agents retrying failing unit tests or workflows encountering deterministic tool errors. The accumulated memory must remain concise to avoid crowding the context window, as discussed in [tokens and the context window](lesson:ai-llm-fundamentals.tokens-and-context).
