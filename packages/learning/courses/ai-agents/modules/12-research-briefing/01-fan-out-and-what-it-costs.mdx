A comprehensive research agent decomposes a complex query, gathers evidence from document sources,
synthesizes a structured briefing, and verifies each cited claim against source texts:

```
question -> plan -> worker 1 -> \
                 -> worker 2 -> - -> supervisor -> verifier -> brief
                 -> worker 3 -> /
```

This lesson constructs the planning and retrieval components: the query planner, isolated worker execution,
and token budget tracking.

## Context isolation versus single-prompt retrieval

While simple questions can be addressed in a single prompt containing an entire document corpus,
parallel fan-out excels when sub-questions require independent investigation across large document sets.

Partitioning work across isolated workers provides context boundaries:
- Each worker receives only the documents retrieved for its specific sub-question.
- Workers cannot accidentally cite irrelevant documents from adjacent topics.
- Context windows remain focused, reducing distraction and attention degradation.

Maintaining strict context isolation is essential. If a worker receives the entire corpus, the architecture
loses its contextual clarity while incurring multi-worker invocation costs.

## Token cost dynamics in multi-agent fan-out

Multi-agent research pipelines consume substantially more tokens than single-turn chat completions:

- **Planning stage**: 1 model call to decompose the root query.
- **Worker stage**: $N$ independent worker calls, each carrying dedicated retrieved documents and extraction prompts.
- **Synthesis stage**: 1 supervisor call aggregating all extracted notes.
- **Verification stage**: 1 verification call per cited statement in the generated draft.

Because every worker executes an independent context prompt, token consumption scales linearly with worker count.
Tracking spend across stages ensures visibility into execution expenses:

```python
@dataclass
class Budget:
    limit: int
    spent: int = 0
    by_stage: dict[str, int] = field(default_factory=dict)

    def charge(self, stage: str, usage) -> None:
        self.spent += usage.total_tokens
        self.by_stage[stage] = self.by_stage.get(stage, 0) + usage.total_tokens
        if self.spent > self.limit:
            raise BudgetExceeded(f"budget of {self.limit} exceeded at {stage!r}")
```

Recording token spend before raising `BudgetExceeded` ensures audit logs accurately reflect billed API usage.
Preserving completed worker notes upon budget exhaustion allows partial recovery rather than abandoning completed work.

## Query decomposition and deduplication

The planning stage generates sub-questions that each initiate an independent worker run. Redundant or duplicate
sub-questions consume budget unnecessarily.

Clean planner output before execution:
1. Strip leading and trailing whitespace.
2. Deduplicate queries while preserving original ordering.
3. Truncate the query list to the configured worker cap.

If the planner yields an empty plan, fall back to executing a single worker against the original query to ensure
execution proceeds.

## Worker grounding and fabrication filtering

A research worker receives a sub-question, a set of retrieved documents, and a structured extraction tool.
If a worker emits a note referencing an unprovided document ID, that citation is invalid.

Verify document membership before accepting notes:

```python
allowed = {doc.id for doc in documents}

notes, dropped = [], 0
for note in raw_notes:
    if note["doc_id"] not in allowed:
        dropped += 1
        continue
    notes.append(note)
```

Tracking `dropped` note counts provides an operational metric for hallucinated citations, flagging prompt degradation
or context mismatch early in the pipeline.

## Fan-out mechanisms in graph frameworks

Graph frameworks model fan-out using dynamic branching and append reducers:

```python
# Reference example using LangGraph syntax
class State(TypedDict):
    question: str
    notes: Annotated[list[Note], operator.add]   # append reducer aggregates worker outputs

def fan_out(state: State):
    return [Send("worker", {"sub_query": q}) for q in state["sub_queries"]]
```

In custom runtimes, iterating over sub-queries and aggregating extracted notes via `notes.extend(...)`
implements the exact same execution pattern.
