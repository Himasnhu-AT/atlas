Durable execution in a graph runtime requires writing a checkpoint dictionary at the end of
each super-step. Because the scheduler maintains no external execution queues or transient
flags, the complete runtime state consists solely of channel values, channel versions, and `versions_seen`.
Persisting these three structures fully captures the execution state.

## The checkpoint record

The checkpoint structure aligns with conventions used in production systems like LangGraph:

```python
@dataclass
class Checkpoint:
    v: int                       # schema version
    id: str                      # lexicographically sortable identifier
    ts: str                      # ISO 8601 timestamp for display
    channel_values: dict
    channel_versions: dict
    versions_seen: dict
    updated_channels: list
```

- `v`: Schema version number to support future migrations of stored state records.
- `ts`: Display timestamp. Timestamps alone are insufficient for deterministic ordering due to potential sub-millisecond collisions.
- `id`: A zero-padded numeric string (e.g. `0000000001`) that sorts chronologically when compared as text. Production implementations often use ULIDs or UUIDv6.
- `updated_channels`: Lists which channels modified during the super-step, aiding debugging and audit inspection.

```python
def new_checkpoint_id(counter):
    return f"{counter:010d}"
```

## Thread configuration and addressing

Checkpoints belong to a thread representing an isolated workflow, conversation, or task.
Threads are referenced via configuration dictionaries:

```python
{"thread_id": "incident-4181"}                              # latest checkpoint in thread
{"thread_id": "incident-4181", "checkpoint_id": "00000002"} # specific historical checkpoint
```

Omitting `checkpoint_id` retrieves the latest checkpoint for that thread. Resuming execution
consists of loading the newest checkpoint and running the standard scheduler loop.

## Resuming from saved state

To resume execution:
1. Load `channel_values`, `channel_versions`, and `versions_seen` from the checkpoint.
2. Invoke the scheduler.

Completed nodes have their subscribed channel versions recorded in `versions_seen`, so they do not
re-run. Unexecuted or pending nodes detect version differences and execute normally. The scheduler
requires no special-case logic for resume operations.

Important implementation details:
- **Deep copies**: Copy channel values when writing checkpoints. Storing raw dictionary references
  allows subsequent node mutations to alter historical records retrospectively.
- **Sequential IDs**: Resumed runs must continue checkpoint numbering from the existing thread count
  rather than resetting to zero, avoiding ID collisions.

## Replay and thread branching

Specifying an older checkpoint ID restores execution state to that historical point:

```python
config = {"thread_id": "incident-4181", "checkpoint_id": older_id}
run_with_checkpoints(graph, saver, config)
```

Replaying appends new checkpoints to the thread history without overwriting past entries.

Forking creates a new thread starting from an existing checkpoint. The runtime copies the checkpoint
into a new `thread_id` and records a `parent_config` referencing the source:

- Within a thread, checkpoints form a chronological sequence.
- Across forks, `parent_config` pointers form a version tree, supporting features like trying alternate tools or running comparative prompt evaluations from a shared prefix.
- Storage must namespace records by thread first, ensuring strict data isolation between parallel runs.

## Production checkpointer considerations

In-memory storage is useful for testing and transient graphs. Production checkpointers (such as PostgreSQL or Redis backends) add:
- Serialization handling for non-JSON Python objects.
- Write-ahead checkpoints recorded before external API invocations.
- TTL policies to prune historical threads automatically.
- Pending writes tracking: persisting individual node outputs before the super-step merge. This prevents re-executing completed side effects (like payments or emails) if a sibling node fails during the same step.
