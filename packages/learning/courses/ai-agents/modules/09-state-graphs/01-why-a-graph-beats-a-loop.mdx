Earlier modules modeled an agent as a state graph or a loop. This module opens
the runtime internals. By the end of it you will have written a complete graph runtime:
channels with reducers, a scheduler that runs nodes in super-steps, and a checkpointer
that enables resume, replay, and branching from saved state records.

This implementation uses the same core mechanisms and naming conventions found in production
frameworks like LangGraph, kept compact enough to understand in detail.

## Where the graph sits

Agent frameworks divide into two distinct layers that are often conflated.

The top layer is the harness: prebuilt ReAct agents, role-based teams, and handoffs between
specialists. It is what quickstart tutorials highlight and provides a fast way to get
an initial prototype running. It is also the layer that breaks first when custom requirements
diverge from the framework's abstractions.

The bottom layer is the runtime: how state is stored, how concurrent writes merge,
how the execution order is determined, and how state persists across process restarts.
LangGraph's prebuilt `create_react_agent` is a thin wrapper over its execution runtime.
CrewAI teams and the OpenAI Agents SDK handoffs share a similar structure: a harness
sitting on top of a scheduler.

Understanding the runtime is necessary because it explains subtle runtime errors.
A node executing twice, a state value being overwritten instead of appended, or a resumed run
replaying an expensive API call are all runtime behaviors governed by channels, reducers,
and state versions.

## What a while loop cannot express

A standard ReAct loop follows a simple structure:

```python
while not done:
    choice = call_model(messages).choices[0]
    if choice.finish_reason != "tool_calls":
        return choice.message.content
    messages += run_tools(choice)
```

State is a single growing list, and control flow is a single cycle. For many linear
agent tasks, this structure is sufficient.

However, standard loops struggle with more complex patterns:
- Running two research branches concurrently against the same question and merging their findings deterministically.
- Pausing execution for human approval and resuming three days later in a different process.
- Inspecting the exact intermediate state from step 9 of a 17-step run.
- Recovering from a failure on step 4 of 5 without paying to re-run preceding steps.

You can bolt these features onto a while loop using mutable intermediate state dictionaries,
custom dispatch tables, and manual checkpoint calls. That approach essentially creates an
ad-hoc graph runtime that lacks formal guarantees under concurrent execution.

## The runtime in one paragraph

State lives in named channels rather than a single list. Each channel has a reducer that decides
how new writes combine with existing values, and a version counter that increments on every write.
Each node declares which channels it subscribes to. The scheduler repeatedly identifies every node
whose subscribed channels updated since that node last ran, executes all eligible nodes against
a single state snapshot, and merges their writes after all nodes in the step finish.
This unit of execution is a super-step. After each super-step, the checkpointer writes a persistent record.

The following lessons cover these three components: channels, scheduling, and checkpointing.

## What this looks like in the real thing

This example demonstrates the pattern using LangGraph syntax for comparison:

```python
from typing import Annotated, TypedDict
import operator

from langgraph.graph import END, START, StateGraph
from langgraph.checkpoint.memory import InMemorySaver


class State(TypedDict):
    # The annotation defines the reducer. Without it, writes overwrite the list.
    findings: Annotated[list[str], operator.add]
    question: str
    verdict: str


builder = StateGraph(State)
builder.add_node("search", search)
builder.add_node("critique", critique)
builder.add_edge(START, "search")
builder.add_conditional_edges("critique", route)   # returns "search" or END

graph = builder.compile(checkpointer=InMemorySaver())
graph.invoke(
    {"question": "did the deploy break checkout?"},
    config={"configurable": {"thread_id": "incident-4181"}},
)
```

The `Annotated` type on `findings` defines a channel with an append reducer. The `thread_id`
specifies the conversation thread, and the checkpointer enables resuming or inspecting that thread.
You will build equivalents for all of these concepts in the exercises.

## When the graph is ceremony

Graphs introduce architectural overhead compared to simple loops. Local variables become channel
declarations, errors propagate through a scheduler stack, and basic linear flows require more boilerplate.

Prefer a plain loop when the agent performs a single model call with tool invocations and finishes in
seconds. A graph is unnecessary when execution follows a strict linear sequence of function calls.

Use a graph runtime when workflows require fault tolerance across process boundaries, parallel execution
paths with explicit merge strategies, or step-by-step state inspection and time travel.

When requirements are evolving, understanding the underlying runtime mechanisms allows you to make
principled architectural decisions based on state management and persistence needs.

3. **The checkpointer**: State persistence per super-step, resume, replay, and thread branching.
