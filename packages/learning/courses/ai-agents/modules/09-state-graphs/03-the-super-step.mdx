The scheduler operates on a single execution model derived from Pregel, Google's distributed
graph processing system:

1. Identify all eligible nodes.
2. Capture a snapshot of current channel state.
3. Run all eligible nodes concurrently or sequentially against that snapshot.
4. Merge all node outputs through channel reducers only after every node in the step completes.

This atomic execution cycle is called a super-step.

## One snapshot per step

Nodes executing within the same super-step cannot observe each other's writes during execution.
Each receives a copy of the state as it existed before the step started:

```python
snapshot = state.values()
snapshot_versions = state.versions()

# Every node in the step reads the same snapshot.
outputs = [(name, self._nodes[name](dict(snapshot))) for name in eligible]

# Updates apply only after every node has returned.
updated = []
for name, update in outputs:
    if update:
        updated.extend(state.apply(update))
```

Merging updates incrementally during node execution introduces non-determinism based on execution
order or dictionary iteration. Isolating reads from writes guarantees reproducibility: identical inputs
and node definitions yield identical merged states.

Channel updates apply in the sorted order of node names determined by `eligible_nodes`, ensuring deterministic
reducer output when multiple nodes append to the same list.

## Edges are channels

In this architecture, an edge is not a separate control-flow structure. It is implemented as a channel
paired with a subscription.

When adding an edge from node `a` to node `b` via `add_edge("a", "b")`, the runtime ensures a trigger channel
exists for `b` (conventionally named `to:b`). When `a` finishes, it writes a tick counter to `to:b`.
That write increments the channel version, making `b` eligible for the next super-step:

```python
def trigger_channel(node):
    return f"to:{node}"

# After node "a" completes:
triggers[trigger_channel("b")] = tick
state.apply(triggers)
```

This design provides three architectural advantages:
- Entry point invocation uses standard channel writes before step zero.
- Triggering nodes via static edges and data channel updates uses the exact same scheduler logic.
- Checkpointing requires storing only channel values and versions rather than a separate pending execution queue.

## Fan-out and fan-in

Fan-out occurs when one node targets multiple downstream nodes via edges. All target nodes become eligible
simultaneously and execute in parallel during the next super-step.

Fan-in requires no dedicated join primitives. A join node subscribes to a channel written by multiple
upstream branches. When those branches execute during step $N$, their outputs merge into the target channel
via reducers. The target channel version increments, making the join node eligible in step $N+1$.

If a join node is mistakenly subscribed to only one branch's channel, it triggers prematurely with incomplete
data. The subscription must include the channels from all dependencies to ensure proper synchronization.

## Marking what a node has seen

After channel writes merge, the runtime updates `versions_seen` for each executed node.
Recording the correct version timestamp is essential for loops:

The runtime records the channel versions observed at the *beginning* of the super-step, not the post-merge versions.
If post-merge versions were recorded, a node writing to its own subscribed channel would immediately mark
its own write as seen, preventing self-triggering cycles. Storing pre-step versions ensures self-looping
nodes remain eligible in subsequent steps.

## Conditional edges

A static edge always directs flow to a fixed target. A conditional edge evaluates a routing function:

```python
router = self._routers.get(name)
if router is not None:
    target = router(state.values())   # evaluated after the merge
```

Routers execute after the step's writes have merged, allowing the routing logic to inspect the latest values
produced by the node. Evaluating before the merge would cause routing decisions based on stale state.

Routing to `END` terminates that execution branch. If a router returns a target node name that does not exist,
the runtime should raise an error immediately. Silently accepting unknown node names leads to stranded
writes without active subscribers.

## How graph execution terminates

A graph execution halts under three distinct conditions:

1. **Explicit end**: A step routes to `END`.
2. **Quiescence**: No nodes have pending version updates (`eligible_nodes` returns an empty list).
3. **Step budget exceeded**: The loop counter exceeds `max_steps`.

Step limits should track super-steps rather than individual node calls or model invocations.
A fan-out across five nodes counts as one super-step. When a graph exceeds its step budget,
raise an exception containing the execution history up to the failure point to aid debugging.
