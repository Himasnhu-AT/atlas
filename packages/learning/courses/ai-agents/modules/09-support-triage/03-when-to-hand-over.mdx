The answering layer from the last lesson has no memory and no opinion about the conversation
it is part of. It answers whatever it is handed. The session is the thing that decides whether
this message should be answered at all, and it is a state machine with three states and two
transitions.

```
answering  --customer asks for a person-->  pushed back
pushed back --customer asks again-------->  escalated
escalated  --anything at all------------->  escalated
```

Everything difficult about a support agent lives in those two arrows.

## Detecting the request

Start with keywords. Not because it is sophisticated, but because a request for a human is one
of the few things customers say in a small, stable vocabulary, and a classifier here costs a
model call on every single message to answer a question a regex answers correctly.

```python
WANTS_HUMAN = ("human", "real person", "agent", "representative", "someone else")
```

Two rules make this work rather than embarrass you.

Match on word boundaries. Without them, "this is a question about humanities funding" contains
`human` and escalates a customer who was asking about a grant.

Mask the phrases that merely contain a trigger word, before you match:

```python
NOT_A_REQUEST = ("user agent", "agent string", "support agent", "this agent")

text = message.lower()
for phrase in NOT_A_REQUEST:
    text = text.replace(phrase, " ")
```

`agent` is both a support word and a computing word. A customer pasting "my user agent string
is broken" is asking for help, not for a person, and word boundaries do not save you here
because "user agent" is two whole words. Every keyword detector in production grows an
exclusion list like this within about a month of launch, built from the false positives. Ship
it with one and read your logs.

The asymmetry is worth stating plainly. A false positive escalates a customer who never asked,
which quietly destroys the deflection number. A false negative traps somebody who did ask,
which is the interaction people screenshot. When you are unsure, err toward hearing the
request.

## Push back exactly once

Once, not zero and not twice.

Zero pushbacks means the agent hands over anyone who says the word, including the many
customers who ask for a person out of habit before they have seen an answer, and would have
been perfectly happy with article A2. That is the whole business case going out of the door on
a keyword.

Two pushbacks is arguing with a customer who has now asked twice. There is no version of that
which reads well in a screenshot, and the second offer is almost never better than the first,
because nothing new has been learned between them.

The number is configurable and the default is one:

```python
def __init__(self, client, articles, max_pushbacks=1):
```

Setting it to zero is a legitimate choice for a queue where nobody bluffs, such as billing
disputes or anything with a regulator attached. Setting it above one is a decision somebody
should have to defend.

## What the pushback offers matters

The naive pushback retrieves against the message it just received. The message is "can I speak
to a human", which retrieves nothing useful, so the customer gets a generic apology and asks
again. You have spent your one attempt on nothing.

The customer's question is still the question. Look back for the last message that was not a
request for a person, and offer the best article for that:

```python
def _topic(self, message):
    for role, said in reversed(self.transcript[:-1]):
        if role == "user" and not wants_human(said):
            return said
    return message
```

Now "my password reset link expired" followed by "can I speak to a human" offers the password
reset article, which is a real second attempt rather than a stalling noise. When there is no
earlier question, because the customer opened by asking for a person, fall back to the message
itself and take what retrieval gives you.

## The handoff is the deliverable

When the agent gives up, a person picks the conversation up. What that person receives is the
entire point of the escalation, and it is the part most implementations leave empty.

```python
@dataclass
class Handoff:
    reason: str
    summary: str
    attempted: list[str]
    article_ids: list[str]
    transcript_turns: int
```

Every field earns its place by removing work from the human.

`summary` is the one line they read before deciding whether to open the transcript. It quotes
what the customer opened with and says how long this has been going on.

`attempted` is every reply the agent already sent, in order. Without it the human's first
message is an answer the customer has already been given and already rejected, which is how a
mildly annoyed customer becomes an angry one.

`article_ids` says which parts of the knowledge base were already tried, deduplicated. If the
same three articles keep appearing in escalations, that is a documentation gap with a queue
attached to it, and it is the single most actionable report a support agent can produce.

`transcript_turns` is how much patience has already been spent. Two turns and one is a
different ticket from nine turns and one.

Copy the lists into the handoff rather than aliasing them. A payload that keeps changing after
it has been handed over is a bug nobody finds by reading the code.

## Then stop talking

Once escalated, every later message returns the same handoff and never calls the model again.

```python
if self.escalated:
    return self._say(ALREADY_ESCALATED_TEXT, "escalated", self.handoff)
```

Two reasons, one commercial and one human. The commercial one is that a conversation a person
now owns generates model calls forever if you let it, on messages nobody will read. The human
one is that an agent still offering help articles while somebody waits for a person is worse
than an agent that says nothing. Returning the same handoff object, rather than building a
fresh one, keeps a single escalation from becoming three tickets.

## The same idea in a framework

For illustration, since it needs an API key and a network. The OpenAI Agents SDK gives handoff
a first class shape:

```python
# Illustration. Does not run here.
from agents import Agent, handoff

billing = Agent(name="Billing specialist", instructions="...")
triage = Agent(
    name="Triage",
    instructions="Answer from the knowledge base. Hand off when the customer asks.",
    handoffs=[handoff(billing, on_handoff=log_handoff)],
)
```

The framework routes the conversation and carries the message history across. What it does not
decide is when to hand off, what counts as asking, how many attempts come first, or what the
receiving side gets beyond the raw transcript. Those are the four decisions in this lesson,
and they stay yours whichever framework you pick. Knowing that is the difference between
choosing a framework and hoping one will make the product decisions for you.

## Your exercise

Build the session. `wants_human`, `summarise`, and a `TriageSession` whose `handle` implements
the contract above. The answering layer from the last exercise ships with the scaffold,
already written.

The tests check that the first request pushes back and the second escalates, that the pushback
offers the article for the last real question, that the handoff lists both earlier replies and
counts the customer's turns, that a session which never asks never escalates however long it
runs, that nothing calls the model after escalation, and that
`wants_human("my user agent string is broken")` is False.

Watch the order of operations in `handle`. The customer's turn goes into the transcript first,
so a handoff built on that turn counts it.
