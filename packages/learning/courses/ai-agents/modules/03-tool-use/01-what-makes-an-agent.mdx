A model call is a function. Text goes in, text comes out, and nothing in the world has
changed. Call it a thousand times and you have a thousand pieces of text.

An agent places that function inside a loop, allowing the runtime to execute code between calls and put
the result back in front of the model. That is the entire structural difference. Every
other property people attribute to agents follows from it or reflects marketing claims.

## Where the line sits

Two programs, both using a model, both useful. One is an agent and one is not.

```python
# Not an agent. One call, one answer, done.
summary = client.chat.completions.create(
    model="mock",
    messages=[{"role": "user", "content": f"Summarize this ticket:\n{ticket}"}],
)

# An agent. The model asks for something, your code runs it, the loop goes round.
while True:
    response = client.chat.completions.create(model="mock", messages=messages, tools=TOOLS)
    if response.choices[0].finish_reason != "tool_calls":
        break
    messages.append(assistant_turn(response.choices[0]))
    for call in response.choices[0].message.tool_calls:
        result = dispatch(registry, call.function.name, call.function.arguments)
        messages.append(tool_result_turn(call.id, to_tool_content(result)))
```

The second program has a property the first cannot have: the number of model calls is decided at
runtime by the model, based on what your code returned. You wrote the loop and you own
every tool inside it, but you do not know in advance how many times it will run.

This creates the primary engineering difficulty. A program whose control flow is decided by a
model cannot be tested by enumerating paths, bounded by reading the source, or costed out in
advance. The rest of this course focuses on placing controlled bounds on that execution.

## Three parts, and the one people leave out

An agent needs a goal, tools to act with, and a reason to stop.

The goal arrives as the user's message, usually with a system prompt shaping how it is
interpreted.

The tools are functions you wrote, described to the model in a schema it can read. The next
lesson focuses on that description, which is the only information the model receives about
your code.

The stopping condition is frequently omitted, and omitting it increases compute costs. A
loop with no exit does not terminate cleanly; it makes model calls, each carrying the entire
conversation history, until an external process kills it. Two mechanisms handle termination:
the natural exit and the backstop budget. The natural exit occurs when the model produces a
reply requesting no tools, detected by reading `finish_reason` directly rather than inspecting text.
The backstop is a step budget: a hard cap on model calls, terminating the run whether or not an
answer was reached.

The budget must act as a hard cap rather than a hint, and hitting it must fail visibly. A loop that
quietly returns partial output when the budget expires produces a value indistinguishable
from a completed answer, leaving the caller unable to detect an incomplete run. The third lesson
implements this termination logic.

## Autonomy means who picks the next step

Autonomy in code comes down to one question: who decides what happens next?

If your code decides by executing steps in a predefined sequence, the model acts as a component.
It transforms text at predetermined integration points. This is a pipeline.

If the model decides by choosing which tool to invoke with which arguments and when to stop,
the model acts as the controller. Your code serves as the runtime environment it executes on.

Most production systems operate between these extremes. System position represents an intentional
architectural decision rather than a maturity level. You can allow the model to choose freely
from twenty tools, or constrain choices to three tools inside a fixed execution sequence.
Granting broader control accommodates unexpected inputs at the expense of predictability,
testability, and cost bounds.

## What people mean when they say agent

Five architectural patterns illustrate how control shifts toward the model:

| Shape | Who decides the next step | What breaks first |
| --- | --- | --- |
| One call with structured output | You | Nothing; it is a function call |
| One tool call, then you handle it | You | The model picks the wrong tool |
| A fixed pipeline of model calls | You, at design time | An input the pipeline has no branch for |
| A loop with tools and a budget | The model, within your tools | Loops, cost, and silent wrong answers |
| A loop that can write and run new code | The model, nearly unbounded | Everything, spectacularly |

Most production systems described as agents occupy the third or fourth row. Row three delivers
reliable value, and teams describing fixed pipelines as agents are being imprecise rather than
dishonest. Unbounded code generation in row five rarely runs unattended in customer-facing environments
without sandboxing and human oversight.

Knowing your system's category clarifies failure modes and engineering requirements. Row three
fails when an input lacks a matching branch, resolved by adding branches. Row four fails through
infinite loops, confident tool calls with incorrect arguments, and unhandled logic errors.
Resolving row four failures requires step budgets, structured observations, and explicit termination tracking.

## The loop is the same underneath every framework

You will implement this loop manually. It requires roughly forty lines of code.

Later in the course you will use frameworks that manage this loop. Building it manually first
matters because framework abstractions are named after parts of this loop, and framework bugs
reflect this loop's failures wrapped in foreign stack traces. When a framework agent calls a tool
repeatedly, drops a tool result, or exceeds cost projections, the cause resides in the message list
it constructed. Visualizing that list is the essential skill.

Frameworks provide persistence between runs, concurrency, retries, tracing, human approval steps,
and shared conventions for teams. The core loop itself has remained consistent across provider tool-calling
APIs and fits on a single screen.
