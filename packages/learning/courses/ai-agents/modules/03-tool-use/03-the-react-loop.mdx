The execution loop follows four steps. The model determines what action is required. It emits a tool call request.
Your code executes the tool and returns the observation. The model evaluates the updated context and continues.

The name comes from the 2022 ReAct paper (Reasoning and Acting), which demonstrated that interleaving reasoning
traces with concrete actions outperformed either approach in isolation on knowledge retrieval tasks. Early implementations
prompted models to output `Thought:`, `Action:`, and `Observation:` lines, parsing the response text using regular expressions.
Modern model providers support this loop directly through dedicated tool calling APIs. The underlying loop remains the same,
while structured schemas replace brittle text parsing.

## The loop in full

```python
messages = [{"role": "user", "content": question}]

for _ in range(max_steps):
    response = client.chat.completions.create(
        model="mock", messages=messages, tools=tools
    )
    choice = response.choices[0]

    if choice.finish_reason != "tool_calls":
        return choice.message.content or ""

    messages.append(assistant_turn(choice))

    for call in choice.message.tool_calls:
        result = dispatch(registry, call.function.name, call.function.arguments)
        messages.append(tool_result_turn(call.id, to_tool_content(result)))

    raise MaxStepsExceeded(max_steps, messages)
```

The control flow relies on a `for` loop with two exits. The critical complexity lies in message bookkeeping.
The `messages` list represents the entire runtime state of the agent. Provider APIs do not maintain session memory
between calls. Any context the model evaluates on step seven exists solely because it was appended to that list.

## The same run, message by message

Tracing the message list clarifies state transitions. Consider a two-step run against `mockllm`, configured with
one tool call followed by a final answer.

On the initial iteration, `messages` contains only the user query:

```python
[{"role": "user", "content": "What is the population of Tokyo?"}]
```

The model returns `finish_reason == "tool_calls"` containing one call: id `call_1_0`, name `lookup_population`,
and arguments `'{"city": "Tokyo"}'`. Before the next loop iteration, two messages are appended:

```python
[
    {"role": "user", "content": "What is the population of Tokyo?"},
    {"role": "assistant", "content": None, "tool_calls": [
        {"id": "call_1_0", "type": "function",
         "function": {"name": "lookup_population",
                      "arguments": '{"city": "Tokyo"}'}}]},
    {"role": "tool", "tool_call_id": "call_1_0",
     "content": '{"city": "Tokyo", "found": true, "population": 13960000}'},
]
```

These message structures reflect API protocol requirements:
1. The assistant turn records the model's exact generation, keeping `content` as `None` and preserving the raw `arguments` JSON string.
2. The tool turn immediately follows, matching the request via `tool_call_id`.
3. The tool output dictionary is serialized into a sorted JSON string rather than converted via Python's default `str()`.

The second iteration submits all three messages to the model. The model replies with `finish_reason == "stop"`
and the content "Tokyo has about 14 million people". The loop returns this string immediately. The final answer is
not appended to the transient `messages` list.

The test suite validates this structure by inspecting `client.requests[1]["messages"]` to ensure the sequence of
roles is `["user", "assistant", "tool"]`.

## Why message ordering and call identifiers matter

Two rules in this trace prevent HTTP 400 errors from API providers.

First, the assistant turn must precede the corresponding tool result. When a model requests tool executions, its
emitted response is a message containing `tool_calls`. A tool message is defined protocol-wise as a response to a
prior request. Omitting the assistant turn sends a tool response referencing a nonexistent call ID:

```python
[
    {"role": "user", "content": "What is the population of Tokyo?"},
    {"role": "tool", "tool_call_id": "call_1_0",
     "content": '{"city": "Tokyo", "found": true, "population": 13960000}'},
]
```

Providers reject this payload because a `tool` role message must follow an assistant message containing matching
`tool_calls`. Conversely, appending the assistant turn while omitting any of the requested tool results creates an
unanswered call, which providers also reject.

Second, the `tool_call_id` is the only pairing mechanism between request and response. Neither array index nor
tool name resolves this association. When a model invokes the same tool multiple times in a single turn, the IDs
distinguish the operations:

```python
{"role": "assistant", "content": None, "tool_calls": [
    {"id": "call_1_0", "type": "function",
     "function": {"name": "lookup_population", "arguments": '{"city": "Paris"}'}},
    {"id": "call_1_1", "type": "function",
     "function": {"name": "lookup_population", "arguments": '{"city": "Tokyo"}'}}]},
{"role": "tool", "tool_call_id": "call_1_0",
  "content": '{"city": "Paris", "found": true, "population": 2102650}'},
{"role": "tool", "tool_call_id": "call_1_1",
  "content": '{"city": "Tokyo", "found": true, "population": 13960000}'},
```

The tool messages share identical roles and names, differing only in `tool_call_id` and payload. Pairing by position
fails when tool results complete out of order during parallel execution. Always match on `tool_call_id`.

Tool outputs must be serialized as strings. Using `json.dumps(..., sort_keys=True)` produces deterministic byte
representations, ensuring consistent cache hits on providers supporting prompt caching.

## Stopping, and why it must be loud

The termination condition relies on `finish_reason`. Never rely on heuristic text inspections.

| finish_reason | Meaning | Action |
| --- | --- | --- |
| `tool_calls` | The model requested tools | Dispatch tools, append results, continue loop |
| `stop` | The model completed the turn | Return message content |
| `length` | Generation exceeded token limit | Raise error; the response is incomplete |

Inspecting text content to determine whether an agent has finished fails whenever the model outputs natural language
thoughts prior to calling a tool.

The `length` finish reason requires its own branch. When output hits the token ceiling, the returned text represents
a truncated response. Returning this string downstream passes an incomplete answer as a successful result. Your
runtime must catch this state and raise an exception or trigger a continuation strategy.

The `max_steps` budget counts total model invocations. Model calls account for API cost and latency. Configure step
budgets according to task complexity: 2 to 3 steps for lookups, 6 to 10 for multi-source gathering.

When the step budget is exhausted, raise an exception containing the accumulated messages. Returning partial
text hides loop exhaustion behind what appears to be a valid response. Attaching the message transcript ensures
debugging tools can inspect which tools were invoked prior to budget failure.

## What a step costs

Each loop iteration resends the cumulative message history. Step seven incurs token costs for the initial question,
all seven assistant turns, and all intervening tool results.

Input token counts grow linearly with each turn, causing cumulative run costs to scale quadratically with step count.
The primary driver of agent cost is often tool payload size rather than base model selection. A tool that returns
an entire document instead of relevant excerpts increases the input token overhead of all subsequent steps.

Keep tool outputs concise and position stable system instructions and schemas at the beginning of the prompt to maximize
prompt cache reuse.
