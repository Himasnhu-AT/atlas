The model never sees your Python function. It sees a name, a description string, and a list of parameters with
their own descriptions. Every decision regarding when to invoke your code and what arguments to supply
derives from that schema and the active conversation context.

A tool schema acts as a prompt with a rigid structure. It requires the same care as a system prompt,
written with an understanding of where models typically fail.

## Two components that must stay separate

The schema is read by the model but never executed. The function is executed by your runtime but never
directly inspected by the model. They connect only through a name and a dispatch table you control.

```python
{
  "type": "function",
  "function": {
    "name": "lookup_order",
    "description": "Look up one order by its id.",
    "parameters": {
      "type": "object",
      "properties": {
        "order_id": {"type": "string", "description": "The order id, like ORD-4821."},
      },
      "required": ["order_id"],
      "additionalProperties": False,
    },
  },
}
```

This structure matches the OpenAI chat completions schema, which most providers mirror and which
`mockllm` follows. Anthropic's Messages API uses the same JSON Schema format under a slightly
different envelope, using `input_schema` instead of a nested `parameters` object. The schema
itself is identical in both.

Separating the schema from execution provides practical advantages. The schema can expose a narrower contract
than the underlying function accepts, preventing the model from accessing supported arguments you prefer to
keep private. Furthermore, the arguments generated by the model arrive as untrusted JSON strings. Your runtime
must validate them against the schema before invoking the function. Provider APIs do not perform this validation
for you.

## The supported JSON Schema subset

JSON Schema is an expansive specification, but only a small subset reliably guides model tool calls:
`type`, `properties`, `required`, `enum`, `description`, `items` for arrays, and nested objects.

Other keywords, such as `minimum`, `maxLength`, `pattern`, and `format`, behave inconsistently across providers.
Some providers forward them to the model context, some ignore them silently, and some reject the schema during
request validation. Even when forwarded, a constraint acts only as a generation bias in token sampling rather
than a runtime invariant.

Express constraints within the supported subset, detail edge cases in the parameter description, and validate
all inputs explicitly at runtime before execution. Relying on unsupported keywords that providers drop silently
introduces hidden validation holes.

Provider implementations also differ in strictness modes. OpenAI's strict function calling mode requires
`additionalProperties: false` and demands that every property appear in the `required` array. In strict mode,
an optional argument is represented as a union with `null` rather than omitted from the list.

Under constrained decoding, the sampler cannot emit a malformed argument object. However, if a response is
cut off by an output token limit, the incomplete JSON arrives with a `finish_reason` of `length` rather than
a catchable parse error. Lesson 3 handles this case with an explicit branch. Provider schemas change over time,
so consult vendor documentation for current constraints.

## Write the description for the model, not the changelog

Vague schemas consistently trigger incorrect tool calls:

```python
{"name": "search", "description": "Search.",
 "parameters": {"type": "object",
                "properties": {"q": {"type": "string", "description": "Query"},
                               "n": {"type": "integer", "description": "Number"}},
                "required": ["q"]}}
```

This schema omits the search target, prompting the model to invoke it for unrelated queries like weather.
It fails to explain what `n` measures, causing the model to pass page offsets instead of counts. The parameter `q`
lacks formatting guidance, causing models to pass full natural language questions to keyword search endpoints.

Here is the revised schema:

```python
{"name": "search_help_articles",
 "description": "Search the customer help centre for articles about billing, shipping and "
                "returns. Use this before answering any question about company policy. It "
                "does not know about a specific customer's orders.",
 "parameters": {"type": "object",
                "properties": {
                    "query": {"type": "string",
                              "description": "Two to six keywords, not a sentence. "
                                             "For example: refund window international."},
                    "limit": {"type": "integer",
                              "description": "How many articles to return, 1 to 10. "
                                             "Default 3."}},
                "required": ["query"]}}
```

The name clarifies the target data source. The description defines when to invoke the tool and when to avoid it.
Explicitly stating what a tool does not cover prevents incorrect dispatches. The parameter descriptions provide
concrete examples and specify value ranges.

Parameter names also shape generation. Generic identifiers like `q` and `n` provide weak context, whereas
descriptive names like `query` and `limit` match common conventions found in training data.

## Required, optional, and parameter descriptions

A required parameter must be generated by the model. An optional parameter introduces a branching decision
during generation.

Vague optional descriptions are a frequent source of malformed calls. When presented with ambiguous fields like
"Filters" or "Options", models either invent plausible structures or omit necessary data. If a parameter is
optional, the description should state the default behavior when omitted.

Enums provide structured constraints for finite value sets:

```python
"status": {"type": "string",
           "enum": ["pending", "shipped", "delivered", "cancelled"],
           "description": "Order status to filter by. Omit for all statuses."}
```

An unconstrained string parameter invites variations such as `"in transit"`, `"Shipped"`, or `"on its way"`,
requiring downstream normalization. Under constrained decoding, enum values are enforced during sampling.

## How many tools before selection degrades

Tool selection degradation depends on tool similarity rather than an arbitrary count threshold.

Selection accuracy degrades first between overlapping tools rather than across distinct tools. Twenty tools
with distinct domains behave more reliably than six tools where three perform similar search operations. The primary
remedy is clarifying negative boundaries in tool descriptions rather than arbitrarily removing tools.

Token costs accumulate across steps. Every tool schema is sent on every model call in the loop, meaning large toolsets
increase token consumption on every turn.

Large tool lists also dilute attention across the system prompt, weakening instruction adherence.

When managing large tool collections, filter tool availability per turn based on conversation state rather than
passing the entire catalog to every request. Routing between specialized agents represents the same pattern at a higher
level, as covered in module 6.

## Your exercise

You will implement the schema layer: `split_docstring` to extract descriptions from an `Args:` block,
`build_schema` to generate a schema from a function signature, `build_registry` to index functions by name,
`validate_arguments` to check arguments against schemas, and `dispatch` to handle execution.

The test suite verifies that parameter descriptions populate the schema, that nonexistent enum parameters raise
errors immediately, and that argument validation runs before function invocation.

Note two implementation details. First, because the module includes `from __future__ import annotations`, type
annotations resolve as strings. Use `inspect.get_annotations(fn, eval_str=True)` or handle string mappings as
noted in the docstring. Second, in Python, `isinstance(True, int)` evaluates to `True`. Ensure integer checks
reject boolean values so the model does not pass boolean flags to integer arguments.
