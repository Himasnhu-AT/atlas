A basic agent loop crashes on the first encountered error. While failing fast simplifies initial debugging,
production agents must handle recoverable failures cleanly. Unhandled errors fall into four distinct categories,
each requiring a specific response strategy.

## Four failures, and where each one goes

| What happened | Source of failure | Runtime action |
| --- | --- | --- |
| The model requested a nonexistent tool | Model generation | Return tool error observation, continue loop |
| Arguments fail parsing or schema validation | Model generation | Return validation error observation, continue loop |
| Tool raised an execution exception | Tool runtime (recoverable) | Return exception observation, continue loop |
| Provider API returned an error (e.g. 503) | External infrastructure | Retry request with exponential backoff, omit from context |

The first three categories represent execution feedback. The model attempted an action, the runtime processed it,
and the outcome was unsuccessful. Returning a structured tool error observation provides actionable feedback,
allowing the model to select an existing tool, correct invalid parameter types, or supply alternative query arguments.

Crashing immediately discards valid progress from prior turns and drops successful results from the current batch.

The fourth category requires different handling. An HTTP 503 from an API provider indicates an infrastructure issue,
not a decision made by the model. Appending infrastructure failures into the conversation wastes context tokens
and misleads the model into modifying a valid tool call.

## What an error observation should contain

The tool message payload represents the model's only visibility into failure causes. Error strings should state
what failed, why it failed, and what parameters are valid:

```python
"error: unknown tool 'lookup_pop'. Available tools: lookup_population, lookup_timezone"
"error: LookupError: no population on file for 'Atlantis'. On file: lagos, paris, tokyo"
"error: wrong arguments for lookup_population: unexpected keyword argument 'town'"
```

Compare these with raw exception strings:

```python
"error: KeyError"
"error: 'town'"
"Traceback (most recent call last):\n  File \"agent.py\", line 74, in dispatch..."
```

Generic error strings provide insufficient guidance, while full tracebacks consume excessive context tokens
without actionable instructions.

Including the exception type helps the model determine recovery strategies. A `LookupError` signals that alternative
lookup keys may exist, whereas a `ConnectionError` indicates a service outage where repeated attempts with
different arguments will not succeed.

Never include sensitive internal hostnames, credentials, or proprietary environment variables in error messages,
as message transcripts may appear in telemetry logs or user-facing responses.

## Retrying provider failures

Wrap model API invocations in retry logic with backoff:

```python
for attempt in range(attempts):
    try:
        return client.chat.completions.create(model=model, messages=messages, tools=tools)
    except APIError as error:
        if error.status_code not in RETRYABLE_STATUS:
            raise
        if attempt == attempts - 1:
            raise
        sleep(base_delay * (2**attempt))
```

Retry only transient status codes, such as rate limits (429) and server errors (5xx). Client errors (400) indicate
malformed requests that will fail repeatedly, while authentication errors (401) will not resolve on subsequent attempts.

Exponential backoff reduces request pressure during provider outages. In production environments, add jitter
(a randomized timing offset) to prevent synchronized retries across concurrent clients.

When retry attempts are exhausted, re-raise the provider exception so upstream callers can inspect the HTTP status code.

Retrying model calls is safe because the request is idempotent. Retrying tool executions requires care, as tools
with side effects (such as payment processing or state mutations) must not execute repeatedly without idempotency keys.

## Detecting repetitive failure loops

Returning errors as observations introduces the risk of repetitive failure loops: a model encounters an error,
repeats the identical call, receives the same error, and consumes its step budget without progress.

A `max_steps` budget limits total calls but fails to identify where execution stalled. Track call failures by signature
(tool name plus sorted argument pairs). Terminate the run when an identical call signature fails multiple consecutive times.

Setting a threshold of three attempts allows the model to attempt error recovery while preventing endless loops on
deterministic failures.

## Returning structured run summaries

Inside the agent loop, budget exhaustion represents a hard boundary. At the application integration boundary,
an incomplete run represents structured result data that callers must handle.

```python
@dataclass(frozen=True)
class AgentRun:
    answer: str
    ok: bool
    reason: str      # answered, max_steps, repeated_failure, provider_error
    steps: int
    messages: list[dict]
```

The `reason` field differentiates between system states:
- `max_steps`: The step budget was insufficient for task complexity.
- `repeated_failure`: A tool schema or validation rule caused repeated bad calls.
- `provider_error`: Upstream API infrastructure failed.

Always include the message transcript in `AgentRun` so failures can be inspected and debugged.
