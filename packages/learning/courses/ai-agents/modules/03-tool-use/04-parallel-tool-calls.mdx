A basic loop handles multiple tool requests if the inner loop iterates over `choice.message.tool_calls`
instead of reading only `tool_calls[0]`. However, executing multiple calls sequentially introduces latency
when calls involve network operations, and unhandled exceptions in any single call can break the entire batch.

A batch represents a single turn containing multiple independent operations. Each operation can succeed or fail
separately, and the resulting message list must remain well-formed regardless of completion order.

## Models batch when calls do not depend on each other

If a user requests the population of three cities, a capable model can emit three lookup requests in one turn.
If the user asks for the population of the largest city in a country, the model cannot batch those calls, because
it cannot supply the second call's arguments until it receives the first call's output.

Task dependency dictates whether batching is possible. A model attempting to batch dependent calls must guess
missing arguments, which causes incorrect tool invocations.

Model providers expose controls for this behavior. For example, OpenAI provides `parallel_tool_calls: false`
to restrict turns to a single tool call. Disabling parallel execution is useful when tools produce side effects
and subsequent decisions depend on intermediate state. However, serializing calls increases total round-trip latency.

## What a batch changes about the message list

Batching alters message counts rather than protocol structure. Three tool requests in a turn produce a single
assistant message containing all three call definitions, followed by three tool messages:

```python
{"role": "assistant", "content": None, "tool_calls": [
    {"id": "call_a", "type": "function", "function": {"name": "lookup_population", ...}},
    {"id": "call_b", "type": "function", "function": {"name": "lookup_population", ...}},
    {"id": "call_c", "type": "function", "function": {"name": "lookup_timezone", ...}},
]},
{"role": "tool", "tool_call_id": "call_a", "content": '{"city": "Paris", ...}'},
{"role": "tool", "tool_call_id": "call_b", "content": "error: LookupError: ..."},
{"role": "tool", "tool_call_id": "call_c", "content": "Asia/Tokyo"},
```

Every requested call ID must have a matching tool message in the conversation. If three calls are requested,
omitting one tool response results in an invalid payload that providers reject.

Tool messages match requests by `tool_call_id`. Maintain request order when appending tool results. Appending
results in completion order causes non-deterministic message histories across runs due to variable network
latencies, creating flaky tests and difficult transcript diffs.

## Handling partial batch failures

Consider a batch where three calls execute: the first succeeds, the second raises `LookupError`, and the third
succeeds.

Letting the exception propagate unhandled aborts the agent run, drops the successful results, and prevents the
model from seeing which call failed.

Capture exceptions per call and format the error message into that specific tool's response payload:

```python
try:
    result = fn(**arguments)
except Exception as error:
    return ToolResult(call.id, name, f"error: {type(error).__name__}: {error}", ok=False)
```

The `ok` attribute supports internal metrics, logging, and retry logic. The model inspects only the string content.

Include the exception type alongside the error message. A message like `LookupError: no population on file for 'Atlantis'`
signals that alternative arguments may work. A message like `ConnectionError: timed out` signals an external service failure.

## Running tools concurrently while preserving order

Tool operations often spend most of their execution time waiting for I/O operations (HTTP requests, database queries, file access).
Running three 400ms calls sequentially takes 1.2 seconds, whereas concurrent execution finishes in roughly 400ms.

Use `ThreadPoolExecutor` to handle concurrent I/O:

```python
with ThreadPoolExecutor(max_workers=max_workers) as pool:
    futures = [pool.submit(run_one, registry, call) for call in calls]
    return [future.result() for future in futures]
```

Submitting futures in request order and collecting results in the same order preserves sequence regardless of
which worker finishes first.

Avoid sorting messages by arrival time with `as_completed` in conversation state. Latency-ordered message histories
vary across identical runs, complicating automated testing and trace diffing.

If tools perform CPU-intensive computations, thread pools offer minimal benefit and process pools are required.
Most agent tools primarily perform network or database I/O.

## When concurrency creates problems

Concurrency introduces issues in two scenarios.

The first is data dependency: a subsequent call requires values produced by a prior call. Models should execute
dependent calls across separate turns.

The second is shared state: multiple tools modifying the same record, updating a shared database row, or mutating
in-memory variables concurrently create race conditions. Ensure tools with side effects are thread-safe or enforce
sequential execution for stateful operations.
