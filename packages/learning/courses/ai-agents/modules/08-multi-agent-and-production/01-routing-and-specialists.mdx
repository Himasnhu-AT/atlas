As an agent grows, its system prompt accumulates edge-case instructions and its tool registry expands. Eventually, contradictory instructions collide and tool selection accuracy drops.

Separating a monolithic agent into focused specialists addresses these scaling limits.

## Prompt contention and tool confusion

Contradictory instructions rarely enter a prompt simultaneously. They accumulate incrementally: one instruction enforces confirmation before processing refunds, while another mandates resolving billing inquiries in a single turn. When evaluated together, the model arbitrates between competing directives unpredictably across runs.

A large tool registry presents a similar problem. Every added tool occupies space in the schema payload evaluated on each inference step. Irrelevant tools increase the probability of false matches. If multiple tool descriptions overlap (such as `get_order`, `get_order_status`, and `lookup_order`), the model struggles to differentiate them cleanly.

Splitting the agent into dedicated specialists isolates prompts and limits tools to relevant subsets.

However, introducing multiple agents adds overhead. Routing adds an extra inference step and introduces an additional failure point. If an intent router achieves 95% accuracy and a downstream specialist achieves 95% accuracy, compound reliability across independent failure modes drops to roughly 90%. Misrouted requests often produce confident errors because the assigned specialist lacks the appropriate tools.

Splitting an agent is justified by measured failure rates, such as prompt degradation or tool confusion, rather than architectural preference.

## Routing as classification

At runtime, a router operates as a classifier paired with a dispatch table: it maps an incoming request to a category label and invokes the associated handler.

```python
@dataclass(frozen=True)
class Route:
    name: str
    description: str
    handler: Callable[[Handoff], str]
    keywords: tuple[str, ...] = ()
```

The route description serves as the semantic target evaluated during classification. A vague description like "billing" provides minimal signal. A descriptive target like "invoices, refunds, card charges and plan changes" gives the classifier explicit phrases to match against user inputs such as "my card was charged twice".

## Routing mechanisms

Three common approaches implement intent routing:

```
rules            score keywords or patterns, pick the best
label            one model call that returns a route name
tool call        give the model the routes as tools and let it call one
```

| Approach | Cost | Latency | Accuracy | Failure Mode |
| --- | --- | --- | --- | --- |
| Rules | None | None | High on anticipated vocabulary | Unanticipated phrasing fails to match |
| Model label | Single lightweight call | Single round trip | High on ambiguous natural language | Borderline inputs produce unstable labels |
| Tool invocation | Single call with tool schemas | Single round trip | High, supports structured arguments | Zero calls or multiple simultaneous calls |

Using tools for routing combines classification with the initial execution step, allowing the model to generate structured parameters immediately. However, the runtime must handle scenarios where the model emits multiple tool calls or declines to invoke any tool.

Variability in model outputs can occur even at temperature zero due to batched execution dynamics and floating-point non-associativity on provider hardware. Borderline inputs with close confidence scores may flip classification categories across retries.

A practical hybrid architecture evaluates deterministic rules first, falling back to a model classifier only when rules produce no match.

### Format of the classification request

A standard classification request passes route definitions in the system prompt and places the user query at the end:

```python
messages = [
    {"role": "system", "content": (
        "Classify the user's request into exactly one route.\n"
        "Routes:\n"
        "billing: invoices, refunds, card charges and plan changes\n"
        "tech: crashes, errors and anything that stopped working\n"
        "general: anything that does not clearly belong elsewhere\n"
        'Answer with JSON only: {"route": "<name>", "confidence": <0.0-1.0>}'
    )},
    {"role": "user", "content": "my card was charged twice after the app crashed"},
]
```

Classifier responses must be handled across several output formats:

```
{"route": "billing", "confidence": 0.91}      Valid and usable
{"route": "billing", "confidence": 0.55}      Below confidence threshold (0.6)
{"route": "refunds", "confidence": 0.93}      Route name absent from registry
Probably billing, though it mentions a crash.  Unstructured text instead of JSON
```

When an LLM generates a route label outside the allowed set, the dispatcher must catch the invalid key and trigger fallback logic.

Additionally, models frequently wrap JSON outputs in markdown code fences:

````
```json
{"route": "billing", "confidence": 0.91}
```
````

To avoid unnecessary retry latency, parse and strip code fence markers before deserialization:

```python
if stripped.startswith("```"):
    stripped = stripped.split("\n", 1)[-1]
    stripped = stripped.rsplit("```", 1)[0].strip()
```

Structured output modes enforce JSON schemas at the provider level when supported, eliminating formatting errors.

## Handling unclassifiable requests

If a model must choose from a fixed list of labels, it will select one even when none apply. Ambiguous or out-of-scope requests can therefore be routed to the wrong specialist.

Two controls address this risk:
1. Require a confidence score in the output and enforce a minimum threshold.
2. Provide an explicit fallback route to handle unclassified inputs.

Reported confidence scores represent relative ranking signals rather than calibrated probabilities. They serve as tunable thresholds against production traffic.

The fallback route should direct ambiguous requests to a general handler capable of asking clarifying questions or triaging for human review.

## Preserving context across handoffs

When delegating a request to a specialist, the router must forward the complete conversation history rather than solely the final user turn:

```python
handoff = Handoff(request=request, history=tuple(history), reason=decision.reason)
```

If a user previously referenced multiple invoice numbers and then states "refund the second one", the specialist requires the preceding conversation history to resolve the reference.
