Intent routing directs an entire query to a single specialist. However, composite requests (such as "compare our pricing against competitor pricing and evaluate seat minimums") involve multiple independent tasks and a synthesis step that exceed the scope of a single specialist.

Complex workflows require multi-agent coordination topologies.

## Coordination topologies

Three structural patterns define multi-agent architectures:

```
pipeline      A -> B -> C

orchestrator      +-> W1 -+
              O --+-> W2 -+--> O
                  +-> W3 -+

peer group    A <-> B <-> C
```

**Sequential pipeline.** Stages execute in a fixed linear order, with each stage consuming output from the prior step. Pipelines are straightforward to debug and reason about because data flows through a deterministic sequence. However, execution stages are static and cannot adapt dynamically to varying prompt structures.

**Orchestrator and workers.** A central orchestrator evaluates the prompt, generates a decomposition plan of independent subtasks, dispatches subtasks to parallel workers, and aggregates the returned structured results. This topology adapts dynamically to per-request requirements while enabling concurrent execution.

**Autonomous peer group.** Agents communicate bidirectionally and negotiate task assignments without a centralized coordinator. This pattern offers high conversational flexibility but sacrifices predictability. Execution bounds become difficult to enforce, costs fluctuate unpredictably, and reproducing system traces requires logging complex conversational states.

In production engineering, the orchestrator-worker topology is preferred because clear ownership boundaries exist: the orchestrator is responsible for planning and aggregation, while individual workers execute strictly bounded tasks evaluated in isolation.

## Decomposition failures and plan validation

The orchestrator decomposes a broad task into discrete subtasks. Planning errors generally fall into two categories:

**Subtask overlap and duplication.** Planners may emit semantically redundant tasks, such as "find the list price on the pricing page" alongside "on the pricing page, find the list price". Redundant tasks waste inference budget without gathering new information.

A token-set fingerprint catches exact restatements efficiently:

```python
WORD = re.compile(r"[a-z0-9']+")

def goal_fingerprint(goal):
    return frozenset(WORD.findall(goal.lower()))

goal_fingerprint("find the list price on the pricing page") == \
    goal_fingerprint("on the pricing page, find the list price")   # True
```

**Task dependency in parallel plans.** A plan cannot execute subtasks concurrently if one subtask depends on intermediate outputs from another (for example, attempting to calculate price differentials before retrieving competitor pricing). Dependent tasks require sequential staging rather than concurrent fan-out.

Validating the plan before dispatching workers intercepts structural errors early:

```python
problems = plan_problems(subtasks, max_workers=self.max_workers)
if problems:
    raise PlanError("; ".join(problems))
```

Validating the plan prior to execution incurs only the single planning call, preventing failed concurrent worker runs.

## Structured worker outputs

Workers should return strongly-typed structured schemas rather than free-form prose.

```python
WorkerResult(
    subtask_id="t1",
    status="ok",
    key="price",
    value="49",
    confidence=0.8,
    evidence="pricing-page",
)
```

Enforcing structured output yields several operational benefits:
- The orchestrator can match the returned `key` against the requested subtask specification, catching off-topic worker outputs before aggregation.
- The `status` field differentiates between empty findings, tool network timeouts, and missing source citations, enabling targeted retry logic.
- Structured key-value pairs allow deterministic aggregation without requiring an extra LLM call to parse worker summaries.

## Aggregation and resolving worker conflict

Aggregating worker results involves filtering failed tasks, resolving conflicting findings, and structuring the combined output.

When independent workers gather data on the same attribute from different sources, returned values may conflict:

```
t1  seats = "5"   confidence 0.30   evidence  onboarding-deck
t2  seats = "5"   confidence 0.30   evidence  onboarding-deck-v2
t3  seats = "10"  confidence 0.90   evidence  signed-contract
```

Counting worker votes directly would assign majority weight to "5" (2 against 1), despite both workers drawing from the same outdated presentation slide.

Instead, group findings by distinct candidate values and evaluate the maximum confidence score associated with each candidate:
- Value "10" holds a maximum confidence of 0.90 (supported by the signed contract).
- Value "5" holds a maximum confidence of 0.30.

When the highest confidence score strictly exceeds competing scores, accept the top candidate. If competing values yield tied confidence scores, mark the key as unresolved and omit it from conclusive findings rather than guessing based on list order.

## Cost multiplier in parallel execution

Fanning out tasks across multiple concurrent workers multiplies inference overhead:

```python
model_calls = 1 + len(subtasks)
```

Total token usage scales with the number of parallel workers and their prompt sizes. As demonstrated in [The research briefing project](lesson:ai-research-briefing.fan-out-and-what-it-costs), worker prompts often include retrieved documentation chunks, making the combined token consumption significantly higher than sequential single-turn calls.
