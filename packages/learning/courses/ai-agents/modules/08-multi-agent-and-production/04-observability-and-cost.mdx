Emitting structured telemetry logs during agent execution is the foundation of production observability. However, telemetry only provides value if the storage and query layer is structured to answer operational questions.

Production telemetry primarily addresses three requirements:
1. **Root cause analysis for single runs.** Inspecting the exact sequence of steps, tool calls, and model outputs for a specific user session.
2. **Failure classification across aggregated runs.** Categorizing errors across all executions to prioritize engineering fixes.
3. **Unit economic tracking.** Calculating cost per successfully completed task to guide pricing and operational scaling.

## Runs and steps

```python
@dataclass(frozen=True)
class StepRecord:
    run_id: str
    index: int
    kind: str        # "model", "tool", "validate"
    name: str
    outcome: str     # "ok", "error", "invalid", "aborted"
    prompt_tokens: int = 0
    completion_tokens: int = 0
    payload: dict = field(default_factory=dict)
```

The `run_id` binds individual execution steps to a single session. Generate a unique ID at the system entry point, propagate it across internal service boundaries and tool calls, and include it in client-facing error responses.

Separating `kind` from `outcome` keeps step classification orthogonal: `kind` identifies the component type (model invocation, tool execution, or validation check), while `outcome` records whether the step succeeded, failed, or timed out.

Core telemetry terminology:
- **Trajectory:** The sequence of internal steps and tool calls executed during a single agent run.
- **Transcript:** The user-facing conversational turns exchanged during a session.
- **Tracing:** The runtime instrumentation that records step events into structured telemetry objects like `StepRecord`.

## Sensitive data and redaction strategies

Telemetry payloads capture prompts, tool inputs, and intermediate outputs. These structures frequently contain personal data, credentials, and customer identifiers.

Redaction prevents sensitive data from propagating into persistent log storage and indexing tiers. Two architectural approaches manage redaction:

**Ingress redaction (scrub on write).** Sanitize sensitive keys before writing records to disk. This guarantees that backend storage never holds sensitive credentials or payment details, satisfying data retention and compliance requirements. However, scrubbing parameters can hinder debugging if the redacted argument caused the underlying runtime error.

**Egress redaction (scrub on read).** Store complete telemetry payloads in encrypted, access-restricted datastores and apply redaction filters at query time when presenting logs to operators. This preserves complete diagnostic traces but requires strict retention policies, encryption, and access controls.

A balanced approach applies ingress redaction unconditionally to high-risk secrets (API tokens, passwords, payment numbers) and egress redaction to operational identifiers requiring diagnostic inspection.

## Five failure buckets

Aggregating all errors into a single error rate obscures actionable signals. Classify failures into discrete operational categories:

| Category | Indicator | Remediation |
| --- | --- | --- |
| Provider error | Model API raises 5xx or rate limit | Implement exponential backoff or provider fallback |
| Tool error | Underlying tool or external service throws exception | Debug tool implementation or upstream service health |
| Malformed tool call | Model generates arguments violating tool schema | Refine tool parameter descriptions or adjust prompt formatting |
| Step budget exhausted | ReAct loop reaches iteration cap | Adjust execution limits or resolve cyclical reasoning loops |
| Output rejected | Final generation fails schema validation or guardrail | Update validation constraints or refine output prompting |

Classifying failures into specific buckets provides clear operational routing: rising provider errors indicate external outages, whereas climbing malformed tool calls following a deployment point to schema incompatibilities.

## Cost per completed task

Token consumption is reported on model completions:

```python
total += step.prompt_tokens / 1000 * prompt_price
total += step.completion_tokens / 1000 * completion_price
```

Pricing tables should be passed as runtime configuration rather than hardcoded in source files, ensuring costs adapt as provider rates fluctuate. Unknown model identifiers should raise explicit errors rather than defaulting to zero cost.

Track financial metrics based on **cost per completed task** rather than **cost per API call**:

```
                        Before      After validation retry
Model calls             300         500
Total cost              $9.00       $10.45
Cost per call           $0.030      $0.021     (Down 30%)
Tasks completed         90          95
Cost per completed      $0.100      $0.110     (Up 10%)
```

Adding lightweight retries lowers the average cost per call while increasing total inference cost per successful user outcome. Evaluating economics by completed tasks aligns measurement with delivered business value.

Failed runs must be factored into cost aggregations because they consume tokens without delivering results. When zero tasks complete successfully within a reporting window, cost per completed task evaluates to `math.inf` rather than zero.

## Early warning signals: step count and latency

Aggregate error rate acts as a lagging indicator. When underlying components degrade (such as degraded search relevance or ambiguous prompts), the agent initially compensates by taking additional steps within its execution budget.

Mean step count per completed task reveals degradation before hard budget limits trigger failures. An agent whose average trajectory climbs from 3 steps to 7 steps against an 8-step ceiling signals imminent failure risk, even while current runs report success.

Summary reports should track mean step counts across completed runs and flag individual outliers approaching step limits.
