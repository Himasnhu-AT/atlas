Evaluating standard prompts involves checking inputs against expected outputs. However, evaluating agents requires assessing intermediate execution trajectories alongside final answers.

An agent that calls destructive tools unexpectedly or loops excessively before arriving at a correct answer is flawed, even if the final text appears valid.

## Evaluation targets: outcomes and trajectories

Agent evaluation encompasses two distinct layers:

**Outcome evaluation.** Evaluates the final text response presented to the user. This verifies whether the customer question was answered, required information was included, and formatting guidelines were followed.

**Trajectory evaluation.** Evaluates intermediate execution steps, including which tools were invoked, call sequences, iteration counts, and untouched functions. Trajectory assertions catch three critical classes of errors:
1. Unintended side effects (invoking write tools without user confirmation).
2. Resource inefficiency (executing redundant tool calls).
3. Accidental success (arriving at a correct answer through an invalid path that will fail on slight input variations).

Four core trajectory assertions provide strong coverage:

| Assertion | Defect Detected |
| --- | --- |
| `called("search")` | Omitted necessary intermediate retrieval step |
| `never_called("issue_refund")` | Triggered unintended side effect |
| `called_in_order("search", "summarise")` | Executed operations in inverted dependency order |
| `at_most_steps(4)` | Exceeded execution budget or entered infinite loops |

Sequence checks should match ordered subsequences rather than exact equality. Requiring exact sequence equality causes tests to fail when an agent performs benign retries (such as issuing a refined search query). Subsequence matching verifies that key dependencies executed in proper order:

```python
def check(trajectory):
    cursor = 0
    for step in trajectory.steps:
        if cursor < len(wanted) and step.tool == wanted[cursor]:
            cursor += 1
    if cursor == len(wanted):
        return None
    return f"never reached {wanted[cursor]!r}"
```

## Deterministic graders and model-based judges

Evaluation suites should prioritize deterministic checks wherever feasible: validating JSON parsing, schema conformance, tool execution status, and substring assertions. Deterministic assertions run rapidly, cost nothing in inference, and yield reproducible results.

Model-based judges evaluate subjective output where exact string matching is insufficient. When implementing LLM judges, account for known systematic biases:

**Verbosity bias.** Evaluator models frequently assign higher scores to longer, more detailed responses regardless of conciseness. Mitigate this by providing explicit, property-focused evaluation rubrics.

**Self-enhancement bias.** Models score generations higher when text closely aligns with their own training distribution. Evaluator models should ideally differ from the generator model family.

**Position bias.** In pairwise comparisons, judges often favor the candidate presented first in the context. Mitigate position bias by evaluating candidate pairs in both orderings and discarding conflicting verdicts.

**Version drift.** Provider updates can alter judge scoring across time. Pin specific model versions and establish recalibrated baselines when updating evaluation models.

Integrate model evaluations into the standard assertion interface:

```python
def judged_by(client, rubric):
    def check(trajectory):
        verdict = ask_judge(client, rubric, trajectory.output)
        return None if verdict.startswith("PASS") else verdict
    return Assertion(name=f"judged_by({rubric!r})", check=check)
```

Non-deterministic model evaluations are best suited for asynchronous batch evaluation pipelines rather than blocking CI merge gates.

## Sourcing evaluation cases

Effective test cases originate from real production failures and incident postmortems.

When an agent encounters a bug in production, capture the reproduction inputs and convert the scenario into a permanent evaluation case. Over time, the test suite reflects the operational distribution of real-world edge cases.

Suite size determines measurement granularity. In a 20-case test suite, each case accounts for 5 percentage points of the aggregate pass rate, meaning the suite cannot detect performance shifts smaller than 5%.

## Regression gating and baselines

Relying solely on aggregate pass rates allows critical regressions to slip through unnoticed:

```
case                    baseline    after the change
refund-requires-auth    pass        FAIL
handles-empty-cart      fail        pass
cites-the-article       fail        pass
stops-at-budget         pass        pass
answers-in-one-step     pass        pass

pass rate               0.60   ->   0.80
```

Although the aggregate pass rate increased from 60% to 80%, the regression on `refund-requires-auth` represents an unacceptable safety failure.

Evaluation gates must evaluate per-case regressions against a stored baseline dictionary:

```python
regressions = sorted(name for name, ok in now.items() if baseline.get(name) and not ok)
ok = not regressions and suite.pass_rate >= floor
```

Using `baseline.get(name)` ensures newly added test cases do not trigger false regression alerts before baseline establishment, while the overall pass-rate floor prevents gradual performance degradation.

## Operational limits of evaluation suites

Evaluation suites measure known failure modes. Production traffic will inevitably surface novel behaviors not anticipated during test design.

A high pass rate verifies that previously identified bugs have not regressed, while continuous telemetry and incident feedback ensure the evaluation suite expands as new edge cases emerge.
