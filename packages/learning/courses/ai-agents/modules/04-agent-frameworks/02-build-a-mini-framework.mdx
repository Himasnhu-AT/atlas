A minimal framework comprises three components: a schema generator that converts Python functions into
tool definitions, a registry that indexes tools and handles dispatch, and an `Agent` class that manages
prompts, client connections, and the execution loop.

## The problem with manual tool definitions

Without a centralized registry, defining a tool requires synchronizing code in three places:

```python
def get_weather(city: str, unit: str = "celsius") -> str:
    ...

SCHEMAS = [                                    # manual definition
    {"type": "function", "function": {"name": "get_weather", ...}},
]

def dispatch(name, arguments):                 # manual dispatch
    if name == "get_weather":
        return get_weather(**arguments)
```

Maintaining separate definitions creates drift. Renaming a parameter in the function signature without
updating the schema leaves the model sending obsolete argument names. The mismatch surfaces as an unhandled
`TypeError` inside the runtime dispatch step.

Deriving the schema and dispatch handler directly from the function eliminates this synchronization problem:

```python
registry = ToolRegistry()

@registry.add
def get_weather(city: str, unit: str = "celsius") -> str:
    """
    Current weather for a city.

    Args:
        city: City name, for example 'Paris'.
        unit: celsius or fahrenheit. Defaults to celsius.
    """
    return f"18 degrees {unit} in {city}"
```

The function serves as the single source of truth.

## Deriving a schema from a signature

The `describe` function extracts metadata directly from function attributes:
- The tool name comes from `fn.__name__`.
- The summary description comes from the first line of the docstring.
- Parameter types come from type annotations.
- Parameter descriptions come from the `Args:` section of the docstring.

This produces the standard chat completions schema:

```python
{"type": "function",
 "function": {
     "name": "get_weather",
     "description": "Current weather for a city.",
     "parameters": {
         "type": "object",
         "properties": {
             "city": {"type": "string", "description": "City name, for example 'Paris'."},
             "unit": {"type": "string", "description": "celsius or fahrenheit. Defaults to celsius."},
         },
         "required": ["city"],
     }}}
```

The `unit` parameter is omitted from `required` because it provides a default value. Required parameter
handling must remain precise: marking an optional parameter as required forces the model to invent values,
while marking a required parameter as optional causes missing argument `TypeError`s during dispatch.

Two Python type mechanics require specific handling:
1. Stringified annotations: When files include `from __future__ import annotations`, annotations evaluate as strings.
Use `inspect.get_annotations(fn, eval_str=True)` to evaluate string expressions in the function's scope.
2. Generic types: Generic annotations like `list[str]` are instances of `types.GenericAlias`.
Use `typing.get_origin(annotation)` to unwrap the base type to `list`, mapping it to the JSON Schema `array` type.

## Where automatic schema derivation stops

Automatic schema derivation must reject types that cannot be expressed unambiguously in JSON Schema.
The implementation should raise `ToolSpecError` when encountering:
- Missing docstring summaries.
- Parameters lacking type annotations.
- Annotations not mapped in the supported type table.
- Variadic arguments (`*args` or `**kwargs`).

Union types like `str | None` cannot be represented as single primitives in basic schema tables, and variadic
keywords like `**kwargs` provide no named fields for the model to target.

Failing fast at registration time ensures configuration errors surface during application startup with clear
function names in the error message, rather than failing silently during production runs.

The docstring parser in this exercise (`parse_docstring`) implements a lightweight line-based format.
Production frameworks typically rely on dedicated AST or docstring parsing libraries to handle complex multi-line
descriptions and diverse docstring formats.

## Encapsulating execution in an agent class

The `Agent` class encapsulates the client, registry, system instructions, and step budget:

```python
registry = ToolRegistry([get_weather, get_forecast])

terse = Agent(client, registry, system="Answer in one word.")
chatty = Agent(client, registry, system="Explain your reasoning.")
```

Encapsulation allows multiple agents to share tool definitions while maintaining distinct prompts and budgets.

To ensure thread safety and avoid cross-run state pollution, all execution state must remain local to `Agent.run`:

```python
def run(self, question: str) -> AgentResult:
    messages: list[dict] = []          # local to execution
    records: list[ToolCallRecord] = []
    ...
```

Storing `messages` or execution counters on `self` causes subsequent calls to inherit prior conversation
histories, inflating token costs and causing race conditions in concurrent environments.

## Returning structured results

`Agent.run` returns an `AgentResult` object rather than a raw text string. This object captures the final answer,
step count, detailed `ToolCallRecord` items, and total token usage.

Returning structured execution records provides essential telemetry for debugging without requiring manual
trace parsing.

## Your exercise

Implement `parse_docstring`, `describe`, `tool`, `ToolRegistry`, and `Agent`.

The test suite validates:
1. Schema derivation for standard types and `list[str]` generic arrays.
2. Excluding default-valued parameters from the `required` list.
3. Raising `ToolSpecError` for unsupported types, variadic arguments, or missing docstrings.
4. Preserving tool registration order in schema outputs.
5. Capturing tool execution failures as structured records with `failed=True` and formatted error strings.
6. Isolating execution state across repeated calls to the same `Agent` instance.

Remember to resolve annotations using `eval_str=True` in `describe` so type lookups match primitive type keys.
