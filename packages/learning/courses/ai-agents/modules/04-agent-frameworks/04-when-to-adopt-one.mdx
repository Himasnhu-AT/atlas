      kind: text-contract
      prompt: >-
        This spec comes off disk and your loader rejects it. Fix it so it loads, using the
        registry and the bounds beside it.
      context:
        as: pairs
        items:
          - { k: tools in the registry, v: lookup, escalate, refund }
          - { k: max_steps, v: a whole number from 1 to 12 }
          - { k: name, v: how this agent is referred to in a log line and in a diff }

      lang: json
      initial: |
        {
          "name": "",
          "system": "Work out what the customer needs.",
          "tools": ["lookup", "lookup", "eskalate"],
          "maxSteps": 4,
          "temperature": 0.2
        }
      rules:
        - message: Syntax first. This no longer parses as JSON.
          check: { op: parses, as: json }
        - message: The name is empty. It is what a diff line and a trace refer to, so an unnamed agent is one you cannot talk about.
          check: { op: length, path: name, min: 1 }
        - message: temperature is not a key this loader knows. A dict accepts anything you type, which is exactly why unknown keys have to be an error rather than a shrug.
          check: { op: absent, path: temperature }
        - message: maxSteps is the same problem wearing camel case. Python would have told you at the call site, and a dictionary will not.
          check: { op: absent, path: maxSteps }
        - message: There is no max_steps now. A budget with no value is a run with no bound.
          check: { op: exists, path: max_steps }
        - message: max_steps has to be a whole number. A boolean passes an int check in Python, so the loader has to reject one explicitly.
          check: { op: type, path: max_steps, is: integer }
        - message: max_steps is outside the allowed range of 1 to 12.
          check: { op: range, path: max_steps, min: 1, max: 12 }
        - message: lookup is listed twice. Duplicates in the tool list mean a duplicated schema on every model call, paid for on every turn.
          check: { op: length, path: tools, min: 2, max: 2 }
        - message: eskalate is not in the registry. The closest name it holds is escalate.
          check: { op: equals, path: tools, value: [lookup, escalate] }
      hints:
        - Five things are wrong and two of them are keys rather than values.
        - Compare each key against what the loader accepts, then each value against the bounds.
        - One tool name is a typo and one is a repeat.
      reveal: >-
        All of this is caught before a single model call is made. That is the whole argument
        for the spec: a config error costs you a startup failure with a function name in it,
        rather than a run that dies on step three having already spent money. The price is
        that validation moved from the Python call site into your loader, so the loader has
        to be strict about types and about keys it has never heard of.
      solution: |
        {
          "name": "triage",
          "system": "Work out what the customer needs.",
          "tools": ["lookup", "escalate"],
          "max_steps": 4

        - id: tool-list
          label: The list of tool names this agent may use
          bucket: spec
          because: A whitelist is data, and putting it in the spec is what lets build_agent hand the agent a registry containing nothing else.
        - id: budget

          bucket: spec

        - id: model-name

          bucket: spec

        - id: tier-tools

        - id: fallback-model
          label: Retry twice, then fall back to a cheaper model

        - id: loop-until
          label: Loop until the invoice balances
          bucket: code
          because: A loop with a condition over application state. Python already has one and it is easier to read.

          label: Trim a tool result down before it is appended

        - Four of these depend on something that arrives with the request.
        - If expressing it in the file would need an if, it is not a file.
      reveal: >-
        Static properties as data, decisions as code. Config formats that acquire an

        have become programming languages with no editor support and no way to set a

          label: Read the spec, then build the registry subset in Python from the tier before constructing the agent.
          correct: true
          note: The spec stays a static whitelist and the tier decision stays where tiers are already known. The agent still receives a registry holding nothing it is not allowed to call.
        - id: condition-syntax
          label: Add a when field to the tool list so the file can express the condition.
          note: You have started a language. The second requirement adds an operator, the third adds nesting, and none of it has a type checker, a debugger, or a way to unit test a branch.

          label: Put a dotted import path in the file and have the loader import and call it.
          note: The same problem with worse failure modes. A typo becomes an ImportError at load time, the call site is invisible to your editor, and anything that can write config can now name code to run.

          label: Give the agent every tool and tell it in the system prompt not to refund free customers.
          note: A prompt is guidance, not a permission boundary. Anything that reaches the model's context can argue with it, and the tool is still on the list to be called.

        - The tier is known when the request arrives, which is before the agent is constructed.
        - Two of these turn the config file into something that runs.
        - The registry the agent receives is a value you build, not a fixed property of the spec.
      reveal: >-
        The tool list in the spec is a boundary because build_agent hands over a registry
        containing exactly those tools and no others. Narrowing that list in Python before
        construction keeps the boundary real, and keeps the file readable by somebody who
        does not know Python.

      kind: choice
      prompt: >-
        A library gives you a registry, retries, streaming, state channels and tracing. You

          label: You only need four of its five features.
          note: Four of five is most of it, and that argues for adoption rather than against. The version of this argument that bites is needing one of five and taking the whole dependency for it.
        - id: opaque-traces
          label: Its own failures surface as a KeyError several frames inside its executor, with no mention of your node.
          correct: true
          note: This is the cost you pay on every incident for as long as you use it. The other three are one-time or under your control, and this one is neither.
        - id: nobody-knows-it
          label: Nobody on the team has used it before.
          note: Real, and the cheapest of the four to pay. Onboarding is paid once per person and is mostly a function of how many concepts the library asks you to hold.

          label: Adopting it would put its types in every module.
          note: That is a choice rather than a property. Call it from your own loop and the coupling stays in a couple of files, which is also what makes leaving possible later.
      hints:
        - Three of the four are costs you pay once, or costs you get to decide the size of.
        - Ask which one you would still be paying in eighteen months, at three in the morning.
        - One of the four is not a fact about the library at all.
      reveal: >-
        Four questions rather than a mood: how much of it you need, what its failures look
        like, how much of your code it would touch, and how many concepts it asks a new
        engineer to hold. Having built the registry, the hooks, the tracer and the spec
        parser yourself, you can now open a library and see which of those it is, which is
        the only way to answer the first question honestly.

Many agent frameworks transition from procedural Python definitions to declarative data structures:

```python
agent = Agent(client, registry.subset(["lookup", "escalate"]),
              system="Work out what the customer needs.", max_steps=4)
```

```json
{"name": "triage",
 "system": "Work out what the customer needs.",
 "tools": ["lookup", "escalate"],
 "max_steps": 4}
```

Representing an agent as data allows configurations to be loaded from storage, diffed in source control,
generated programmatically, and shared across services.

## What declarative specifications provide

Representing agent configurations as data enables three practical capabilities:

1. Static validation before execution: `validate_spec` checks that names and prompts are populated, step budgets
remain within defined bounds, tool lists contain no duplicates, and every specified tool exists in the active registry.
Catching configuration errors at load time prevents runs from failing mid-execution after incurring model costs.

2. Structured diffing between revisions:

```python
diff_specs(before, after)
# ["name: 'triage' -> 'router'",
#  "system: changed",
#  "tools removed: escalate",
#  "max_steps: 4 -> 8"]
```

Comparing two specification dictionaries produces concise change summaries for pull requests. Large system prompts
can be flagged as changed while leaving detailed textual analysis to standard line-diff utilities.

3. Automated prompt and parameter optimization: When specifications are structured objects, evaluation harnesses
can generate variations in a loop, evaluating parameter permutations against standardized test sets.

In addition, specifying tool names as a list creates an explicit boundary. `build_agent` configures the agent with
a restricted registry containing only the declared tools in their specified order, ensuring agents cannot access
unintended functions.

## The limits of declarative configuration

Declarative schemas struggle when workflows require dynamic logic or control flow.

When an application requires conditional tool access based on runtime state (such as user subscription tier),
configuration formats often grow ad-hoc expression languages or dynamic string handler imports. At that point,
configuration becomes an untyped programming language without native debugging tooling.

Configuration formats work well for static properties like system prompts, tool whitelists, and numerical budgets.
When workflows require dynamic branching, loops, or complex state transformations, standard Python code provides
clearer execution semantics and better editor tooling.

Data formats also shift validation responsibility to your loader. Python syntax checkers validate argument names
in code, whereas dictionaries require explicit schema validation. The loader `spec_from_dict` must validate types
and reject unknown keys to catch typos before execution.

## Framework evaluation criteria

Evaluating third-party frameworks depends on specific system requirements:

### How much functionality is required

Frameworks bundle multiple features together (registries, retry policies, streaming, state channels, tracing).
If a project requires most of these capabilities, using an established framework saves engineering effort.
If a project only needs simple tool dispatch, adopting a large framework introduces unnecessary dependency
overhead.

### Debugging transparency

Examine framework failure behavior. Tracebacks should pinpoint application nodes and parameters clearly rather
than failing deep within internal executor loops with opaque dictionary key errors.

### Migration surface area

Consider the effort required to migrate off the library. Calling framework components from standard Python loops
limits migration surface area to specific integration files. Permeating framework types and decorators throughout
every application interface couples the entire codebase to that dependency.

### Team onboarding overhead

Evaluate the conceptual model required to understand the framework. Complex abstractions increase onboarding
time and require continuous maintenance overhead across the engineering team.

## Practical guidance

Building registries, hook systems, tracers, and specification parsers from scratch demystifies framework internals.
When evaluating commercial libraries, you can assess how each feature is structured and determine whether it
aligns with your system's architecture.
