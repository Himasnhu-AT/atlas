Many agent frameworks transition from procedural Python definitions to declarative data structures:

```python
agent = Agent(client, registry.subset(["lookup", "escalate"]),
              system="Work out what the customer needs.", max_steps=4)
```

```json
{"name": "triage",
 "system": "Work out what the customer needs.",
 "tools": ["lookup", "escalate"],
 "max_steps": 4}
```

Representing an agent as data allows configurations to be loaded from storage, diffed in source control,
generated programmatically, and shared across services.

## What declarative specifications provide

Representing agent configurations as data enables three practical capabilities:

1. Static validation before execution: `validate_spec` checks that names and prompts are populated, step budgets
remain within defined bounds, tool lists contain no duplicates, and every specified tool exists in the active registry.
Catching configuration errors at load time prevents runs from failing mid-execution after incurring model costs.

2. Structured diffing between revisions:

```python
diff_specs(before, after)
# ["name: 'triage' -> 'router'",
#  "system: changed",
#  "tools removed: escalate",
#  "max_steps: 4 -> 8"]
```

Comparing two specification dictionaries produces concise change summaries for pull requests. Large system prompts
can be flagged as changed while leaving detailed textual analysis to standard line-diff utilities.

3. Automated prompt and parameter optimization: When specifications are structured objects, evaluation harnesses
can generate variations in a loop, evaluating parameter permutations against standardized test sets.

In addition, specifying tool names as a list creates an explicit boundary. `build_agent` configures the agent with
a restricted registry containing only the declared tools in their specified order, ensuring agents cannot access
unintended functions.

## The limits of declarative configuration

Declarative schemas struggle when workflows require dynamic logic or control flow.

When an application requires conditional tool access based on runtime state (such as user subscription tier),
configuration formats often grow ad-hoc expression languages or dynamic string handler imports. At that point,
configuration becomes an untyped programming language without native debugging tooling.

Configuration formats work well for static properties like system prompts, tool whitelists, and numerical budgets.
When workflows require dynamic branching, loops, or complex state transformations, standard Python code provides
clearer execution semantics and better editor tooling.

Data formats also shift validation responsibility to your loader. Python syntax checkers validate argument names
in code, whereas dictionaries require explicit schema validation. The loader `spec_from_dict` must validate types
and reject unknown keys to catch typos before execution.

## Framework evaluation criteria

Evaluating third-party frameworks depends on specific system requirements:

### How much functionality is required

Frameworks bundle multiple features together (registries, retry policies, streaming, state channels, tracing).
If a project requires most of these capabilities, using an established framework saves engineering effort.
If a project only needs simple tool dispatch, adopting a large framework introduces unnecessary dependency
overhead.

### Debugging transparency

Examine framework failure behavior. Tracebacks should pinpoint application nodes and parameters clearly rather
than failing deep within internal executor loops with opaque dictionary key errors.

### Migration surface area

Consider the effort required to migrate off the library. Calling framework components from standard Python loops
limits migration surface area to specific integration files. Permeating framework types and decorators throughout
every application interface couples the entire codebase to that dependency.

### Team onboarding overhead

Evaluate the conceptual model required to understand the framework. Complex abstractions increase onboarding
time and require continuous maintenance overhead across the engineering team.

## Practical guidance

Building registries, hook systems, tracers, and specification parsers from scratch demystifies framework internals.
When evaluating commercial libraries, you can assess how each feature is structured and determine whether it
aligns with your system's architecture.

## Your exercise

Implement `spec_from_dict`, `validate_spec`, `build_agent`, and `diff_specs`. The `AgentSpec`, `ToolRegistry`,
and `Agent` classes are provided.

The test suite validates:
1. Validating dictionary types and rejecting unknown specification keys.
2. Validating tool existence against the provided registry.
3. Suggesting close matches via `difflib` when a tool name is mistyped.
4. Constructing agents with isolated registries containing only declared tools in specification order.
5. Emitting deterministic change lists in `diff_specs`.
6. Rejecting boolean inputs for integer fields like `max_steps`.
