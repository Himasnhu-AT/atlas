[The loop you wrote in module 3](lesson:ai-tool-use.the-react-loop) is the engine. Call the model,
check `finish_reason`, run what it asked for, append the results, call again, stop when it stops
asking. Agent frameworks execute variations of this core loop.

The relevant architectural question is what capabilities are required around the loop to run it
in production systems.

## What the loop does not do

Here is the loop implemented previously:

```python
def run(client, registry, system, question, max_steps=6):
    messages = [{"role": "system", "content": system},
                {"role": "user", "content": question}]

    for _ in range(max_steps):
        response = client.chat.completions.create(
            model="mock", messages=messages, tools=registry.schemas,
        )
        choice = response.choices[0]
        if choice.finish_reason != "tool_calls":
            return choice.message.content or ""

        messages.append(assistant_turn(choice.message))
        for call in choice.message.tool_calls:
            result = registry.invoke(call.function.name, call.function.arguments)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})

    raise MaxStepsExceeded(max_steps)
```

Running this function in a larger application reveals missing production features.

Adding a second agent requires parameterizing prompts and registries. Adding debugging visibility requires
logging statements. Tracking usage requires threading token accumulators. Handling API outages requires retry
wrappers. Coordinating multiple agents requires handoff logic and conditional branching.

Each change adds parameters or helper blocks. Over time, an unstructured function accumulates numerous arguments
and becomes difficult to maintain. Frameworks provide standard abstractions for these cross-cutting concerns.

## The five core capabilities

Production agent frameworks structure five main areas:

| Capability | Purpose | Consequence without it |
| --- | --- | --- |
| Tool registry | Derives schemas from signatures, dispatches by name | Duplicate schemas that drift from implementation |
| State persistence | Stores run data outside the message transcript | State smuggled through natural language text |
| Control flow | Manages branching, parallelism, loops, and resumption | Ad-hoc loops and sentinel values in application code |
| Observability | Emits structured step records during execution | Unstructured print statements and missing audit logs |
| Error and retry policy | Centralizes failure handling and recovery rules | Fragmented try/except blocks across call sites |

State persistence isolates application data from the LLM conversation transcript. In a basic loop, `messages`
is the only persistent data structure between turns. Passing documents, user IDs, or numerical totals across steps
forces values into conversational prose. Frameworks provide typed state channels to decouple application memory
from model context.

Observability provides auditability when a multi-step run fails. Because LLM outputs and external tool states vary,
reproducing failures requires structured execution records captured at each step.

## Two execution models

Frameworks typically follow one of two architectural patterns:

A graph runtime models the agent as a state machine. Developers declare nodes and edges, while the runtime
engine schedules execution. LangGraph illustrates this approach. Because the engine controls scheduling, it
can checkpoint state between steps, resume or rewind runs, and execute concurrent graph branches. The trade-off
is that execution flow is distributed across node definitions and edge transitions rather than structured as
linear code.

A conversational runtime extends the sequential loop with targeted abstractions. Code executes sequentially.
The OpenAI Agents SDK follows this pattern with agent handoffs and guardrails. Pydantic AI applies a similar
approach centered on structured, typed output boundaries. This design preserves linear readability at the cost
of requiring custom implementations for distributed checkpointing and parallel graph branching.

You will implement both models later in this course. [Why a graph beats a loop](lesson:ai-state-graphs.why-a-graph-beats-a-loop)
covers graph runtimes with state schedulers and checkpointers. [Two runtimes, one loop](lesson:ai-handoffs-and-typed-output.two-runtimes-one-loop)
covers conversational runtimes.

## What adopting a framework costs

Adopting a third-party framework introduces specific trade-offs:

1. Debugging indirection: When a manual loop fails, the traceback points directly to local application code.
When a framework executor fails, tracebacks often traverse internal library files, obscuring configuration mistakes.
This indirection is the cost of higher-level abstraction.

2. Upstream dependency risk: Rapidly evolving agent libraries frequently introduce breaking interface changes
and deprecate core decorators. Evaluate library stability and release history before committing critical infrastructure.

3. Abstraction mismatches: Frameworks optimize for specific execution patterns. When application requirements
fall outside those patterns, developers must choose between working around framework internals, overriding private
APIs, or migrating off the library.
