When an agent run fails during an intermediate step, reproducing the exact state is difficult: models
sample non-deterministically, tool responses change, and input workloads vary. Tracing captures execution
state at every step during the live run.

This lesson implements tracing using two concepts: five lifecycle hooks in the execution loop, and a listener
that converts hook events into structured step records.

## Five lifecycle hook points

The execution loop interacts with external systems at specific transition boundaries. For a standard batching loop,
these transitions yield five hook points:

```python
before_model(index, messages)              # about to call the model
after_model(index, response)               # model call succeeded
before_tool(index, name, arguments)        # about to run a tool
after_tool(index, name, result, failed)    # tool call completed
on_error(index, error)                     # execution failed
```

Logging, metrics collection, caching, rate limiting, and approval workflows attach to these five points because
they represent all boundaries where data enters or leaves the loop.

Two operational behaviors govern these hooks:
1. `after_model` does not fire when the API call raises an exception; `on_error` fires instead, and the exception
propagates up the stack. Hooks observe state changes without swallowing execution errors.
2. `after_tool` includes the `failed` boolean flag, enabling listeners to record tool errors without inspecting
the text payload.

## Composition via hook lists

Managing cross-cutting concerns through subclassing leads to brittle inheritance hierarchies:

```python
class LoggingAgent(TracedAgent):
    def run(self, question):
        print("starting")
        return super().run(question)
```

Combining logging, token limits, and redacting requires multiple inheritance, which complicates method resolution
and fails when plugins need visibility inside the loop.

Using a list of hook instances avoids inheritance coupling:

```python
agent = TracedAgent(client, toolbox, hooks=[Tracer(), SpendCap(limit=5000), Redactor()])
```

Hooks execute sequentially in list order. Ordering is significant: a redactor must precede a logger to ensure
sensitive data is masked before logging.

Individual hook exceptions should be handled defensively to prevent telemetry failures from breaking core execution:

```python
for hook in self.hooks:
    try:
        hook.after_model(index, response)
    except Exception:
        pass
```

Isolate each hook invocation in its own `try/except` block so a failing listener does not prevent subsequent
hooks from running. Critical business invariants (like hard financial caps) belong in the core loop rather than
in optional hooks.

## Capturing step-level records

The fundamental unit of agent tracing is the model step, rather than the complete run or an individual tool call:

```python
StepRecord(
    index=1,
    messages=[{"role": "user", "content": "where is order A-1174?"}],
    response_text=None,
    finish_reason="tool_calls",
    tool_calls=["lookup_order"],
    prompt_tokens=94, completion_tokens=12,
    elapsed_ms=250,
    error=None,
)
```

The fields capture step details:
- `response_text` remains `None` when the model emits tool calls rather than text content.
- `tool_calls` preserves the ordered list of requested tools (a list rather than a set, preserving call repetitions).
- `messages` snapshots the active conversation list. Deep copies prevent later turns from mutating past records.

To support deterministic testing, pass an explicit clock function (defaulting to `time.monotonic`). Measure timing
by sampling the clock exactly twice per step (at start and end).

Handle `on_error` carefully:
- If a model call raises an exception, create a new `StepRecord` capturing the failure.
- If the run fails after a step has already closed (such as budget exhaustion), update the existing final record
rather than appending a duplicate entry.

## Redaction while preserving telemetry invariants

Production traces often contain user data that must be sanitized before persistence.

The `redact` function replaces specified text fields with a constant placeholder while preserving structural metadata:

```python
kept = redact(record, ["content", "response_text"])
```

Redacting masks message strings while retaining role sequences, call IDs, finish reasons, tool names, token counts,
and elapsed timings.

This design guarantees a structural invariant:

```python
summarise(redact(record, fields)) == summarise(record)
```

Because redaction targets text fields and `summarise` evaluates numeric metrics and tool identifiers, metric
calculations remain consistent on sanitized traces.

Ensure `redact` performs a deep copy of message dictionaries to avoid mutating live conversation memory.

## Deriving usage metrics from step records

`summarise` processes accumulated step records to calculate total steps, failed steps, token totals, overall
duration, and tool usage frequencies.

Capturing structured step records simplifies reporting into list aggregations, decoupling data collection from
specific metric queries.

to implement model pricing models, error taxonomy classification, and task-level cost analysis.
