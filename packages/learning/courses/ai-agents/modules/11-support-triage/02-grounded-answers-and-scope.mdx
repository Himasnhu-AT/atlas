The grounded answering workflow executes in four distinct stages:

1. **Retrieve**: Identify candidate knowledge base articles relevant to the user query.
2. **Prompt**: Construct structured context including retrieved documents and the target question.
3. **Call**: Execute a single model invocation against the structured prompt.
4. **Verify**: Parse and validate citation markers against the retrieved context.

Verification ensures that responses generated by the model reference real retrieved sources.

## Retrieval as an execution prerequisite

Language models generate plausible support responses even when relevant documentation is absent.
Enforcing grounding requires evaluating retrieval results before constructing the model prompt:

```python
hits = retrieve(articles, question, k=2, floor=0.12)
if not hits:
    return Reply(OUT_OF_SCOPE_TEXT, [], [], "out_of_scope")
```

If no articles satisfy the similarity floor, the system returns an `out_of_scope` routing state immediately.
Invoking the model without relevant context incurs unnecessary token costs and risks generating hallucinated policy details.

Calibrating the similarity floor balances recall and precision:
- Setting the floor too high filters out relevant articles, triggering unnecessary human escalations.
- Setting the floor too low includes irrelevant documents, inducing misleading answers.

To ensure deterministic evaluation, retrieval sorting must break score ties using article identifiers:

```python
scored.sort(key=lambda pair: (-pair[1], pair[0].id))
```

## Embedding mechanics and text preprocessing

In local testing environments, `mockllm.embed_text` uses a 256-dimensional feature hash.
Because feature hashing lacks semantic training weights, text normalisation (lowercasing and stopword filtering)
is required to prevent common grammatical words from inflating similarity scores.

Production retrieval pipelines apply equivalent preprocessing before passing queries to dense embedding models
or vector databases, ensuring similarity calculations emphasize domain keywords.

## Prompt composition and context ordering

The prompt structure organizes information to optimize model attention:

```python
[
    {"role": "system", "content": SYSTEM},
    {"role": "user", "content": "Context:\n\n[A2] Password reset\n..."},
    {"role": "user", "content": question},
]
```

- **System message**: Instructs the model to answer exclusively from the provided context and attach bracketed citation markers (such as `[A2]`) to every factual statement.
- **Context payload**: Presents retrieved articles with explicit identifier headers.
- **User question**: Positioned last to ensure the model attends to the specific user inquiry after reading the reference text.

## Citation parsing and verification

Citation verification validates that generated response tags match the set of retrieved document IDs:

```python
CITATION = re.compile(r"\[(A\d+)\]")

def parse_citations(text, allowed):
    permitted = set(allowed)
    cited, dropped = [], []
    for marker in CITATION.findall(text or ""):
        bucket = cited if marker in permitted else dropped
        if marker not in bucket:
            bucket.append(marker)
    return cited, dropped
```

`allowed` contains the article identifiers returned by the retrieval step. Any marker in the model output
outside this set is classified as `dropped`. This deterministic check flags hallucinated references and
prevents prompt injection tags copied from untrusted document bodies from being treated as valid citations.

## Dispatched routing states

The resulting `Reply` object assigns one of three operational routes:

- **`answered`**: The model generated text and included at least one verified citation from the retrieved context.
- **`out_of_scope`**: Retrieval returned no documents above the similarity threshold. The model was not invoked, and the session routes to human triage.
- **`unsupported`**: Retrieval returned valid context, but the model generated a response without valid citations.

Distinguishing `out_of_scope` from `unsupported` clarifies diagnostic logging: frequent `out_of_scope` routes indicate
knowledge base gaps, whereas frequent `unsupported` routes signal prompt ambiguity or model compliance failures.

## Production retrieval architecture

In production environments, vector indexes (such as pgvector or dedicated vector search engines) replace in-memory loops:

```python
# Reference production SQL query
rows = db.execute(
    "SELECT id, title, body, 1 - (embedding <=> %s) AS score "
    "FROM articles ORDER BY embedding <=> %s LIMIT 2",
    (query_vector, query_vector),
)
hits = [r for r in rows if r.score >= 0.12]
```

The downstream pipeline remains identical: format prompt context, execute the model call, verify citation markers,
and classify the response into explicit routing states.
