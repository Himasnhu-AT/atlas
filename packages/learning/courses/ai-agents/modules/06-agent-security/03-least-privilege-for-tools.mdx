In [tool schemas](lesson:ai-tool-use.tool-schemas), you constructed a tool registry dictionary containing every tool available to the agent, passed in its entirety on every iteration. While straightforward, that pattern exposes all capabilities on every turn regardless of execution phase.

## Dynamic tool availability

The runtime controls which tool definitions populate the `tools` array on each outgoing API call.

Instead of presenting the full registry on every turn, provide tools conditionally based on state:

```python
def tools_for(state):
    if state.phase == "gathering":
        return [search_docs, lookup_order]        # read only
    if state.phase == "acting" and state.approved:
        return [search_docs, lookup_order, refund_order]
    return [search_docs, lookup_order]
```

When an injected document attempts to trigger a refund during the `gathering` phase, `refund_order` is absent from the schema definition. The model cannot emit a valid tool call for a tool that does not exist in its prompt payload.

System sandboxing answers security boundary requirements by denying capabilities at runtime rather than relying on model compliance.

## Core state distinctions

Three operational distinctions cover most agent workflows:

**Read versus write operations.** Tools that read data (such as search or lookup functions) should be isolated from tools that mutate records, execute payments, or send outbound messages.

**Pre-confirmation versus post-confirmation.** Destructive or write-heavy actions remain unavailable until an explicit authorization step or human review completes.

**Scoped resource boundaries.** Restrict tools to specific resource identifiers tied directly to the authenticated session context.

## Constraining arguments against session state

Exposing `refund_order` without parameter verification allows an agent to emit calls against arbitrary resource IDs.

Parameter validation must execute against verified session state that the LLM cannot manipulate:

```python
def check(call, session):
    if call.name != "refund_order":
        return Allow()
    order = session.orders.get(call.arguments["order_id"])
    if order is None:
        return Deny("that order is not in this session")
    if order.total > session.limits.auto_refund:
        return Deny("over the automatic limit")
    return Allow()
```

The validation reads `session.orders` populated directly by authentication services. The validation policy inspects values that the prompt context cannot modify.

This check protects against both malicious injection and accidental model confusion, such as mixing up entity IDs across long conversation histories.

## Handling denials as tool observations

When authorization denies a tool call, the execution loop records an observation rather than raising an unhandled exception, matching the pattern established in [when tools fail](lesson:ai-tool-use.when-tools-fail):

```json
{"role": "tool", "content": "refund_order was not permitted: over the automatic limit"}
```

This returns a clear status back to the model, allowing the agent to explain the constraint or suggest an escalation path.

Denial messages become part of the ongoing prompt context. Error messages returned to the model should avoid exposing internal security rules, sensitive environment metadata, or administrative bypass keys.
